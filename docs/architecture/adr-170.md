# ADR-170: Slice 7 — CompletionMetrics is a pure derivation from (outcomes, plans, classifications); no mutable counter store

**Date:** 2026-05-09T22:31:30.815Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/verification/metrics.ts, extensions/vscode/src/architect-v2/verification/types.ts  

## Context

Cards (Slice 5) and the orchestrator both want completion counters, and v1 maintained mutable counter state at multiple sites that drifted. Without a single derivation function, replaying a pass for diagnosis produces different numbers than the original.

**Constraints:**
- computeMetrics is pure: same input -> same output (no Date.now, no random, no I/O)
- Every metric field is derivable from canonical arrays (outcomes, plans, classifications); no parallel mutable store
- STATUS_RANK ordering is the single source of truth for finalStatus aggregation
- Metric counters are non-negative integers

## Decision

computeMetrics(input) is a pure function that derives CompletionMetrics from (outcomes, capabilityPlans, verificationPlans, classifications, priorRepairAttemptsByKind, enrichmentTasksDrained). All counters are computed by scanning the canonical event/plan arrays — no parallel mutable counter store. finalStatus is the worst-case classification rank across the pass (mutation_failed > failed_verification > blocked > repair_recommended > completed_no_verification_needed > completed). enrichmentTasksDrained is supplied by the orchestrator (it owns the queue), but every other field is locally derivable.

### Alternatives Considered

- **Counters as mutable fields incremented at side-effect sites** — Rejected: double-counting bugs are the v1 metrics failure mode; mutable counters drift from the source of truth
- **Compute metrics inside the orchestrator only** — Rejected: couples cards (Slice 5) to orchestrator internals; cards should consume a typed result instead
- **Persist metrics to disk per pass** — Rejected: premature; cards consume in-memory; persistence can be added without changing the derivation function

## Consequences

- Cards (Slice 5) render counters by calling computeMetrics; no parallel state to keep in sync
- Replaying a pass's outcomes always produces identical metrics (testable, deterministic)
- Adding a new metric field is a pure additive change to computeMetrics
- finalStatus aggregation is consistent across all consumers (single STATUS_RANK table)

**Risks accepted:**
- enrichmentTasksDrained must be supplied externally (orchestrator owns the drain loop); slight asymmetry vs other fields
- Re-deriving on every render has small CPU cost (acceptable: O(n) over a single pass's outcomes)

## Guard Rails

> ⚠️ computeMetrics MUST NOT read from disk, network, or clocks

> ⚠️ STATUS_RANK MUST be updated in the same commit as any new CompletionStatus kind

> ⚠️ New metric fields MUST be derivable from existing inputs OR added as explicit input parameters

> ⚠️ TaskState additions for metrics MUST be additive widening only (ADR-151 preserved)
