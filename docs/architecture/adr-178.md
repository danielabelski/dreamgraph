# ADR-178: Architect-v2 host wiring is a single createArchitectHost factory

**Date:** 2026-05-10T16:18:25.071Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/host/index.ts, extensions/vscode/src/architect-v2/index.ts, extensions/vscode/src/architect-v2/orchestrator/loop.ts, extensions/vscode/src/architect-v2/orchestrator/ports.ts, extensions/vscode/src/architect-v2/context/builder.ts  

## Context

8A.1\u20138A.4 produced the orchestrator loop, composer, builder, fallback provider, memory adapter, and DreamGraph reader+recorder adapter. None of them are wired together. The v10.0.0 atomic cutover commit needs to replace the v1 Architect entry point in extension.ts with a single call against v2; without a host wiring module the cutover diff would have to know every port and adapter, defeating ADR-140's parallel-folder isolation. Additionally the builder's effectiveWindow() still returned a hard-coded 16k value; the provider's actual model window must thread through every pass.

**Constraints:**
- createArchitectHost MUST resolve the model window via resolveDefaultModel exactly once per host instance; per-pass model resolution is forbidden (it would re-list models on every pass).
- Every port the factory cannot construct because a dependency is missing MUST default to its Null implementation; the factory MUST NOT throw merely because optional wiring is absent.
- When mcpClient is supplied, the same DreamGraphRecorderAdapter instance MUST satisfy BOTH the ProjectGraphRecorder and ContextDiscoveryRecorder ports (ADR-177's split is at the type level only).
- host/ MUST NOT import from extension.ts, vscode, fs, http, or any v1 path — it composes ports from architect-v2 modules only.
- windowTokensOverride exists only for intentional degradation (small-context dry runs, tests). Production callers leave it unset.

## Decision

A new architect-v2/host/ module exports `createArchitectHost(options)` returning `{ providerProfile, windowTokens, ports, runPass }`. The factory: (1) calls resolveDefaultModel(providerId) ONCE and caches model.contextWindow as the authoritative window for every subsequent pass; (2) substitutes Null implementations for any unwired port (MemoryPort -> NullMemoryPort when no workspaceState; ProjectGraphReader/Recorder -> Null* when no McpClient; FallbackSignalProvider -> NullFallbackSignalProvider when none supplied) so sparse-mode is the default rather than a special case; (3) when an McpClient is wired, BOTH the ProjectGraphRecorder slot and the ContextDiscoveryRecorder slot get the same DreamGraphRecorderAdapter instance \u2014 ADR-177's two-port split is preserved at the type level while sharing one transport at runtime; (4) returns a `runPass(taskState, userIntent)` closure that threads the resolved windowTokens through every RunPassInput. extension.ts is unchanged today; the v10.0.0 cutover commit replaces the v1 entry call with `host.runPass(...)`. All other modules untouched.

### Alternatives Considered

- **Wire ports inline in extension.ts.** — Rejected: Extension.ts would have to know every architect-v2 port and adapter; the cutover commit becomes a sprawling diff and any future port addition forces extension.ts churn.
- **Make every port mandatory.** — Rejected: Defeats sparse-mode (ADR-173). The host has to keep working when the workspace has no MCP server, no graph, and no fallback provider — day-1 install.
- **Resolve the model window inside the builder on every pass.** — Rejected: Resolving requires async listModels(); doing it per-pass adds a network call to every prompt. Resolve once at host construction; thread the number through every pass.
- **Bundle ProjectGraphRecorder and ContextDiscoveryRecorder into one constructor argument.** — Rejected: ADR-177 keeps them as separate ports for narrow capability. The host happens to bind both to the same DreamGraph adapter instance, but the orchestrator and the assembler still see two separate port surfaces.

## Consequences

- The v10.0.0 cutover commit's diff in extension.ts is a one-line swap: from the v1 entry point to `await createArchitectHost({...}).runPass(...)`.
- Future port additions only touch host/index.ts and the calling site, not extension.ts.
- Sparse-mode is the *default* operating mode of the host — omit the McpClient and the orchestrator still produces complete passes against fallback signals.
- Provider window changes (new flagship model, lock bump) flow through resolveDefaultModel automatically without touching any builder/composer code.

**Risks accepted:**
- Adapter wiring drift: a new port added later may be forgotten in createArchitectHost. Mitigation: OrchestratorPorts is the canonical aggregate; TypeScript fails the build if a slot is missing.
- windowTokensOverride misused in production. Mitigation: documented as test/degradation-only; default path always resolves from the provider profile.
- Same adapter satisfying two ports could mask test failures (one port behaves but the other does not). Mitigation: the two recorder ports have different method shapes; the type system enforces both.

## Guard Rails

> ⚠️ Test (8B): createArchitectHost({ providerId, executor: stubExecutor }) returns a working host that can run a pass producing a non-empty PassResult with sections.length === 0 and unmetRequirements.length === manifest.requirements.length.

> ⚠️ Test (8B): host.windowTokens === resolveDefaultModel(providerId).model.contextWindow when no override given.

> ⚠️ Test (8B): host wired with an InMemoryKeyValueStore + InMemoryMcpClient survives load/save round-trips (saveTaskState then loadTaskState returns deep-equal state).

> ⚠️ Build-time check (Slice 8B): grep that fails if host/index.ts imports from /^(vscode|fs|node:|http|mcp_)/ or from any v1 path.
