# ADR-231: Architect CLI rich TUI renderer uses Ink after dependency-free log-mode foundation

**Date:** 2026-06-07T01:09:32.434Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/cli/commands/architect.ts, src/cli/utils/architect-client.ts, tests/architect-cli.test.ts, plans/architect-cli.md, plans/architect-cli.implementation-log.md, architect_cli_terminal_shell, dg architect  

## Context

Architect CLI needs a durable terminal UI direction that supports pane-based, keyboard-first Architect workflows without creating a second runtime authority, provider envelope parser, or direct filesystem mutation path. The current implementation ships a dependency-free log-mode shell, but future rich interaction needs an ADR-backed renderer choice before adding durable dependencies.

**Constraints:**
- Architect CLI must remain a thin daemon/MCP client; daemon-owned runtime identity, plan state, tool execution, provenance, and governed mutations stay authoritative.
- The renderer must stay terminal-native and scriptable, with JSON/non-interactive command behavior preserved separately from presentation state.
- The implementation should align with the existing TypeScript/Node CLI codebase and avoid adding a second language runtime for presentation.
- Terminal layout, folds, focus, scroll, and filters are local presentation state only and must not become repository facts or plan authority.
- The renderer must consume normalized daemon events/results rather than parsing provider-native envelopes or raw terminal output as truth.
- Unused dependencies should not be shipped before the rich renderer slice imports and tests them.

## Decision

Select Ink as the future rich interactive TUI renderer for Architect CLI while keeping the current shipped `dg architect tui` implementation as dependency-free log mode until the dedicated renderer slice adds Ink and focused terminal layout tests.

### Alternatives Considered

- **Blessed or neo-blessed** — Rejected: Good for terminal dashboards, but the imperative widget/state model is easier to drift from daemon-owned state, and maintenance risk is higher for a new product-level surface.
- **Bubble Tea** — Rejected: Technically strong, but it introduces a Go runtime boundary for a TypeScript/Node product and complicates packaging, testing, and daemon-client sharing.
- **Textual** — Rejected: Technically strong, but it introduces a Python runtime boundary and a separate UI architecture that would not reuse existing TypeScript CLI contracts.
- **Raw ANSI-only custom pane renderer** — Rejected: Keeps dependencies small but pushes DreamGraph into maintaining a bespoke focus/layout/scroll/input renderer, increasing complexity without improving daemon authority.
- **Reuse browser/xterm rendering** — Rejected: Blurs ADR-222 terminal convenience boundaries and would make the terminal feel like a browser payload projection rather than a terminal-native client.

## Consequences

- Architect CLI keeps its current dependency-free log-mode TUI for the implemented release while preserving a clear upgrade path to a rich keyboard pane UI.
- Future rich renderer work can add Ink deliberately with component tests, narrow-terminal snapshots, no-color handling, heartbeat suppression, and daemon-event fixtures.
- The CLI remains in the existing TypeScript/Node product and can reuse daemon client contracts without language/runtime bridge overhead.
- Terminal presentation remains separate from daemon authority, plan state, and evidence capture.

**Risks accepted:**
- Ink adds React-family dependencies when the rich renderer slice lands, increasing package size and requiring focused terminal rendering tests.
- Ink may need custom handling for large scrollback, complex tables, and high-volume event streams.
- The dependency-free log-mode shell is less ergonomic than the eventual pane UI until the rich renderer slice is implemented.

## Guard Rails

> ⚠️ Do not add Ink or React dependencies to the shipped package until source code imports them and renderer tests cover the behavior.

> ⚠️ Do not move Architect runtime identity, plan lifecycle, task control, or tool execution authority into Ink component state.

> ⚠️ Do not parse provider-native envelopes or raw CLI output in the TUI renderer; consume daemon-normalized contracts only.

> ⚠️ Do not make terminal output repository evidence unless a governed DreamGraph evidence/action path explicitly promotes it.

> ⚠️ Preserve non-interactive `dg architect` subcommands and JSON/JSON-events output as separate automation contracts from the interactive TUI.
