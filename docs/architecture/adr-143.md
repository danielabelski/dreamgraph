# ADR-143: Cards are split by responsibility: DreamGraph persists task state, webview owns UI state, cards are views not entities

**Date:** 2026-05-09T19:57:08.801Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/cards/, extensions/vscode/src/architect-v2/webview/, data/, plans/ARCHITECT_V2_SLICE1_INVENTORY.md  

## Context

v1 Architect mixes card responsibilities: the webview parses LLM JSON envelopes itself (third copy of extraction logic), some task state is implicit in chat history with no separate record, and cognitive cycles cannot reason over past task outcomes because they are not persisted as graph entities. The team needs a clean split that preserves graph-grounded reasoning while letting the UI evolve freely.

**Constraints:**
- Task history must survive extension reload, workspace reload, and multi-session work — it is durable evidence.
- UI presentation must evolve freely without migrating persisted data.
- Cognitive cycles (dreams, tensions, narrative) must be able to reason over past task outcomes.
- Webview must not become a parallel parsing surface for LLM envelopes — today's three-extractor problem must not recur.

## Decision

Cards are split by responsibility. DreamGraph persists task-state records: decisions taken, blockers encountered, verification evidence, graph-linked context summaries, autonomy pass outcomes, provider+model used, and tool-call results that have lasting value. The VS Code webview owns rendered card UI state: layout, expand/collapse, streaming progress, transient presentation, animation timing, and per-instance preferences. Cards are views over persisted task records, not graph entities themselves. The webview consumes typed events emitted by the orchestrator and never re-parses LLM envelopes directly.

### Alternatives Considered

- **Cards as full graph entities** — Rejected: Couples graph schema to UI presentation churn; every webview redesign would mutate persisted graph data, and the graph would carry rendering noise (collapse states, scroll positions) that has no semantic value.
- **Cards owned entirely by webview** — Rejected: Loses durable task history; reload, multi-session continuity, and graph-grounded reasoning over past decisions would all be impossible because the webview is ephemeral and unreachable from cognitive cycles.
- **Mirror everything to both stores** — Rejected: Doubles persistence cost and creates synchronization bugs; every UI tweak risks corrupting graph state and every graph update risks mis-rendering.

## Consequences

- Task history is queryable via DreamGraph for audit, narrative, and dream-cycle reasoning.
- Webview redesign is a presentation-only change with zero persistence migration.
- Single canonical envelope extractor in architect-v2/cards/ — the three-parallel-extractors problem from v1 cannot recur because the webview consumes typed events instead of raw text.
- Cards display correctly across all providers, all streaming states, and all partial-response edge cases because rendering reads from a single typed source.

**Risks accepted:**
- Graph schema must accommodate task-state records (new entity type or extension of existing); requires careful design.
- Typed event protocol between orchestrator and webview becomes a stable contract that must be versioned.
- Initial implementation cost is higher than 'webview parses everything' but pays back in reliability and graph reasoning.

## Guard Rails

> ⚠️ Do not parse LLM envelopes inside the webview — it consumes only typed events from the orchestrator.

> ⚠️ Do not store UI presentation state (collapse, scroll, animation) in DreamGraph.

> ⚠️ Do not store durable task evidence (decisions, blockers, verification, provider, model) only in the webview.

> ⚠️ Do not introduce a second envelope extractor anywhere in architect-v2/; the canonical extractor lives in architect-v2/cards/.

> ⚠️ Do not let webview state and graph task records drift — graph is authoritative for what happened, webview is authoritative only for how it currently looks.
