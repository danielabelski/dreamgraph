# ADR-139: DreamGraph v9.0.0 is the released baseline and SDK roadmap M0–M6 is complete, tested, verified, documented, committed, and tagged

**Date:** 2026-05-09T03:37:49.079Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** ADR-131, ADR-132, ADR-135, ADR-137, ADR-138, RELEASE_NOTES_v9.0.0.md, package.json, packages/sdk/package.json, packages/host/package.json, docs/sdk, docs/architecture.md, guide/02-installation.md, tests/sdk, examples/hello-events  

## Context

The canonical DreamGraph graph currently contains plugin-host ADRs up through M3 normalization, but it does not yet explicitly record that DreamGraph v9.0.0 is the released baseline where the SDK roadmap from M0 through M6 is complete and no longer merely planned. Repo and git evidence now show a v9.0.0 tag, release commits, package versions at 9.0.0 for root/sdk/host, release notes stating 'Plugin SDK milestones M0 → M6 (complete)', docs updated to the v9.0.0 baseline, and passing tests covering M4 plugin contributions, M5 outbound webhook/core behavior, M6 UI/closure seams, plugin lifecycle behavior, and hello-events end-to-end validation. Without recording this in the canonical graph, future reasoning may continue to treat late-stage SDK milestones as provisional or infer stale roadmap status.

**Constraints:**
- The graph record must distinguish verified released baseline status from earlier milestone ADRs that described only subsets such as M3 plugin runtime.
- M5 outbound webhooks were intentionally delivered as core platform behavior rather than plugin-owned runtime capability and that scope boundary must remain preserved.
- M6 records extensibility seams and host/UI integration contracts without implying a plugin marketplace, sandbox, or signed-distribution model.
- The release claim must be grounded in repo evidence: git tag/commits, package versions, release notes, docs, and passing tests.
- Earlier ADRs (including ADR-131, ADR-132, ADR-135, ADR-137, ADR-138) remain historically valid and should be interpreted as stepping stones to this released baseline, not contradictions.

## Decision

Record DreamGraph v9.0.0 as the canonical released baseline in which the SDK roadmap M0 through M6 is complete, tested, verified, documented, committed, and tagged. Treat the SDK/host capability family as active platform surface rather than roadmap intent: M0 manifest and host loader foundation, M1 dg plugin operator CLI, M2 telemetry/observability contracts, M3 trusted in-process plugin runtime and inventory, M3.5 hot reload and richer introspection, M4 plugin-contributed tools/resources/prompts, M5 outbound webhooks delivered as core-first platform capability interoperating with SDK surfaces, and M6 UI/closure/extensibility seams. Future graph reasoning should use v9.0.0 as the stable baseline unless superseded by a later release ADR.

### Alternatives Considered

- **Leave v9.0.0 release status implicit in release notes and source only** — Rejected: That would force future sessions to re-verify release evidence from files and git rather than relying on canonical graph memory.
- **Record only that roadmap work is 'mostly complete' without asserting released baseline status** — Rejected: That would understate the verified evidence and preserve stale ambiguity about whether M4-M6 are still roadmap items.
- **Model M5 and M6 as plugin-runtime-only milestones** — Rejected: That would conflict with the implemented architecture where webhooks are core-first and M6 exposes extensibility seams without implying a broader marketplace/runtime model.

## Consequences

- Future graph queries can answer that DreamGraph v9.0.0 is the stable release baseline for SDK/host functionality without re-reading repo evidence.
- Roadmap ambiguity is reduced: M0-M6 should be treated as completed/released history rather than active planned work.
- Plugin/runtime, webhook, and UI seam discussions can anchor to a single release-baseline ADR that supersedes planning-era assumptions.
- Later releases can explicitly supersede this baseline with narrower change-focused ADRs instead of restating completion history.

**Risks accepted:**
- Some existing feature/workflow nodes may still retain older planning-era wording until separately normalized.
- If later patch releases refine contract details, this baseline ADR may need supersession or targeted clarification.

## Guard Rails

> ⚠️ Do not describe SDK milestones M0-M6 as pending roadmap work after v9.0.0 unless a later ADR explicitly reopens scope.

> ⚠️ Do not reinterpret M5 as plugin-owned webhook runtime; preserve the core-first webhook boundary.

> ⚠️ Do not infer sandboxing, signing, or marketplace guarantees from this release baseline unless separately recorded.

> ⚠️ Use v9.0.0 as the authoritative baseline for SDK/host/docs/tests until superseded by a later release ADR.
