# ADR-148: Single 'openai' provider; ModelCapabilities.api selects Chat Completions vs Responses API per model

**Date:** 2026-05-09T20:48:43.660Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/providers/openai.ts, extensions/vscode/src/architect-v2/providers/profile.ts, ADR-147  

## Context

v1 ships two parallel OpenAI code paths \u2014 standard Chat Completions in `architect-llm.ts` and Responses API in `openai-responses-adapter.ts`. Inventory flags this as a HIGH-MEDIUM duplication smell. v2 must support both APIs (because gpt-5.5 requires Responses API while older models still use Chat Completions) without reproducing the dual-path problem.

**Constraints:**
- v1's two parallel OpenAI paths (architect-llm.ts standard route + openai-responses-adapter.ts) are a HIGH-MEDIUM smell in inventory §2 row 6; v2 must not reproduce them at the provider-id level.
- Users select a model, not an API; the UX must match.
- OpenAI's roster includes both Chat Completions models and Responses-API-only models simultaneously, so a single-API-per-provider model is incorrect.
- The dispatch decision must be declarative on the model descriptor, not buried inside adapter code.

## Decision

Architect v2 exposes ONE `openai` provider entry. Each model's `ModelCapabilities.api` field is the discriminator that selects between OpenAI Chat Completions and OpenAI Responses API at request time. Slice 2 wires gpt-5.5 with `api: 'openai-responses'` and gpt-5.4 with `api: 'openai-chat-completions'`. The orchestrator never sees an 'OpenAI mode' selector; users pick a model, and the model's metadata routes the request.

### Alternatives Considered

- **Two distinct providers: 'openai-chat' and 'openai-responses'** — Rejected: Splits the OpenAI surface in the settings UI and forces users to think about which API a model uses; this is exactly the cognitive leak ADR-148 exists to remove. It also recreates the v1 two-paths smell at a higher level.
- **Hardcode an api branch inside one OpenAI adapter implementation (no capability flag)** — Rejected: Pushes the provider-specific switch one level deeper instead of removing it; the orchestrator would still need to know which OpenAI 'mode' it was talking to in order to handle reasoning round-trip semantics correctly.
- **Auto-detect API per model from id naming conventions ('gpt-5*' → responses)** — Rejected: Naming conventions are not a contract; OpenAI has changed model id conventions before and may again. A declarative capability flag on the descriptor is robust to future renames.

## Consequences

- Settings UI shows a unified 'OpenAI' provider with all models in one list.
- Adding a new OpenAI model (e.g. a future Responses-API-only release) is one entry in `OPENAI_MODELS` with the correct `api` flag; no code branches change.
- The v1 inventory §2 row 6 'Two OpenAI paths' smell is structurally extinct in v2.
- Per-model behavior (reasoning round-trip, encrypted_content for Responses) is encapsulated inside the OpenAI adapter implementation, gated on `model.capabilities.api`.

**Risks accepted:**
- The OpenAI adapter implementation must contain a clean per-`api` dispatch internally; if it grows undisciplined it will become a smaller version of the v1 ArchitectLlm.
- If OpenAI introduces a third API surface, the `ModelApi` enum must be widened and the adapter must add a third internal branch.

## Guard Rails

> ⚠️ Do not introduce a second OpenAI-family entry in the registry (e.g. 'openai-responses', 'openai-classic'); the registry has exactly one `openai` provider.

> ⚠️ Do not branch on model id strings to choose the API; branch on `model.capabilities.api`.

> ⚠️ Do not allow an OpenAI model descriptor without a populated `capabilities.api` field.

> ⚠️ Do not hardcode Responses-API-specific shapes (encrypted_content, output array) outside the OpenAI adapter.
