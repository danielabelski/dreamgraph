# ADR-152: Autonomy modes preserved by name (cautious, conscientious, eager, autonomous); semantics rebuilt as a MODE_PROFILES data table

**Date:** 2026-05-09T21:18:40.357Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/autonomy/modes.ts, extensions/vscode/src/architect-v2/autonomy/decision.ts, ADR-151  

## Context

v1 autonomy modes are defined by per-mode code branches inside `chooseActionForMode` and `shouldContinueAfterPass`. The behavioral difference between modes is invisible without reading both functions in parallel. The user directive at Slice 3 kickoff was to keep the v1 setting names but rebuild the semantics around explicit knobs.

**Constraints:**
- v1 mode names must remain the user-facing labels (Slice 3 carry-over).
- Adding a fifth mode in the future should be one row in the table plus widening the `AutonomyMode` union, NOT a refactor.
- Tuning thresholds to telemetry must not require code changes outside `modes.ts`.
- All four modes must remain meaningfully distinct — each row's knob values differ from every other row in at least three of the five columns.

## Decision

Architect v2 keeps the four v1 mode names verbatim (`cautious`, `conscientious`, `eager`, `autonomous`) as the user-facing setting. Mode SEMANTICS are rebuilt from scratch as a `MODE_PROFILES` data table whose rows declare exactly five knobs: `defaultPassBudget`, `defaultTimeBudgetMs`, `confidenceThreshold`, `blockerTolerance`, `verificationStrictness`. No code anywhere in v2 branches on the mode enum directly \u2014 every consumer reads a knob value off `getModeProfile(mode)`. Initial calibration: cautious=(3 passes, 2 min, 0.95, 0, strict); conscientious=(8, 5 min, 0.85, 0, strict); eager=(20, 10 min, 0.70, 1, normal); autonomous=(50, 30 min, 0.55, 2, normal).

### Alternatives Considered

- **Rename the modes too** — Rejected: User directive at Slice 3 kickoff was explicit: keep the same UX labels with completely new behavior. Renaming would force users to relearn settings without delivering UX value.
- **Keep v1's per-mode rule branches but move them into a single function** — Rejected: Hides the same complexity in one location. Modes-as-data is structurally simpler and makes the four-way comparison legible at a glance.
- **Drop modes entirely and expose individual knobs** — Rejected: Violates the carry-over directive. Mode names ARE part of the v1 settings the user explicitly told us to preserve.

## Consequences

- Settings UI shows the same four labels users already know.
- Behavior differences between modes are visible in one table, not scattered across switch statements.
- Threshold tuning is a single-file edit (with a superseding ADR for the values).
- Mode-comparison diagrams and docs auto-derive from `MODE_PROFILES`.

**Risks accepted:**
- Initial threshold calibration is a guess; real-world telemetry may show, e.g., that `eager`'s 0.70 threshold is too permissive. Mitigation: thresholds are one-line edits gated by a superseding ADR.
- Wall-clock budget defaults assume reasonable provider latency; very slow providers may exhaust the time budget before the pass budget on `cautious` mode. Mitigation: both budgets are caller-overrideable.
- Reducing every mode difference to five knobs may not capture future requirements (e.g. per-mode tool allowlists). Widening the row schema is the resolution path.

## Guard Rails

> ⚠️ Do not add a `switch (mode)` statement anywhere in `architect-v2/`; read `MODE_PROFILES[mode]` instead.

> ⚠️ Do not change a `MODE_PROFILES` row value without a superseding ADR — the calibration is part of the contract.

> ⚠️ Do not introduce a fifth mode without widening `AutonomyMode` AND adding the matching `MODE_PROFILES` row in the same change.

> ⚠️ Do not use the v1 `chooseActionForMode` or `shouldContinueAfterPass` algorithms; the `MODE_PROFILES` knobs are the only mode-driven inputs.
