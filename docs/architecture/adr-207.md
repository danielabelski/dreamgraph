# ADR-207: Defend graph purity by separating durable plans from adaptive operational graph cognition

**Date:** 2026-05-27T19:42:29.235Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** plans/STANDALONE_ARCHITECT_MIGRATION_PLAN.md, planning:start_plan, planning:resume_plan, planning:get_plan_state, planning:list_slices, planning:next_slice, planning:append_plan, planning:review_gate, planning:update_slice_status, planning:sync_plan_graph, planning:sanitize_plan, planning:archive_plan, planning:get_resume_packet, Graph RAG, Standalone Architect, DreamGraph  

## Context

Standalone Architect plans and implementation slices need permanent historical preservation, but completed workflow/task cognition must not remain indefinitely active in the DreamGraph. If every completed task, slice, checkpoint, and execution instruction stayed in the active graph forever, retrieval and reasoning would accumulate stale context and the underlying LLM would drown in obsolete operational detail instead of seeing current project reality.

**Constraints:**
- Markdown plans under plans/ are durable project artifacts and must remain preserved after completion.
- Per-plan implementation logs are mandatory for auditability, user visibility, and crash/power-outage recovery.
- The DreamGraph prioritizes active project understanding, durable operational state, accepted architecture, verified capabilities, and current implementation reality.
- Temporary execution workflow structures are useful during active implementation but become harmful when they continue to participate in active cognition after stabilization.
- Historical evidence must remain available through markdown plans, implementation logs, ADR history, provenance, and archived evidence even when temporary graph workflow entities fade.
- Graph RAG and Architect context assembly must avoid overloading the LLM with stale completed-task context.

## Decision

Plans remain as permanent markdown-backed historical artifacts, while graph workflow cognition is adaptive and temporary. During active work, plans may be operationalized into graph workflow entities such as plan nodes, slice nodes, gates, continuation state, checkpoints, candidate futures, and execution entities. As work completes and stabilizes, those temporary structures must crystallize into durable project knowledge by creating, mutating, enriching, superseding, merging into, or removing durable entities such as Feature, DataModel, Workflow, API, Capability, Tool, UIRegistryElement, ADR, and related project-state entities. Completed implementation instructions should not remain indefinitely active as future execution cognition.

### Alternatives Considered

- **Keep every plan, task, slice, checkpoint, and implementation step permanently active in the graph.** — Rejected: This preserves detail but pollutes operational cognition, increases stale retrieval, and risks drowning the LLM in obsolete execution context.
- **Remove completed plans and logs once graph entities are updated.** — Rejected: This destroys the permanent historical project record and undermines auditability, reasoning traceability, and crash/recovery continuity.
- **Store plans only in the graph and not in markdown.** — Rejected: This makes historical artifacts dependent on graph lifecycle policies and conflicts with DreamGraph markdown-backed planning practices.
- **Never create temporary workflow graph entities for plans.** — Rejected: This avoids graph cleanup but loses useful active coordination, review gates, continuation state, and graph-aware implementation support during execution.

## Consequences

- Plans and implementation logs remain permanently available under plans/ as historical evidence.
- The active graph remains focused on current durable project reality instead of completed execution instructions.
- Planning tools must distinguish temporary workflow state from durable project entities.
- planning:sync_plan_graph and planning:archive_plan must support crystallization and fading of completed workflow cognition.
- Graph RAG context quality should improve by avoiding retrieval of stale completed slices as if they were active work.
- Users retain visibility into implemented vs unimplemented plan parts through markdown logs even after workflow graph structures are archived or removed.

**Risks accepted:**
- Crystallization bugs could remove useful workflow context before durable entities are correctly updated.
- Over-aggressive graph cleanup could make resume behavior worse if implementation logs are incomplete.
- Under-aggressive cleanup could still allow stale execution cognition to pollute retrieval.
- Entity mapping from slices to durable graph concepts may require human review for ambiguous plans.

## Guard Rails

> ⚠️ Do not delete or discard markdown plans or their implementation logs after completion.

> ⚠️ Do not keep completed plan slices, checkpoints, or execution instructions indefinitely active in the graph once they have stabilized.

> ⚠️ Before fading temporary workflow entities, crystallize verified results into durable project entities or record why no durable graph change is appropriate.

> ⚠️ planning:archive_plan must preserve historical markdown artifacts and provenance while reducing active graph workflow noise.

> ⚠️ planning:get_resume_packet must prefer the live implementation log and current durable project state over stale completed workflow entities.

> ⚠️ Graph RAG and Architect context assembly should prioritize durable project entities and active plan state, not archived completed-task cognition.

> ⚠️ Any implementation that treats the graph as the sole historical store for plans violates this decision.
