# ADR-172: runPass is pure-shaped over OrchestratorPorts; no direct I/O

**Date:** 2026-05-09T22:54:59.723Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/orchestrator/loop.ts, extensions/vscode/src/architect-v2/orchestrator/ports.ts, extensions/vscode/src/architect-v2/orchestrator/types.ts  

## Context

The orchestrator pass loop is the hottest path in the Architect. If runPass performs I/O directly, every later sub-slice has to mock the runtime to test against it, and replacing any subsystem means editing the orchestrator. v1 fell into exactly this trap.

**Constraints:**
- No top-level imports in loop.ts other than architect-v2 sibling modules.
- Every async boundary in runPass is a port method call. No raw setTimeout, no Date.now (use ClockPort), no console.* (logging is a future port if needed).
- runPass returns a PassResult; it never throws for predictable failure modes — those become CompletionStatus values and BlockerCard / CompletionCard outputs.
- OrchestratorPorts is the only parameter shape that may grow; widening is allowed (additive ADR-151 style), removal/rename requires an amending ADR.

## Decision

runPass is a pure-shaped async function over an injected OrchestratorPorts bag. All effects (context build, prompt compose, provider call, tool execution, persistence, graph reads, graph recording, time) go through one of: ContextBuilderPort, PromptComposerPort, ExecutorPort, MemoryPort, ProjectGraphReader, ProjectGraphRecorder, ClockPort. The loop never imports vscode, fs, http, or mcp_* modules. Tests assemble runPass from in-memory fakes; production assembles from real adapters wired by the extension activate function (Slice 8A.5).

### Alternatives Considered

- **Allow runPass to import vscode/fs/http directly for 'small' I/O.** — Rejected: Every exception trains the next reader that exceptions are fine; tests then need real fakes for the 'small' I/O too.
- **Pass a single mega-port that bundles every effect.** — Rejected: Hides dependency surface; every consumer would import the union.
- **Use module-level singletons to avoid passing ports.** — Rejected: Same global-state failure mode v1 had; impossible to run two orchestrator instances with different providers in the same process.

## Consequences

- Sub-slices 8A.2–8A.5 can be implemented in any order — each delivers one port adapter runPass already calls.
- Unit testing runPass is trivial: assemble all ports as in-memory fakes and assert on PassResult.
- The Architect can be embedded in a non-VS Code host by swapping adapter implementations.
- Refactors of any single subsystem cannot break the orchestrator: the port contract is the firewall.

**Risks accepted:**
- A future contributor adds a 'small' direct import for convenience. Mitigation: build-time guard rail.
- Port count grows unbounded. Mitigation: each new port requires its own justification.
- Determinism leaks via Math.random for card ids. Mitigation: future ADR may introduce an IdGenerator port.

## Guard Rails

> ⚠️ Build-time check (Slice 8B): grep that fails if loop.ts imports anything matching /^(vscode|fs|node:|http|mcp_)/.

> ⚠️ Verification harness: a NullPorts fixture must drive at least one full pass to a terminal status without throwing.

> ⚠️ Each new port method requires a one-line justification in the sub-slice plan that introduces it.
