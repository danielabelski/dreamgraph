# ADR-171: Architect orchestrator binds to ProjectGraphReader/Recorder, not DreamGraph

**Date:** 2026-05-09T22:50:06.977Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/orchestrator/ports.ts, extensions/vscode/src/architect-v2/orchestrator/project-graph.ts, extensions/vscode/src/architect-v2/orchestrator/loop.ts, extensions/vscode/src/architect-v2/context/ (8A.3), extensions/vscode/src/architect-v2/memory/ (8A.4), plans/ARCHITECT_V2_SLICE8_CUTOVER.md  

## Context

The Architect v2 orchestrator (Slice 8A.1) is the seam through which every later sub-slice will fetch graph context (8A.3) and persist cognition (8A.4). If the orchestrator or ContextBuilder imports mcp_dreamgraph_* directly, DreamGraph's MCP shape becomes the de-facto required ontology for the Architect. That violates the slice's "graph-native, not DreamGraph-native" framing: sparse/no-graph projects, alternative graph backends (LSP-derived, Sourcegraph, custom AST graphs), and future cognition stores would all be second-class. The orchestrator must depend only on a project-graph abstraction; DreamGraph is one adapter behind it.

**Constraints:**
- Strict isolation (ADR-140) extended: no architect-v2 module outside an explicit adapters/ folder may import mcp_dreamgraph_*.
- Ports must be narrow enough that an LSP-only or filesystem-only adapter is implementable without stubs returning fake graph nodes.
- Reader returns an opaque ProjectSubgraph; the orchestrator does not introspect its internals beyond what ContextBuilder uses to assemble a ContextEnvelope.
- Recorder methods are async and idempotent on identity (re-recording the same card id is a no-op or upsert; never duplicates).
- Sparse/no-graph mode is a first-class operating mode, not an error path.

## Decision

Define two narrow ports in 8A.1 — ProjectGraphReader (richness signal, subgraph retrieval, neighbors) and ProjectGraphRecorder (record cards, decisions, outcomes, continuations) — and add them to OrchestratorPorts. The orchestrator, ContextBuilder, PromptComposer, and Memory layers consume only these ports. The DreamGraph adapter is implemented in 8A.3 behind the Reader port and in 8A.4 behind the Recorder port; nothing in architect-v2/orchestrator/, architect-v2/context/, architect-v2/prompts/, or architect-v2/memory/ (outside an explicit */adapters/dreamgraph/ subfolder) may import mcp_dreamgraph_*. Sparse/no-graph projects receive top-tier behavior via filesystem/runtime/LSP context reconstruction; resulting cognition is still recorded through the Recorder when one is wired.

### Alternatives Considered

- **Continue with no abstraction; ContextBuilder calls mcp_dreamgraph_* directly.** — Rejected: Bakes DreamGraph's schema into the Architect; no path to alternative backends; sparse projects degrade to broken instead of degraded-but-functional.
- **Single ProjectGraphReader port (read-only); persist via DreamGraph directly from Memory.** — Rejected: Asymmetric — recording is where ontology coupling is strongest (cards, ADRs, continuations all become DreamGraph entity types). Reader without Recorder leaks the schema on the write path.
- **Defer the abstraction until after 10.0 cutover; ship 8A.3 against mcp_dreamgraph_* and refactor later.** — Rejected: Slice 8A.3 is the exact place the leak crystallizes; refactoring after cutover means rewriting the Architect's hottest path under load.

## Consequences

- 8A.3 ships ContextBuilder + a DreamGraph Reader adapter side-by-side; the Reader interface, not the adapter, is what ContextBuilder depends on.
- 8A.4 ships Memory + a DreamGraph Recorder adapter; an in-memory Recorder is trivial for tests.
- The Architect can be lifted into a non-DreamGraph host (or run before DreamGraph has indexed anything) without changing orchestrator code.
- Density measurement (Slice 6) is fed by Reader.getRichnessSignal, not by direct dream://graph reads.
- Existing cognition stores keep working; they are written through the Recorder adapter.

**Risks accepted:**
- Port surface drifts smaller than ContextBuilder needs, forcing a leaky 'getRaw' escape hatch. Mitigation: 8A.3 may extend the port additively but each addition is justified in its slice plan.
- Recorder becomes a thin pass-through with little value over direct writes. Mitigation: Recorder owns identity normalization (card ids → graph node ids) which is real ontology work, not a wrapper.
- Performance: extra indirection on every context fetch. Mitigation: ports are async and the adapter can batch/cache freely; the orchestrator does not assume locality.

## Guard Rails

> ⚠️ Lint/CI rule (added in Slice 8B): grep for mcp_dreamgraph_ outside architect-v2/**/adapters/dreamgraph/** fails the build.

> ⚠️ ProjectGraphReader and ProjectGraphRecorder method signatures are frozen by this ADR; widening is allowed (additive ADR-151 style), narrowing requires an amending ADR.

> ⚠️ No port method returns a DreamGraph-specific type. ProjectGraphNode/Edge/Subgraph are defined in architect-v2 and intentionally narrower than DreamGraph's internal model.

> ⚠️ Sparse-mode behavior is verified by a test that runs the orchestrator with a NullProjectGraphReader (always returns 'absent' richness) and a NullProjectGraphRecorder (no-op writes) and still produces a useful pass.
