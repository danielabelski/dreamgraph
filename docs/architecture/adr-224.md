# ADR-224: Architect plugin tabs are declarative host-rendered contributions

**Date:** 2026-05-31T15:28:17.812Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** feature_plugin_sdk, feature_plugin_runtime, standalone-architect, packages/sdk/src/seams/architect.ts, src/plugins/architect-contributions.ts, src/architect/routes.ts  

## Context

Trusted DreamGraph plugins need to contribute first-class standalone Architect tabs without introducing executable browser plugin code or weakening the daemon-served browser boundary.

**Constraints:**
- Architect browser surfaces remain daemon projections under /api/architect/v1.
- The existing SDK ui:register seam is semantic metadata only and does not authorize executable browser UI.
- The first reference surface is an Action Checklist tab bound explicitly to a plan.
- Plugins remain trusted in-process host modules and browser clients must render validated JSON only.

## Decision

Add ctx.architect.tabs.register() for trusted host-side plugins to register declarative Architect tab descriptors. Descriptors declare identity, label, icon, renderer kind, plan connectivity, schemas, sidebar summary, and badges. The browser renders only host-supported renderer kinds; the initial closed renderer set contains checklist. Plugin JavaScript, arbitrary HTML, remote scripts, inline scripts, iframes, and direct DOM callbacks remain out of scope.

### Alternatives Considered

- **Load plugin browser modules or arbitrary HTML directly into Architect** — Rejected: This would create a new executable browser trust boundary without isolation, CSP, teardown, or supply-chain controls.
- **Reuse semantic ui:register metadata as executable UI permission** — Rejected: The existing seam intentionally carries metadata only and must not be broadened implicitly.

## Consequences

- Architect plugins can contribute first-class tabs through a stable declarative contract.
- Browser rendering remains host-owned and testable.
- Future executable plugin UI requires a separate reviewed ADR.

**Risks accepted:**
- The renderer contract may need additive expansion as new tab kinds are introduced.
- Route rendering complexity may grow if host-supported renderer kinds are not kept focused.

## Guard Rails

> ⚠️ Do not reinterpret ui:register metadata as permission to execute plugin code in the browser.

> ⚠️ Do not ship iframe, arbitrary-script, remote-script, inline-script, or direct DOM callback escape hatches as part of Architect plugin tabs.

> ⚠️ Do not let browser rendering logic invoke plugin code directly.

> ⚠️ Keep the initial renderer union closed to host-supported declarative kinds.
