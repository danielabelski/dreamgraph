# ADR-128: Tool naming must carry primary semantics so tool descriptions need not be injected into model context

**Date:** 2026-05-07T09:53:29.412Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** plans/DREAMGRAPH_SDK_ROADMAP.md  

## Context

Tool descriptions consume prompt budget and create dependency on out-of-band prose for basic tool use. In the SDK and extension tool surfaces, models should be able to infer a tool's purpose primarily from the tool name and parameter names/signatures. If a tool's behavior is not reasonably inferable from name(params) alone, that indicates poor naming or over-broad responsibility.

**Constraints:**
- Tool names must remain concise enough for provider tool schemas and logs.
- Parameter names must be semantically meaningful and disambiguate scope, target, and side effects.
- Existing tools may need compatibility shims or aliases to avoid breaking callers immediately.
- Some edge cases still require machine-readable schema constraints, but not explanatory prose for primary intent.
- Naming should work across providers and SDK surfaces without relying on provider-specific prompt stuffing.

## Decision

Adopt an ADR guard rail that tool interfaces are self-describing by name and parameters. Do not rely on injected natural-language tool descriptions as the primary mechanism for tool understanding. When designing or revising a tool, require that an informed reader can infer the main behavior from toolName(paramNames) alone. Treat failure of that test as a design smell that should trigger renaming, decomposition, or narrower parameterization before adding descriptive context.

### Alternatives Considered

- **Continue passing rich tool descriptions in prompt context** — Rejected: Consumes context budget, duplicates schema intent in prose, and hides weak naming behind prompt engineering.
- **Keep current names but add more examples/documentation in prompts** — Rejected: Improves one runtime path only and does not fix the underlying interface clarity problem.
- **Use opaque stable IDs for tools and depend entirely on external registry metadata** — Rejected: Maximizes indirection and makes ad hoc model reasoning and human inspection worse.

## Consequences

- Reduced prompt/context overhead for tool calling.
- Stronger pressure toward smaller, more precise tool interfaces.
- Easier cross-provider portability because the interface semantics live in the schema surface.
- Some existing tool names may be identified as needing rename or split work.
- Documentation remains useful for edge cases, constraints, and examples, but not for conveying the tool's basic purpose.

**Risks accepted:**
- Renaming tools can break existing callers if migration is not staged.
- Over-indexing on brevity may produce names that are concise but still ambiguous.
- A few legitimate complex tools may resist full semantic compression into name(params) alone.

## Guard Rails

> ⚠️ Before introducing a new tool, apply the self-describing test: can the primary behavior be inferred from toolName(paramNames) without extra prose?

> ⚠️ If not, prefer renaming the tool, renaming parameters, or splitting the tool into narrower operations before adding description text.

> ⚠️ Use descriptions for edge behavior, constraints, caveats, and examples—not as the only place the tool's main action is explained.

> ⚠️ Avoid umbrella tool names that conceal multiple unrelated behaviors behind generic parameters.

> ⚠️ When compatibility requires retaining a poor legacy name, add a clearly named alias and deprecate the ambiguous surface.
