# ADR-100: Architect Lens badge — visible when useful, silent otherwise

**Date:** 2026-05-03T10:27:16.772Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** extensions/vscode/src/prompts/architect-core.ts, extensions/vscode/prompts/architect_core.md, extensions/vscode/src/context-builder.ts, extensions/vscode/src/extension.ts  

## Context

The architect uses one generic prompt for every coding task. Role-specific prompts (Reviewer, Debugger, Refactorer, Performance, Security, Reliability) would let the architect pull task-appropriate evidence and follow task-appropriate query protocols, but announcing the role in prose ("I am now Security Architect") becomes gimmicky and erodes trust over time.

**Constraints:**
- Must not become performative theater
- Must not add friction to trivial tasks (rename variable, fix typo)
- Must reuse the existing intent detector — no parallel classification system
- Must remain explainable / debuggable when it does fire

## Decision

Implement role-specific prompts as "Architect Lenses." Surface the active lens via a subtle badge in the response header (e.g. "Architect Lens: Performance / Refactor / Reliability / Security"). Show the badge ONLY when the lens materially changes reasoning — different evidence pulled, different query protocol, different ADR set. Stay silent for trivial tasks. Lens selection driven by the same intent detector that drives _createContextPlan().

### Alternatives Considered

- **Always announce role in prose** — Rejected: Becomes gimmicky and erodes user trust over time.
- **Never expose role to user** — Rejected: Loses explainability and debuggability — users can't tell why an answer leans one way or another.
- **User-selected lens dropdown** — Rejected: Adds UI burden for what should be inferred from intent in 95% of cases.

## Consequences

- Users learn system behavior over time by observing which lens fires for which task type
- Trivial tasks remain frictionless
- Specialized tasks (security review, perf debugging) get task-appropriate evidence and protocols
- Lens badge gives a single audit point for explainability complaints

**Risks accepted:**
- Intent detector misfires would surface a confusing badge
- Boundary between trivial and material is judgment-dependent and may need tuning
- Multiple lenses could theoretically apply to one task — needs deterministic precedence

## Guard Rails

> ⚠️ Do NOT show the lens badge for trivial tasks

> ⚠️ Do NOT announce the lens in prose — badge only

> ⚠️ Lens selection MUST share the intent detector with _createContextPlan() — no parallel classifier

> ⚠️ Lens precedence rules MUST be deterministic and documented
