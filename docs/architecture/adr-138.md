# ADR-138: Normalize graph understanding of implemented M3 plugin capability surfaces and workflow

**Date:** 2026-05-08T22:19:00.572Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** ADR-137, packages/sdk/src/telemetry.ts, packages/sdk/src/reject-reasons.ts, packages/host/src/context.ts, packages/host/src/gates.ts, packages/host/src/loader.ts, packages/host/src/registry.ts, src/plugins/manager.ts, src/resources/register.ts, src/cli/commands/plugin.ts, examples/hello-events/plugin.json, examples/hello-events/index.js, examples/hello-events/README.md, tests/sdk/host-gates.test.ts, tests/sdk/host-loader.test.ts, README.md, docs/tools-reference.md  

## Context

The graph now has ADR-137 marking M3 plugin host runtime as active, but feature/workflow-level graph understanding still risks under-specifying the implemented seams. Source evidence shows the concrete implemented capability surfaces are broader and more precise than a single milestone ADR: stable host-owned plugin telemetry kinds in @dreamgraph/sdk, a typed PluginRejectReason taxonomy, a real PluginContext surface with an explicit deny-list posture, host discovery/load gating via allowInProcessPlugins and per-plugin trust, system://plugins as canonical inventory, dg plugin admin commands, and examples.hello-events as validation/reference plugin. Without an explicit normalization decision, future graph reasoning may keep treating these as scattered code details instead of one coherent implemented capability cluster and workflow.

**Constraints:**
- M3 is an in-process trusted-plugin runtime, not a sandbox; graph wording must preserve that boundary.
- system://plugins is the canonical operator-visible inventory and must remain the preferred read surface for loaded/discovered plugin state.
- Plugin telemetry event kinds and PluginRejectReason are stable SDK contracts and should not be modeled as experimental or daemon-private.
- PluginContext is an API boundary with an explicit deny-list posture; the graph must not infer unrestricted host authority from in-process execution.
- Plugin loading remains gated by host allowInProcessPlugins policy and/or explicit per-plugin trust overrides.
- examples.hello-events is a reference/smoke-test plugin and runtime validation artifact, not a production capability in itself.
- webhook.dead_letter remains outside M3 scope per prior decisions.

## Decision

Record that the implemented M3 plugin capability cluster comprises: (1) stable SDK plugin telemetry kinds plugin.loaded / plugin.unloaded / plugin.errored / plugin.handler.started / plugin.handler.completed / plugin.output.accepted / plugin.output.rejected; (2) typed PluginRejectReason taxonomy as the canonical rejection-reason contract shared by SDK and host gates; (3) PluginContext as the developer-facing runtime surface with explicit deny-list semantics and scoped identity/instance/logger/read APIs; (4) a host workflow of discover -> manifest/engine validate -> capability/effect gates -> trust/in-process load gate -> activate -> registry publish -> system://plugins exposure -> dg plugin administration; and (5) examples.hello-events as the reference validation plugin proving discovery/load/inspection behavior. Future graph enrichment should treat these as implemented linked surfaces of one active plugin-host feature family.

### Alternatives Considered

- **Leave plugin capability understanding implicit across code/docs and rely only on ADR-137 milestone state** — Rejected: That leaves the graph semantically shallow and forces future reasoning to rediscover concrete surfaces from source instead of using normalized graph knowledge.
- **Model M3 plugin runtime primarily as a sandbox/security feature** — Rejected: That would be inaccurate; the implemented boundary is trust-gated in-process loading with API-level deny-list semantics, not a full sandbox.

## Consequences

- Future graph queries can consistently answer what the active M3 plugin surfaces are without rereading code.
- Plugin discovery/load/rejection reasoning can anchor to a canonical workflow description rather than scattered implementation hints.
- SDK and daemon surfaces stay semantically linked: telemetry kinds, reject reasons, gates, registry, inventory resource, CLI, and example plugin.
- Later milestones such as worker isolation can supersede parts of this capability cluster without obscuring the M3 baseline.

**Risks accepted:**
- ADR-level normalization still does not physically create every desired feature/workflow node if generic upsert tools remain unavailable.
- Some legacy docs still contain planning-era wording and may need later cleanup to fully match the normalized graph view.

## Guard Rails

> ⚠️ Do not describe M3 PluginContext or host loading as a sandbox boundary; it is a trusted in-process API boundary.

> ⚠️ Do not model plugin telemetry kinds or PluginRejectReason as daemon-internal details; they are stable SDK contracts.

> ⚠️ Do not treat examples.hello-events as equivalent to a production plugin marketplace or signing model.

> ⚠️ Do not collapse system://plugins, dg plugin, and host gating into unrelated features; they are part of one operator-facing plugin runtime family.

> ⚠️ Do not pull webhook dead-letter semantics into M3 plugin workflow scope.
