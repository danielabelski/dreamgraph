# ADR-165: Slice 6 — Record-everything contract: every capability invocation writes back to the graph so it self-bootstraps over time

**Date:** 2026-05-09T22:14:54.265Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/capabilities/matrix.ts, extensions/vscode/src/architect-v2/capabilities/enrichment.ts, extensions/vscode/src/architect-v2/capabilities/selection.ts, Slice 7 verification harness (consumer)  

## Context

Without a record-everything contract, sparse-mode invocations leave no trace and the graph never grows. The architect would remain forever sparse on projects that never trigger an explicit scan, contradicting the user's 'evolve with time' directive.

**Constraints:**
- Enrichment is non-blocking; pass completes before enrichment runs
- Enrichment uses Slice-4 Intent literals (compile-time validated)
- EnrichmentTask carries capabilityId + reason for audit
- Orchestrator (post-cutover) decides budget; Slice 6 only declares the queue

## Decision

Every successful capability invocation, regardless of mode (graph-amplified, sparse-mode, or even gap), MUST emit a graph-write describing what it did. In sparse-mode this takes the form of an EnrichmentTask queued on TaskState.enrichmentQueue (Intent + capabilityId + reason='sparse_mode_used' | 'graph_only_gap'), executed by the orchestrator between passes when budget permits. In graph-amplified mode the graph-write is implicit (the graph-first intent itself records to the graph). The matrix declares enrichOnFallback per capability (e.g. mutate.file.create -> graph.scan; navigate.symbol -> graph.scan; mutate.file.edit -> api.modify; search.ui -> ui.register). Enrichment is opportunistic, not blocking.

### Alternatives Considered

- **Only graph-amplified mode writes to graph; sparse-mode is read-only** — Rejected: Sparse installs would never bootstrap the graph; the architect would never improve on a project; contradicts user directive to 'evolve with time through edges and dreams'
- **Manual scan_project on schedule, not driven by capability invocations** — Rejected: Decouples enrichment from actual usage; the graph grows in directions the architect doesn't actually use
- **Synchronous enrichment after each capability invocation** — Rejected: Blocks the pass on graph writes; defeats sparse-mode parity with generic agents

## Consequences

- A project worked on with the architect for a week is measurably more graph-rich than one worked on for a day
- Sparse installs converge on graph-amplified for the capabilities the user actually exercises
- Generic-agent equivalent has no analogue — this is a structural advantage that compounds with project tenure
- Slice 5 cards can show 'enrichment queued: graph.scan' as a pill

**Risks accepted:**
- Enrichment queue grows unbounded if orchestrator never drains — mitigated by Slice 7 verification + budget caps
- Misclassified enrichOnFallback wastes graph-write budget — mitigated by per-capability review against §8 of the plan

## Guard Rails

> ⚠️ Every capability that has a fallback path MUST declare an enrichOnFallback intent OR explicitly note 'no enrichment meaningful' in winRationale

> ⚠️ Enrichment MUST NOT block the originating pass

> ⚠️ EnrichmentTask reason MUST be one of 'sparse_mode_used' | 'graph_only_gap'

> ⚠️ Orchestrator MUST eventually drain the enrichment queue (Slice 7 verifies)
