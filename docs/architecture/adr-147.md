# ADR-147: Architect v2 providers are profile records in a registry; orchestrator depends only on the ProviderAdapter contract

**Date:** 2026-05-09T20:48:43.626Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/providers/profile.ts, extensions/vscode/src/architect-v2/providers/adapter.ts, extensions/vscode/src/architect-v2/providers/registry.ts, extensions/vscode/src/architect-v2/providers/openai.ts, extensions/vscode/src/architect-v2/providers/anthropic.ts, extensions/vscode/src/architect-v2/providers/lmstudio.ts, extensions/vscode/src/architect-v2/providers/ollama.ts, plans/ARCHITECT_V2_SLICE2_PROVIDERS.md  

## Context

Architect v1 routes provider-specific behavior through switch statements inside `ArchitectLlm`, hardcodes model capability flags, and parses tool-call envelopes in multiple places. Inventory \u00a71.4, \u00a72 row 6, and \u00a75 row \"Provider model-list rot\" identify this as a structural cause of the two-OpenAI-paths smell, the silent reasoning-effort header risk, and adapter divergence. v2 needs a uniform abstraction that the orchestrator and autonomy engine can depend on without ever knowing which provider is active.

**Constraints:**
- Architect v2 must remain provider-agnostic at the orchestrator layer; provider quirks may not leak past the adapter boundary.
- Adding or removing a provider must be a single registry change, not a switch-case surgery across multiple files.
- Tool-call reliability target (99.999999% per inventory §3) requires the canonical tool-call shape to be defined once and translated by adapters, not parsed in multiple places.
- Strict isolation from v1 — no `import` and no copy-paste of v1 provider code (locked at Slice 2 kickoff).

## Decision

Architect v2 models providers as `ProviderProfile` records in a registry rather than a class hierarchy. Each profile declares: its `id` (closed enum), `displayName`, `modelSource` ('static' or 'discovery'), `defaultModelId`, `listModels()`, and `createAdapter(model, config)`. Each model is a `ModelDescriptor` with declarative `ModelCapabilities` (api discriminator, streaming, toolCallShape, attachments, reasoning support, maxOutputTokens). The orchestrator depends only on the `ProviderAdapter` contract (`stream`, `callWithTools`) and the canonical request/response/event/error shapes \u2014 it never branches on provider id at the wire layer. Slice 2 ships the types + registry + stub adapters that throw `ProviderAdapterNotImplementedError`; real adapters land in later slices behind the v2 feature flag.

### Alternatives Considered

- **Keep v1's class-based ArchitectLlm shape and just rebuild internals** — Rejected: v1's switch-statement provider routing is the root cause of the two-OpenAI-paths smell and the silent reasoning-effort header mismatch risks documented in inventory §1.4 and §5; a per-provider record-based registry is what makes ADR-148 (one OpenAI provider, model-driven dispatch) implementable cleanly.
- **Use a third-party LLM router library (LangChain.js / Vercel AI SDK)** — Rejected: Adds a heavy runtime dependency, hides the provider quirks behind another abstraction we'd still have to debug, and conflicts with the rewrite principle of owning the wire layer end-to-end for token economy and tool-call reliability.
- **Defer the registry until after a working adapter exists** — Rejected: Slice 3+ work (autonomy, execution) needs a stable seam to depend on; without the registry contract, every later slice would re-invent its own adapter abstraction and we would re-create v1's tangled state.

## Consequences

- Future slices implement their own logic against the `ProviderAdapter` contract; they can be developed and tested with mock adapters before any provider is wired.
- Adding a fifth provider (e.g. xAI, Google) becomes a single new profile file plus one registry entry, not a refactor of `ArchitectLlm`.
- The two-OpenAI-paths smell from v1 inventory §2 row 6 is structurally precluded — model.capabilities.api is the single source of truth for wire format.
- Capability flags drive request shaping declaratively; the silent reasoning-effort header risk from inventory §5 cannot recur because unknown effort levels are caught by `ReasoningSupport.effortLevels` enforcement at the adapter boundary.

**Risks accepted:**
- The canonical `ChatRequest` / `StreamEvent` / `ToolCall` shapes must absorb every provider's quirks; a future provider with truly novel semantics may force a backwards-incompatible widening.
- Stub adapters are runtime-throwing; if a code path accidentally instantiates a stub during Slice 2 work it will fail at the call site (mitigated: feature flag remains off and stub adapters are easy to recognize in stack traces).
- Discovery-source providers (LM Studio, Ollama) ship Slice-2 placeholder lists; consumers that enumerate models must understand this is not yet the real list.

## Guard Rails

> ⚠️ Do not branch on `ProviderId` inside the orchestrator or autonomy engine — branch on `ModelCapabilities` fields.

> ⚠️ Do not introduce a provider-specific request type that bypasses `ChatRequest`; adapters translate from the canonical shape, not from a per-provider one.

> ⚠️ Do not parse provider-specific tool-call envelopes anywhere except the corresponding adapter; the rest of v2 sees only `ToolCall`.

> ⚠️ Do not throw provider-raw errors past the adapter boundary; every failure must be wrapped in `ProviderError` with a closed-enum `kind`.

> ⚠️ Do not ship a provider adapter without the corresponding `ModelCapabilities` flags being honored end-to-end (streaming, toolCallShape, reasoning, attachments).
