# ADR-230: Normalize LLM provider results and gate model parameters through capabilities

**Date:** 2026-06-05T19:42:12.518Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/openai-responses-adapter.ts, extensions/vscode/src/architect-llm.ts, src/cognitive/llm.ts, src/architect/native-tool-loop.ts, tests/llm.routing.test.ts, extensions/vscode/src/test/openai-responses-adapter.test.ts  

## Context

Responses API output shapes and model-specific parameter support can change independently of DreamGraph's engine and Architect workflows. Direct reads of provider response objects and scattered model heuristics make GPT-5.x migrations brittle, especially for temperature and Responses API parsing.

**Constraints:**
- DreamGraph must consume provider-normalized LLM results, not raw OpenAI Responses objects.
- GPT-5.5 OpenAI calls must treat temperature as unsupported and optional.
- Existing Chat Completions models such as gpt-5.4 must keep working without provider-id split.
- ADR-147 and ADR-148 already require ModelCapabilities-driven routing and request shaping.

## Decision

Keep provider raw response parsing inside the OpenAI adapter boundary. Expose normalized result data with text, finishReason, and usage. Centralize daemon-side model parameter support in getModelCapabilities so request builders consult capabilities before sending optional parameters such as temperature.

### Alternatives Considered

- **Continue extracting response.output/output_text at each DreamGraph call site** — Rejected: It leaks OpenAI Responses schema details into orchestration code and makes schema evolution a behavioral risk.
- **Preserve temperature as a required field for all OpenAI-compatible models** — Rejected: GPT-5.5 does not expose temperature and model support must be negotiated as a capability.
- **Infer GPT-5.x behavior from scattered regexes at each call site** — Rejected: Duplicated heuristics drift and contradict ADR-147/ADR-148 capability-driven provider design.

## Consequences

- DreamGraph call sites depend on normalized LLM output shape instead of Responses API internals.
- OpenAI request bodies omit temperature when the selected model capability does not support it.
- Future model upgrades update one capability table instead of several call sites.
- Determinism expectations remain documented as Normalizer/evidence/promotion behavior rather than a temperature guarantee.

**Risks accepted:**
- The daemon capability table still needs upkeep when providers publish new model behavior.
- OpenAI Responses tool-loop migration remains a separate compatibility concern if daemon native tool calls are routed to Responses-only models.

## Guard Rails

> ⚠️ Do not read OpenAI Responses output_text/output[]/status/incomplete_details outside the OpenAI adapter normalization boundary.

> ⚠️ Do not send temperature or other optional parameters without checking model capabilities.

> ⚠️ Do not add new GPT-5.x regex heuristics at call sites when a ModelCapabilities entry can express the behavior.

> ⚠️ Do not treat low temperature as DreamGraph's determinism contract; the Normalizer, evidence scoring, and promotion gates remain the deterministic control surface.
