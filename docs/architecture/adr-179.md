# ADR-179: Provider/model agnosticity: every user-facing fix is applied at provider-neutral seams

**Date:** 2026-05-10T20:20:28.281Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** architect-v2, architect-v2-cards-render, architect-v2-orchestrator-loop, architect-v2-host-chat-panel, architect-v2-providers-registry  

## Context

A defect that manifests under one provider/model can tempt a fix inside that provider's adapter. Such adapter-local fixes silently diverge user-facing behavior across providers, recur the moment another provider's model exhibits the same pattern, and violate ADR-148's no-branch-on-provider principle. Context: during the v10.0.0 Lattice cutover smoke test of architect-v2, the chat surface leaked raw tool-envelope JSON into a chat bubble, and the same defect can be produced by any provider/model.

**Constraints:**
- ADR-140 forbids v1 imports inside architect-v2.
- ADR-160 keeps the card taxonomy closed.
- ADR-148 pins provider-id branching out of the orchestrator.
- The host->webview seam is the only channel through which provider output may reach the user, and only as typed messages.

## Decision

All user-facing fixes for architect-v2 MUST be applied at provider-neutral seams. (1) Free-text sanitization lives in cards/render.ts as sanitizeFreeText, invoked by renderTrailingNote and renderCompletion. (2) Folding model rationale into structured cards lives in orchestrator/loop.ts via composeTerminalSummary. (3) Live activity ticker events come from a thin ExecutorPort wrapper in host/index.ts that taps every executeCapability call. (4) Provider/model selection UI lives in host/chat-panel/ and reads provider metadata exclusively through providers/registry.ts; no UI code names a provider id. (5) Per-provider state is keyed by providerId but the storage shape is identical for every provider. (6) Adapter-only changes are restricted to wire-protocol concerns and to the static provider profile.

### Alternatives Considered

- **Patch each adapter when its model misbehaves** — Rejected: Defect recurs with any provider/model; multiplies code paths; violates ADR-148.
- **Centralize sanitization in a shared adapter base class** — Rejected: Sanitization is rendering, not transport. Bypasses host->webview seam.
- **Add per-provider feature flags to gate UI behavior** — Rejected: Combinatorial UI states; behavior depends on chosen model; violates the agnosticity goal.

## Consequences

- sanitizeFreeText, composeTerminalSummary, and the ExecutorPort activity wrap are part of architect-v2's shared seam contract.
- Adapters stay narrow: pure wire concerns.
- When a new provider is added, no UI/render/loop change is required.
- User-visible behavior is byte-identical across providers given the same model output shape.

**Risks accepted:**
- Centralizing sanitization in cards/render.ts means a bug there affects every provider.
- ExecutorPort wrap adds a thin layer of indirection on every capability call.
- If a future provider returns structured fields the orchestrator does not yet split, the leak path reopens until the adapter is updated.

## Guard Rails

> ⚠️ Do NOT add JSON-stripping, prose-cleanup, ticker-event emission, default-model selection, provider/model dropdown logic, or any user-visible policy inside an adapter file. Such code MUST live in cards/render.ts, orchestrator/loop.ts, host/index.ts wrapper layer, or host/chat-panel/.

> ⚠️ Do NOT introduce branches on providerId outside of host/chat-panel/panel.ts settings persistence. Branch on model.capabilities.api or a provider-neutral capability flag.

> ⚠️ Do NOT bypass the typed HostToWebview message seam. The webview MUST NOT receive any provider-shaped payload.

> ⚠️ Do NOT key user-facing copy or behavior on provider displayName.
