# ADR-164: Slice 6 — Capability matrix is a frozen typed data table; selection is a pure function over (capabilityId, density)

**Date:** 2026-05-09T22:14:28.893Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/capabilities/matrix.ts, extensions/vscode/src/architect-v2/capabilities/index.ts, plans/ARCHITECT_V2_SLICE6_CAPABILITY_MATRIX.md  

## Context

Selection logic could spread capability rules across switch statements, dynamic registries, or string keys — losing auditability of the 'graph-first wins' claim and making it impossible to verify completeness against the §2 plan tables.

**Constraints:**
- Matrix entries reference only Slice-4 Intent literals (compile-time validated)
- All entries Object.freeze'd; no mutation at runtime
- Matrix size = 42 (10+8+9+6+4+5); no duplicates by id
- Exactly 8 graphOnly entries (pure-graph wins)
- winRationale is short, human-readable, renders on cards

## Decision

CAPABILITY_MATRIX is a frozen typed array of CapabilityRecord values exported from matrix.ts. Each row carries: id (CapabilityId literal), group, graphFirst (Slice-4 Intent[]), fallback (Slice-4 Intent[]), graphOnly (boolean derived from fallback.length===0), winRationale (rendered on cards), enrichOnFallback (Intent? queued when sparse-mode runs). The matrix is the contract; the catalog (Slice 4) is the implementation. Exactly 42 entries: 10 navigation + 8 history + 9 mutation + 6 verification + 4 cognition + 5 environment, with 8 graphOnly entries.

### Alternatives Considered

- **Switch statements per capability inside selection logic** — Rejected: 42 capabilities = 42 switch arms; not auditable; impossible to render as a matrix
- **Discover capabilities dynamically from MCP tool roster** — Rejected: Conflates roster (Slice 4 liveness) with capability contract (Slice 6); roster changes per provider but the matrix is provider-neutral
- **Plain JSON config** — Rejected: Loses type safety; CapabilityRecord must reference Slice-4 Intent type checked at compile time

## Consequences

- Adding a capability is a single matrix entry + selection auto-handles it
- TypeScript catches typos in Intent references at compile time
- Slice 5 cards can render winRationale and group from the matrix
- Slice 7 can audit coverage by iterating CAPABILITY_MATRIX

**Risks accepted:**
- Matrix grows unwieldy as capabilities multiply — mitigated by group field for grouping in renderers
- Intent rename in Slice 4 breaks matrix — mitigated by TypeScript compile gate

## Guard Rails

> ⚠️ CAPABILITY_MATRIX MUST stay Object.freeze'd; no runtime mutation

> ⚠️ Adding a capability requires updating matrix.ts AND the plan §2 table in the same commit

> ⚠️ graphOnly is derived (fallback.length===0); never set manually

> ⚠️ All Intent references MUST exist in Slice-4 INTENT_GROUPS (TypeScript compile gate)
