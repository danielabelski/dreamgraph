# ADR-089: architect-core seam — import the v2 orchestrator concept into v1

**Date:** 2026-05-11T00:00:00.000Z
**Status:** accepted
**Decided by:** collaborative
**Affected entities:** architect-llm, chat-panel, context-builder, autonomy, architect-core (new)

## Context

The v1 chat panel (`extensions/vscode/src/chat-panel.ts`) concentrates the entire turn lifecycle — context assembly, prompt composition, provider call, tool dispatch, autonomy decision, card emission, persistence, attachment lifecycle, error recovery — inside a single ~1500 LOC `handleUserMessage` method. This monolith is the root cause of recurring user-visible defects (D1 toLowerCase crash, D2 dead Suggested Action buttons, D3 multi-modal wiring) because there is no seam at which any one stage can be tested or replaced in isolation.

`architect-v2/orchestrator/` was an attempt to split this monolith into a pure pass driver (`runPass`) over an injected port bag (`OrchestratorPorts`). The v2 attempt is non-functional in its current form (8 broken sub-slices) and is explicitly held under ADR-140 isolation. However, the **concept** at the centre of v2 — *a pure ordering of named effects, with every effect behind an injected port* — is sound, small, and proven by the v2 test suite that targets the loop in isolation.

**Constraints:**
- v1 is the only shippable surface today; nothing may regress.
- ADR-140 forbids v1 importing v2 source. The v2 folder remains isolated until cutover.
- All provider/model output must be normalized — no per-provider branching outside the adapter seam.
- No empty stubs: every newly-introduced function must have a complete implementation.
- The seam must be enhancement-only on first introduction (no behavior change).

## Decision

Create a new v1-native module `extensions/vscode/src/architect-core/` that re-implements the v2 orchestrator concept against the v1 working types (`ArchitectMessage`, `ArchitectContent`, the existing `ContextBuilder`, the existing autonomy state machine). The module exposes:

1. **`ports.ts`** — interfaces only: `ContextBuilderPort`, `PromptComposerPort`, `ProviderPort`, `ToolExecutorPort`, `MemoryPort`, `ClockPort`, `AttachmentPort`, `AutonomyPort`. No classes, no I/O.
2. **`types.ts`** — `UserIntent`, `PassResult` re-using v1 envelope types (no new domain types invented).
3. **`pass.ts`** — a single async `runPass(input): PassResult` that orders the port calls in the same sequence `chat-panel.ts` performs today. Contains zero I/O of its own.
4. **`adapters/`** — thin (<40 LOC each) translators wrapping existing v1 internals (`ContextBuilder.buildEnvelope`, `assemblePrompt`, `ArchitectLlm.callWithTools`, `persistMessages`, `_buildUserContentBlocks`, `parseAutonomyRequest`). Adapters introduce no new behavior; they expose the existing implementations as port instances.

The seam is gated by a VS Code configuration setting `dreamgraph.architect.useCorePass` (default `false`). Phase 1 ships the skeleton and the adapter wiring with the flag off; existing `handleUserMessage` continues to run unchanged. Subsequent phases flip the flag for one branch at a time (text-only → attachments → autonomy → tool-calls), each gated on a manual smoke-test parity check, before retiring the inline orchestration in `handleUserMessage`.

`architect-core/` is **v1 territory** under ADR-140's v1 side. It does not import from `architect-v2/`. The concept is imported; the code is not.

### Alternatives Considered

- **Keep refactoring `chat-panel.ts` in place** — Rejected: every recent defect proved the inline orchestration cannot be tested without spinning up the full vscode + provider + MCP stack, which is the reason regressions keep landing.
- **Adopt `architect-v2/orchestrator/` directly via re-export** — Rejected: v2 is non-functional, requires importing the broken `autonomy/`, `verification/`, `cards/`, `capabilities/`, `execution/` slices, and would violate ADR-140's isolation rule.
- **Ship the seam without a feature flag** — Rejected: any defect in the new `runPass` would block all chat traffic. The flag lets us flip per-window and roll back instantly during migration.
- **Wait for the v10.0.0 cutover and use v2 then** — Rejected: the user-visible monolith defects are happening now; deferring the seam means accepting more regressions and more rework when v2 lands.

## Consequences

- v1 gains a single deterministic entry point (`runPass`) that can be unit-tested with in-memory port fakes — a capability v1 has never had.
- New port interfaces document the actual stages of a chat pass; future contributors stop guessing where to add a hook.
- The D3 multi-modal logic, the D2 card-emission logic, and any future per-provider concerns each live in exactly one adapter; the driver stays provider-agnostic by construction.
- During Phase 1–3 the codebase carries two parallel orchestration paths (the legacy inline one and `runPass`). This duplication is intentional and time-boxed: Phase 4 deletes the inline path.
- Once stable, the seam unlocks a project-graph port (Phase 5) that can wrap MCP `mcp_dreamgraph_*` reads — the first concrete step toward graph-bound cards on v1.

**Risks accepted:**
- Adapter wrappers can drift from `chat-panel.ts` internals during refactors; the build will catch signature changes immediately, but behavioral drift requires the manual smoke test at each phase flip.
- The configuration flag could be left on or off accidentally during release; mitigated by defaulting to `false` until Phase 4 and noting the flag state in release notes for every Phase 3 flip.
- New port interfaces may need amendment as Phases 2–3 surface assumptions; locked with explicit type tests in Phase 1 before any adapter is written.

## Guard Rails

> ⚠️ Do NOT import any module from `extensions/vscode/src/architect-v2/` into `architect-core/` or any other v1 source file. ADR-140 isolation remains binding.

> ⚠️ Do NOT introduce per-provider branching inside `pass.ts` or any port interface. Provider differences live exclusively inside the existing architect-llm adapter methods (`_toAnthropicContent`, `_toOpenAIContent`, etc.).

> ⚠️ Do NOT add empty stubs to `architect-core/`. Every function must implement complete behavior; if a stage has no real implementation, the port is not added until it does.

> ⚠️ Do NOT flip `dreamgraph.architect.useCorePass` to `true` by default until Phase 4 retires the inline orchestration in `handleUserMessage`. The flag MUST default to `false` while both paths coexist.

> ⚠️ Do NOT delete the inline orchestration in `handleUserMessage` until every branch (text-only, attachments, autonomy continuation, tool-calls) has been verified against `runPass` via a manual smoke test recorded in the import checklist.
