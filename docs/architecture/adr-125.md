# ADR-125: LLM request timeout is a configurable LlmConfig field driven by env var

**Date:** 2026-05-05T12:04:19.016Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/cognitive/llm.ts, src/server/dashboard.ts, DREAMGRAPH_LLM_TIMEOUT_MS env var, OllamaProvider, OpenAiCompatibleProvider, AnthropicProvider  

## Context

All LLM provider implementations had hardcoded request timeouts. Operators running larger local models that legitimately exceeded the default could not extend the budget without editing source. There was no environment-variable knob and no shared LlmConfig field for the timeout.

**Constraints:**
- Default behaviour must be preserved (120 s budget) for operators who do not set the env var
- All four provider constructors must accept the new parameter with a default value (backward source-compat)
- Liveness probes stay short-circuited; only the completion path honours the configured timeout
- The dashboard.ts LlmConfig literal must include timeoutMs so TypeScript stays clean

## Decision

Add LlmConfig.timeoutMs (number, ms). parseLlmConfig() reads DREAMGRAPH_LLM_TIMEOUT_MS from env and defaults to 120_000 ms when unset or invalid. initLlmProvider() threads c.timeoutMs into all four provider constructors (ollama, openai, lmstudio, anthropic). Each provider stores it as a private field and uses AbortSignal.timeout(this.timeoutMs) on the actual completion fetch. Liveness probes (3 s ollama / 5 s openai-compatible) intentionally retain hardcoded short timeouts \u2014 they test reachability, not request budget.

## Consequences

- Operators running large local models (e.g. 70B+) can extend the LLM request budget without code edits
- Default behaviour is unchanged; existing deployments need no migration
- Dashboard, scheduler, and dream cycle paths all share the same configurable timeout

**Risks accepted:**
- Setting the env var to an unreasonably large value (e.g. hours) can mask a hung provider; operators must choose responsibly
- The cap is per request, not per session — a stuck provider can still consume budget across many calls
- Negative or zero values fall back to the 120_000 default; this is intentional but may surprise operators expecting an instant-fail mode

## Guard Rails

> ⚠️ Do NOT hardcode timeouts in provider implementations — always accept timeoutMs and use AbortSignal.timeout(this.timeoutMs)

> ⚠️ Do NOT change the liveness-probe short timeouts to use the configured value; reachability and request-budget are different concerns

> ⚠️ If adding a new provider, accept timeoutMs as the last constructor parameter with default 120_000 to match existing providers

> ⚠️ The default (120_000) and the env var name (DREAMGRAPH_LLM_TIMEOUT_MS) are part of the operator contract — do not rename without a migration note
