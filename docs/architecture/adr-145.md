# ADR-145: Architect v2 locks local provider flagships: LM Studio = gpt-oss-120b high-context, Ollama = qwen2.5-coder:32b

**Date:** 2026-05-09T19:58:03.979Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/providers/, extensions/vscode/package.json, plans/ARCHITECT_V2_SLICE1_INVENTORY.md  

## Context

v1 Architect leaves local provider model selection entirely to user settings, which produces ambiguous first-run behavior for LM Studio and Ollama users and complicates documentation, benchmarking, and troubleshooting because there is no canonical 'recommended' model per provider.

**Constraints:**
- Local-first deployments need a sensible flagship default per provider; first-run experience with no model picked is poor.
- LM Studio and Ollama have different runtime characteristics; a single shared default would be wrong for at least one.
- User explicitly chose these flagships during the rewrite kickoff and locked them as the v2 baseline.
- Cloud provider defaults must stay aligned with the v9.0.0 locked set (GPT-5.5/5.4, Claude 4.7 xhigh).

## Decision

Architect v2 ships with locked local provider flagships: LM Studio default model = gpt-oss-120b in high-context configuration. Ollama default model = qwen2.5-coder:32b. These are the recommended defaults baked into the provider profile model; users override per-instance via settings, but the out-of-box experience uses these flagships. Cloud provider defaults (already locked in v9.0.0): OpenAI = GPT-5.5 Responses API as default + GPT-5.4 previous API as equal-class option; Anthropic = Claude 4.7 xhigh.

### Alternatives Considered

- **Leave local provider defaults as 'whatever the user has installed'** — Rejected: Settings ambiguity wastes user time; first-run experience with LM Studio or Ollama is poor when no flagship is recommended, and the user explicitly asked for locked defaults.
- **Make local providers a single shared default** — Rejected: LM Studio and Ollama have different runtime characteristics and different best-in-class models; a shared default would be wrong for at least one of them.
- **Auto-detect installed local model and pick the best one at runtime** — Rejected: Adds discovery logic and surprise; users prefer predictable defaults they can override over magic that might pick the wrong model.

## Consequences

- First-run experience with LM Studio or Ollama is predictable: a flagship is selected, user knows what to download.
- Provider profile model can ship validated capability flags for these specific defaults (context window, tool-call format, reasoning support).
- Documentation, troubleshooting, and benchmark suites can target known defaults rather than 'whatever the user picked'.
- Users override defaults per-instance via VS Code settings; the lock is only for out-of-box experience.

**Risks accepted:**
- Recommended local flagships may become outdated as new models release; superseding ADR will be required when bumping defaults.
- User hardware may not support the flagship (gpt-oss-120b high-context needs significant VRAM); UX must clearly signal hardware requirements and provide fallback guidance without silently switching models.

## Guard Rails

> ⚠️ Do not change the LM Studio default away from gpt-oss-120b high-context without a superseding ADR.

> ⚠️ Do not change the Ollama default away from qwen2.5-coder:32b without a superseding ADR.

> ⚠️ Do not change cloud provider defaults (GPT-5.5 Responses API + GPT-5.4 previous API + Claude 4.7 xhigh) without a superseding ADR.

> ⚠️ Do not silently fall back to a different local model when the flagship is unavailable — surface the gap clearly so the user can install or override.
