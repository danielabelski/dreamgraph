# ADR-098: LLM-readiness watcher with fingerprinted re-runs for graph bootstrap

**Date:** 2026-05-03T10:27:16.727Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** src/server/daemon.ts, src/tools/scan-project.ts, src/tools/enrich-seed-data.ts, src/tools/init-graph.ts, src/cli/dg.ts, templates/default, templates/lmstudio, templates/ollama  

## Context

dg init may or may not arrive with a working LLM. Default lmstudio/ollama templates have populated env vars but are useless until the user starts the local server and loads a model. Personal templates with API keys may be ready immediately. No current trigger fires the bootstrap chain (scan_project + enrich_seed_data + ADR discovery + first dream cycle) the moment the LLM actually becomes usable, so instances stay on templates/default schema stubs indefinitely.

**Constraints:**
- Readiness must reflect actual LLM availability, not env-var presence
- Bootstrap must run exactly once per (provider, model, endpoint) configuration
- Provider switches must not waste a full source re-scan
- Users need a manual escape hatch
- Source-file changes after bootstrap need an incremental delta path

## Decision

Add an LLM-readiness watcher in the daemon that fires the bootstrap chain the first time a real completion call against the configured provider returns successfully. Re-run policy: fingerprint = hash(provider + model + url); bootstrap chain runs once per fingerprint. Fingerprint changes trigger re-enrichment ONLY (not a re-scan), reusing existing entity ids and refreshing description/domain/keywords/links. Surface progress via cognitive_status. Add a `dg bootstrap` CLI verb for manual retrigger. Add a debounced file-watcher delta scan for incremental updates after first bootstrap.

### Alternatives Considered

- **Auto-scan during dg init** — Rejected: LLM config isn't ready at init time for local-LLM templates; would require redoing the scan after enrichment.
- **Poll env-var presence to detect readiness** — Rejected: False positives on local-LLM templates whose env vars are populated long before the model is loaded.
- **Re-scan on every fingerprint change** — Rejected: Wasteful — source files haven't moved; only semantic metadata depends on the model.

## Consequences

- Instances bootstrap automatically the moment a real LLM is reachable, regardless of when that happens
- Provider switches are cheap (re-enrichment only) but still refresh model-dependent metadata
- dg bootstrap CLI verb makes the watcher debuggable and gives users an escape hatch
- Delta scans keep the graph fresh without a full re-scan on every file save

**Risks accepted:**
- Real completion call costs tokens / startup latency
- Fingerprint hash collisions are theoretically possible (mitigated by including url)
- Debounced file-watcher needs careful tuning to avoid scan storms

## Guard Rails

> ⚠️ Readiness check MUST be a real completion call, not env-var presence

> ⚠️ Fingerprint changes MUST NOT trigger a full source re-scan

> ⚠️ Existing entity ids MUST be preserved across re-enrichment

> ⚠️ dg bootstrap CLI verb MUST remain available as a manual override
