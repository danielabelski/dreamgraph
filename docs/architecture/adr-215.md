# ADR-215: Architect chat prompts use POST-only body transport

**Date:** 2026-05-27T23:53:25.160Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** standalone-architect, src/architect/routes.ts, /api/architect/v1/chat, standalone_architect_browser_shell  

## Context

Standalone Architect browser chat accepted or risked prompt-bearing interactions being represented as URL-addressable navigation. Prompt text in GET URLs can leak through browser history, referrers, proxy logs, tunnel metadata, and shared machine artifacts.

**Constraints:**
- Architect chat crosses a browser-to-daemon HTTP trust boundary.
- Prompt text is sensitive operator input and must not be serialized into URLs.
- Read-only navigation, plan selection, and snapshot loading may remain GET when they carry only identifiers or navigation state.
- Mutations and prompt-bearing operations must remain daemon-authoritative and auditable.

## Decision

The standalone Architect chat endpoint is POST-only at /api/architect/v1/chat with application/json request bodies. GET requests to that endpoint are rejected with 405 Allow: POST, and the browser chat requests text/event-stream responses over the same POST request when streaming is requested. Plan browsing and other read-only navigation may remain GET.

### Alternatives Considered

- **Allow chat prompts in GET query parameters for easier deep links** — Rejected: This leaks prompt text into browser history, referrers, proxies, logs, and tunnel metadata.
- **Use EventSource GET directly for prompt submission** — Rejected: EventSource is GET-based and cannot safely carry prompt text without URL leakage.
- **Keep JSON-only POST responses** — Rejected: It is safe for prompt transport but does not satisfy the browser Architect streaming response path needed for longer model runs.

## Consequences

- Prompt text stays in POST bodies instead of URLs.
- Browser Architect can request SSE responses without using GET for prompts.
- Daemon remains the authority for chat handling, plan context, and audit events.
- Future provider/model selection work has a clear transport rule for prompt-bearing browser operations.

**Risks accepted:**
- POST SSE parsing is currently final-result oriented and can later be expanded to token-level streaming.
- Existing clients that incorrectly used GET for chat prompts must update to POST.

## Guard Rails

> ⚠️ Do not add or reintroduce any GET endpoint that accepts Architect prompt text, message text, or full conversation content.

> ⚠️ Do not use EventSource GET to submit chat prompts; use POST with JSON and stream the response from that POST or use a websocket with an authenticated daemon-bound session.

> ⚠️ Do not put API keys, model prompts, continuation payloads, or conversation content in query strings.

> ⚠️ Keep read-only GET routes limited to plan selection, snapshot loading, and navigation state that does not contain prompt content.
