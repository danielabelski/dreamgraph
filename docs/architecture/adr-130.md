# ADR-130: Canonical M1 runtime metrics snapshot aligns /metrics, system://metrics, and query_runtime_metrics

**Date:** 2026-05-07T23:53:44.589Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/observability/runtime-metrics.ts, src/index.ts, src/resources/register.ts, src/tools/runtime-senses.ts  

## Context

Runtime observability surfaces were diverging: internal metrics sources existed, but the canonical contract for M1 runtime observability was not uniformly represented across the shared adapter, HTTP endpoint, resource surface, and tool surface. Without a single snapshot schema, future consumers could drift and produce incompatible metrics payloads.

**Constraints:**
- Preserve graceful behavior when runtime metrics are disabled or no external endpoint is configured.
- Use the existing shared consolidation point in src/observability/runtime-metrics.ts rather than creating parallel metrics adapters.
- Keep the initial M1 schema operationally useful even if some buckets are derived heuristically from current tool and graph metrics sources.
- Allow local/private HTTP exposure for /metrics in M1 without requiring public deployment hardening.
- Align resource and tool surfaces to the same canonical snapshot semantics wherever feasible.

## Decision

Adopt src/observability/runtime-metrics.ts as the canonical producer of RuntimeMetricsSnapshotV1 using the nested M1 schema. The HTTP /metrics endpoint, the system://metrics resource, and the query_runtime_metrics tool should all align to this canonical snapshot model. In M1, /metrics is gated by an explicit enable flag and restricted to local/private use, while resource/tool surfaces may use the same snapshot directly or via configured endpoint retrieval depending on context.

### Alternatives Considered

- **Let each surface (/metrics, resources, tools) shape its own metrics payload independently** — Rejected: This would reintroduce contract drift and make observability consumers unreliable.
- **Keep the previous flat metrics schema until all downstream consumers are implemented** — Rejected: The flat schema does not match the approved M1 plan and would force later breaking changes across more consumers.
- **Expose only an external endpoint-backed query_runtime_metrics tool and avoid internal canonicalization** — Rejected: This would make local validation harder and leave resource/HTTP surfaces semantically inconsistent.

## Consequences

- Runtime observability consumers have a single M1 snapshot contract to target.
- Future additions to metrics buckets can be made in one shared adapter and flow to HTTP/resource/tool surfaces consistently.
- There is a clear implementation anchor for M1 observability alignment across runtime surfaces.

**Risks accepted:**
- Some current bucket derivations are heuristic because existing low-level metrics sources were not originally designed around the exact M1 schema.
- Consumers not yet migrated may still assume the previous flat shape.
- Async/sync signature changes in the canonical snapshot producer may require follow-up alignment if hidden call sites exist.

## Guard Rails

> ⚠️ Do NOT introduce a second canonical runtime metrics adapter while RuntimeMetricsSnapshotV1 is owned by src/observability/runtime-metrics.ts.

> ⚠️ Do NOT let /metrics, system://metrics, or query_runtime_metrics drift to incompatible payload schemas without explicitly revisiting this decision.

> ⚠️ Do NOT expose /metrics broadly by default in M1; keep it explicitly enabled and locally constrained unless a later decision hardens it for wider deployment.

> ⚠️ Do NOT treat absent or partial runtime data as evidence of feature health; observability gaps remain possible.
