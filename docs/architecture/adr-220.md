# ADR-220: Architect Level 3 Slice 5 execution control implementation verified against binding ADRs

**Date:** 2026-05-29T14:54:51.232Z  
**Status:** accepted  
**Decided by:** system  
**Affected entities:** standalone-architect, src/architect/routes.ts, src/architect/cli-bridge.ts, tests/standalone-architect-routes.test.ts, plans/architect-level-3.implementation-log.md, standalone_architect_active_session_runtime  

## Context

Architect Level 3 Slice 5 needed a durable graph record that its task execution control implementation was verified against the binding ADR set after source inspection and DreamGraph-run verification, without duplicating already-applied source changes.

**Constraints:**
- Slice 5 execution controls must remain daemon-normalized state transitions exposed through /api/architect/v1/commands rather than browser-local execution.
- Runtime identity, route metadata, provenance, and CLI adapter behavior must stay synchronized with ADR-216 and ADR-217.
- Prompt-bearing chat transport must remain POST-only per ADR-215; execution control commands must not introduce GET prompt leakage.
- Plan lifecycle and execution state must remain distinct per ADR-218, and Project scope must not write selected-plan logs by default per ADR-219.
- Raw CLI commands and raw CLI output must remain hidden from primary chat UX; structured formatted payloads are the user-facing contract.

## Decision

Treat the existing Architect Level 3 Slice 5 implementation as verified: runtime metadata exposes normalized execution-control capabilities and active execution snapshots; /stop, /pause, /resume, and steering flow through daemon command envelopes; supported stop requests use daemon-owned abort signaling for CLI bridge child processes; browser controls remain a projection of daemon state and keep raw CLI details out of normal chat output.

### Alternatives Considered

- **Re-implement Slice 5 despite the implementation log and tests showing it is already applied.** — Rejected: That would risk duplicate or divergent execution-control semantics without evidence of a missing source delta.
- **Record only a chat summary without a graph decision.** — Rejected: The user explicitly requested graph recording, and future guard-rail checks need durable graph context.
- **Treat ADR guard warnings as conflicts and halt despite tests passing.** — Rejected: The warnings were boundary reminders; source inspection showed the implementation satisfies daemon authority, POST transport, runtime identity, and scope separation constraints.

## Consequences

- Future graph queries can find the verified Slice 5 execution-control implementation and its source/test anchors.
- Later Slice 6 UI work can build on the existing daemon execution-control contract instead of redefining stop, pause, resume, or steering semantics.
- ADR guard checks have a durable reconciliation point tying Slice 5 to ADR-215, ADR-216, ADR-217, ADR-218, and ADR-219.

**Risks accepted:**
- Pause, resume, and steering are currently capability-gated false for CLI runtimes, so future provider support will require additive implementation and tests.
- The record is verification-oriented and should not be mistaken for a new execution-control ADR that supersedes existing binding decisions.
- Implementation-log parsing and active runtime snapshots remain sensitive to future route refactors.

## Guard Rails

> ⚠️ Do not make browser buttons or slash parsing authoritative for execution state; they must call daemon command endpoints and render daemon snapshots.

> ⚠️ Do not expose raw CLI commands or raw child-process output as the primary execution-control chat response.

> ⚠️ Do not enable pause, resume, or steering for an adapter until the runtime can preserve and resume execution context with tests.

> ⚠️ Do not reintroduce selected-plan implementation-log writes for Project-scope execution-control chatter by default.

> ⚠️ Do not bypass the CLI MCP bridge or DreamGraph MCP authority when routing CLI adapter repository operations.
