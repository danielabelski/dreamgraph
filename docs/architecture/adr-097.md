# ADR-097: Hard-reserved token slice for graph evidence in architect context

**Date:** 2026-05-03T10:27:16.700Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** extensions/vscode/src/context-builder.ts, extensions/vscode/src/prompts/architect-core.ts, extensions/vscode/prompts/architect_core.md, src/api/routes.ts  

## Context

The context builder treats graph evidence (features, workflows, tensions, ADRs) as optional — gated by intentConfidence ≥ 0.5 and a literal source_files substring match. Under token pressure, graph evidence is the first thing trimmed. The architect ends up file-centric in practice despite a graph-first design intent.

**Constraints:**
- Must work across 8k → 128k+ context windows
- Must not drown core logic in very large windows
- Curated content only, no raw dumps
- Confidence markers must be preserved so the LLM can weight validated vs candidate evidence

## Decision

Reserve a hard token slice: 70% core logic / 15% user request + active code/selection / 15% graph evidence. Absolute caps per window: 8k → 800–1200 tokens; 32k → 2k–4k tokens; 128k+ → dynamic, capped at ~10% of window. Graph slice is curated only — selected node + immediate neighborhood, transitive impacted nodes (depth ≤ 2, ranked), tensions touching the request, ADR constraints touching the request, plus confidence markers. Golden rule: better 300 curated tokens than 3000 garbage tokens.

### Alternatives Considered

- **Keep graph evidence opt-in by intent confidence** — Rejected: Token-pressure trimming consistently strips it first; defeats the graph-first design.
- **Always inject full graph as raw JSON** — Rejected: Drowns the model, blows the budget, and produces worse answers than no graph at all.
- **Percentage-only with no absolute caps** — Rejected: 128k+ windows would dedicate 19k+ tokens to graph evidence and dilute core logic.

## Consequences

- Architect always has at least some graph grounding regardless of intent confidence
- Context builder must rank-and-trim instead of concatenate-and-hope
- LLM can naturally weight validated edges over candidate ones via confidence markers
- Predictable token budgets make response latency more stable

**Risks accepted:**
- Hard reservation reduces room for raw code in tight windows
- Ranking algorithm becomes a quality bottleneck — bad ranking = bad answers
- Curation logic adds CPU cost on every architect invocation

## Guard Rails

> ⚠️ Do NOT remove the 15% graph slice without revisiting this ADR

> ⚠️ Do NOT exceed the absolute caps on small windows (8k/32k) — quality over quantity

> ⚠️ Do NOT inject raw graph dumps into the slice — curation is mandatory

> ⚠️ Confidence markers MUST stay attached to every graph evidence item
