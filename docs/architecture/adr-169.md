# ADR-169: Slice 7 — Repair loop is bounded (1 attempt per kind per task) and always a ContinuationNeed, never inline retry

**Date:** 2026-05-09T22:31:09.185Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/verification/repair.ts, extensions/vscode/src/architect-v2/autonomy/signals.ts  

## Context

A failed verification needs a bounded recovery path that is observable to Slice 3's autonomy budget and Slice 5's cards. Inline retries hide cost and break ADR-154 (tool-name embedding). Unbounded repair loops eat budget and never surface a clean blocker.

**Constraints:**
- Repair MUST be a continuation (Slice 3 ContinuationNeed), never an inline retry
- ContinuationNeed.continuationPrompt MUST embed the verification tool name (ADR-154 enforced by createContinuationNeed)
- Repair budget defaults to 1 per VerificationKind per task (overridable per call, not globally mutated)
- planRepair is pure (no I/O, no Date.now, no random)

## Decision

planRepair is pure: input is (failedStep, repairAttemptsByKind, autonomyBudget, optional nonActionable). Default budget is DEFAULT_REPAIR_BUDGET_PER_KIND = 1 attempt per VerificationKind per task. Repair always emits a ContinuationNeed via createContinuationNeed (which enforces ADR-154 tool-name embedding); inline retry is forbidden. Output is a 3-arm discriminated union: repair_with_continuation, escalate_to_blocker (when budget or autonomy exhausted), skip_repair (when caller flags non_actionable).

### Alternatives Considered

- **Inline retry of the failed verification tool** — Rejected: loses Slice 3 budget accounting; the autonomy state machine never sees the retry; ADR-154 invariant becomes invisible
- **Unbounded repair attempts** — Rejected: trivial path to runaway loops; conflicts with token economy and Slice 3 stop conditions
- **Repair budget shared across all kinds** — Rejected: a flaky build alone could exhaust budget for all other kinds; per-kind isolation gives finer-grained signals

## Consequences

- At most 1 repair continuation per failed verification kind per task by default
- Repair is observable in the autonomy budget view (continuationsRemaining decrements)
- ADR-154 tool-name invariant is enforced at construction time (no silent drift)
- Non-actionable failures produce a soft blocker, not a silent skip (user always sees the gap)

**Risks accepted:**
- Default of 1 repair may be too aggressive for flaky tests (mitigated by maxAttemptsPerKind override and nonActionable flag)
- Per-kind counters add a small amount of state to TaskState (additive widening per ADR-151)

## Guard Rails

> ⚠️ planRepair MUST NOT call createContinuationNeed without a tool name (createContinuationNeed throws)

> ⚠️ Repair attempts MUST be tracked per VerificationKind, not globally

> ⚠️ skip_repair MUST emit a soft Blocker (no silent verification skips)

> ⚠️ Default budget changes require ADR amendment (do not silently increase)
