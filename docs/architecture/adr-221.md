# ADR-221: Standalone Architect terminal output is a local user-facing surface, not a public UI contract

**Date:** 2026-05-29T18:37:23.856Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** standalone-architect, standalone_architect_terminal_surface, codex-cli, copilot-cli, src/architect/cli-bridge.ts, src/architect/routes.ts, ADR-217, ADR-220  

## Context

Standalone Architect needs a clear boundary for terminal visibility. Terminal output is user-facing because the operating user can access it directly, but treating terminal streams as the primary browser/chat contract would conflict with daemon-normalized Architect UI behavior and existing CLI adapter guard rails.

**Constraints:**
- Terminal access is local to the operating user and may be acceptable as a user-facing diagnostic or execution surface on that basis.
- Standalone Architect remains daemon-authoritative; browser clients and chat responses must use governed daemon contracts rather than provider-native shell/read/write routes.
- CLI adapter repository operations must continue through the DreamGraph MCP bridge per the accepted adapter-boundary decisions.
- Raw CLI commands and raw child-process output must not become the primary chat UX or public browser API contract.
- User-facing terminal visibility must not imply multi-user publication, remote exposure, or supportability as a stable product protocol.

## Decision

Define terminal output as a local, user-accessible surface: it may expose execution diagnostics and raw-ish operational detail to the operating user because that user has direct terminal access. This does not make terminal output the canonical browser/chat UI contract, does not authorize provider-native repository access, and does not permit raw CLI streams to replace daemon-normalized structured responses in Standalone Architect.

### Alternatives Considered

- **Treat terminal output as non-user-facing implementation detail only.** — Rejected: The terminal is directly accessible to the operating user, so hiding all diagnostics on that basis would misclassify the surface and make local debugging unnecessarily opaque.
- **Treat terminal output as the primary user-facing contract for Standalone Architect.** — Rejected: That would bypass the daemon-normalized browser/chat contract and conflict with existing CLI adapter and execution-control guard rails.
- **Expose the same raw terminal stream through browser chat as normal output.** — Rejected: Chat must remain structured and daemon-normalized; raw streams can leak unstable implementation detail and provider-specific behavior.

## Consequences

- ADR reasoning can distinguish local terminal visibility from browser/chat publication.
- Terminal diagnostics can remain available to the operating user without weakening the daemon-authoritative UI contract.
- Future implementation can add terminal-oriented diagnostics while preserving structured chat responses and MCP-governed repository operations.

**Risks accepted:**
- Developers may over-read 'user-facing terminal' as permission to expose raw terminal streams in chat or remote browser contexts.
- Local terminal diagnostics may still include sensitive operational detail and need conservative filtering when copied into shared UI surfaces.
- The boundary depends on keeping local terminal access distinct from any future remote or multi-user Architect deployment.

## Guard Rails

> ⚠️ Do not use local terminal visibility as justification for exposing raw CLI streams as primary browser chat responses.

> ⚠️ Do not route repository reads, writes, or shell commands through provider-native terminal access when DreamGraph MCP authority is available.

> ⚠️ Do not treat terminal output as a stable public API; structured daemon payloads remain the product contract.

> ⚠️ Do not expand local terminal diagnostics into remote or multi-user surfaces without a new ADR covering privacy, authorization, and redaction.

> ⚠️ Keep terminal diagnostics scoped to the operating user and clearly separate from plan implementation logs unless a governed log-writing path intentionally records them.
