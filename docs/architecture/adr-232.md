# ADR-232: Architect CLI rich TUI is a distinct terminal surface with implementation-owned Ink dependency

**Date:** 2026-06-07T01:26:40.466Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** src/cli/commands/architect.ts, src/cli/utils/architect-client.ts, tests/architect-cli.test.ts, package.json, package-lock.json, dg architect tui, architect_cli_terminal_shell  

## Context

Architect CLI is becoming a new product surface distinct from the existing browser, VS Code, and dependency-free log-mode CLI interfaces. ADR-231 selected Ink for a future rich renderer but guarded against adding Ink until source imports and renderer tests existed. The rich TUI implementation now needs explicit ADR authority to install and use Ink while preserving daemon-owned runtime, provenance, plan state, and governed mutation boundaries.

**Constraints:**
- Architect CLI must remain a thin daemon/MCP client; daemon runtime identity, plan lifecycle, tool execution, provenance, and governed mutations stay authoritative.
- The rich TUI is a terminal-native Architect surface, not a browser/xterm projection and not a provider-native shell/read/write authority.
- Non-interactive `dg architect` status/config/chat/plans JSON and text outputs must remain stable automation contracts separate from rich TUI presentation state.
- Ink/React dependencies are acceptable only when imported by the rich TUI implementation and covered by focused renderer/CLI tests.
- Terminal layout, focus, scrollback, filters, and local input state remain local presentation state and must not become repository facts or plan authority.
- The TUI must consume daemon-normalized status/config/chat/plan/tool-trace/provenance payloads rather than provider-native envelopes or raw terminal output.

## Decision

Implement the Architect CLI rich TUI as an explicit terminal-native surface under `dg architect tui` using Ink/React dependencies, with daemon-normalized payloads as the only authority for runtime identity, chat, streaming, tool traces, provenance, and plan state. Preserve the existing dependency-free JSON/text automation paths for non-interactive subcommands and allow log-mode fallback when rich rendering is unavailable or not attached to a TTY.

### Alternatives Considered

- **Keep `dg architect tui` permanently dependency-free log mode** — Rejected: It avoids package growth but does not complete the requested rich terminal UX or provide pane/focus/state ergonomics for long Architect sessions.
- **Reuse the standalone browser/xterm surface for terminal UI** — Rejected: That would blur the terminal/browser boundary and make the CLI feel like a browser payload projection rather than its own terminal-native surface.
- **Install Ink before implementation/tests only as a reserved dependency** — Rejected: ADR-231 explicitly rejected unused dependency installation; the dependency is justified by this implementation slice because it will be imported and tested.
- **Let the TUI execute repository operations through provider-native terminal routes** — Rejected: That violates existing DreamGraph MCP authority and CLI adapter guard rails.

## Consequences

- `dg architect tui` can evolve from log mode into a rich pane-based terminal UI while status/config/chat/plans remain scriptable.
- Ink and React-family dependencies enter the package only together with actual source imports and tests.
- Runtime labels shown by `dg architect`, config, chat, and TUI converge on the same daemon-owned session object.
- Future terminal UI refinements can focus on presentation without redefining Architect execution authority.

**Risks accepted:**
- Ink and React increase install size and can add terminal rendering edge cases on narrow or non-TTY environments.
- Rich terminal rendering may require careful tests for no-color, CI, redirected output, resize, and high-volume streams.
- Without strict boundaries, local TUI state could be mistaken for daemon plan or runtime authority.

## Guard Rails

> ⚠️ Do not move Architect runtime identity, plan lifecycle, task control, tool execution, provenance, or governed repository mutation authority into Ink component state.

> ⚠️ Do not parse provider-native envelopes or raw CLI output in the rich TUI; consume daemon-normalized contracts only.

> ⚠️ Do not break non-interactive `dg architect` status/config/chat/plans JSON and text outputs while implementing the TUI.

> ⚠️ Do not require an interactive TTY for automation commands; rich rendering may fall back to log mode or fail clearly only for `dg architect tui`.

> ⚠️ Do not treat terminal rendering, local scrollback, filters, focused pane, or typed draft input as DreamGraph evidence or plan state unless a governed daemon path explicitly records it.
