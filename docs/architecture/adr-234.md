# ADR-234: Implementation status requires verified executable behavior, not plan/graph/doc updates

**Date:** 2026-06-08T19:04:26.362Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** dreamgraph_project_scope, knowledge_graph, living_docs, implementation_status, planning_artifacts  

## Context

Project status can become misleading if plan updates, graph edits, documentation changes, or scope changes are described as implemented before corresponding executable behavior exists and has been verified. This creates drift between DreamGraph facts, project documentation, and the actual source code.

**Constraints:**
- Implementation claims must be grounded in actual executable source changes, not only metadata or narrative changes.
- Graph facts must describe the current implementation state rather than aspirational or planned state.
- Documentation and planning artifacts may describe intent, scope, or decisions, but they do not by themselves change runtime behavior.
- Verification evidence is required before marking behavior as implemented.

## Decision

Treat plan, graph, documentation, and project-scope updates as non-implementation changes unless executable behavior changed in the source code and was verified. Implementation status may only be claimed after code-level changes exist and appropriate verification has passed or is explicitly documented. Graph updates must follow and reflect actual implementation state; graph changes alone are never sufficient evidence of implementation.

### Alternatives Considered

- **Allow graph or documentation updates to mark functionality implemented** — Rejected: This permits aspirational state to masquerade as runtime capability and causes drift between code, graph, and docs.
- **Allow implementation claims based on unverified code changes** — Rejected: Executable behavior may still be broken or incomplete; verification is part of the implementation evidence.
- **Keep implementation status only in plans and not in graph** — Rejected: DreamGraph uses graph state as project authority, so graph must remain aligned with code reality rather than disconnected from it.

## Consequences

- Implementation labels become more trustworthy and evidence-bound.
- Plans, docs, and graph entries must distinguish intended, planned, in-progress, implemented, and verified states.
- Graph maintenance must be synchronized with source-code reality and cannot be used as a shortcut around implementation.
- Agents must avoid saying a task is implemented unless they can cite executable code changes and verification results.

**Risks accepted:**
- More conservative status reporting may slow perceived progress.
- Some completed planning or graph hygiene work may need separate labels to avoid being mistaken for implementation.
- Existing graph or plan entries may require cleanup if they previously overstated implementation state.

## Guard Rails

> ⚠️ Do NOT mark a feature, workflow, remediation, or plan item as implemented solely because a plan, graph, documentation, ADR, or project-scope artifact changed.

> ⚠️ Do NOT claim implementation unless executable project behavior changed in actual source code and verification evidence is available or explicitly recorded.

> ⚠️ Do NOT let graph facts represent aspirational behavior as implemented; graph state must reflect actual implementation state.

> ⚠️ Do NOT treat DreamGraph graph mutations, ADRs, living-doc exports, or scope metadata changes as sufficient implementation evidence.

> ⚠️ When implementation status is ambiguous, label it as planned, documented, graph-recorded, or unverified rather than implemented.
