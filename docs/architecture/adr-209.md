# ADR-209: Standalone Architect plan operational state is daemon-owned and crystallizes into durable graph knowledge

**Date:** 2026-05-27T20:14:01.226Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** plans/STANDALONE_ARCHITECT_MIGRATION_PLAN.md, plans/STANDALONE_ARCHITECT_MIGRATION_PLAN.implementation-log.md, plan records, slice records, continuation state, review gates, task records, tool traces, planning:sync_plan_graph, planning:archive_plan, planning:get_resume_packet, ADR-142, ADR-207  

## Context

The migration plan required a decision on where active plan state lives. Without an explicit rule, implementation could fragment state across sidecar JSON, browser-local business state, markdown-only mutation, or permanently-active graph execution structures.

**Constraints:**
- ADR-142 requires markdown plan narrative plus ADR/graph-readable mirrors, not markdown alone.
- ADR-207 requires permanent markdown preservation while keeping active graph cognition adaptive and temporary.
- Current slice, status, checkpoints, gate outcomes, continuation state, run traces, and pending review state need daemon-owned coordination so resume behavior survives browser reloads and UI restarts.
- UI-local state such as layout, focus, and selection may remain browser-local, but durable operational state must remain authoritative in DreamGraph-owned records.

## Decision

Lock active standalone Architect plan state to daemon-owned DreamGraph operational records and graph workflow cognition during active execution, while preserving markdown plans and append-only implementation logs as the durable historical record. Active state may include current slice, status, checkpoints, gate decisions, continuation state, task/run traces, and pending review projections. As work stabilizes, temporary workflow cognition must crystallize into durable project entities or fade from active cognition per ADR-207.

### Alternatives Considered

- **Persist active plan state primarily in browser storage or a frontend-only cache** — Rejected: This breaks crash/reload continuity and makes the browser the accidental source of truth for operational state.
- **Keep all plan state only in markdown files** — Rejected: Markdown is the historical narrative record, not the sole coordination substrate for active plan execution and checkpoints.
- **Keep completed execution structures permanently active in the graph** — Rejected: ADR-207 rejects permanent active cognition for completed slices because it pollutes retrieval with stale execution detail.

## Consequences

- Resume packets and plan status can be reconstructed from daemon-owned operational records plus append-only markdown logs.
- The browser stays a projection/control surface rather than a business-state owner.
- Implementation can distinguish between historical plan artifacts and active coordination state without inventing sidecar persistence silos.

**Risks accepted:**
- Entity mapping from active slices to durable graph updates may still require careful implementation review.
- If daemon-owned state and markdown logs drift, resume UX may become confusing until synchronization tooling matures.

## Guard Rails

> ⚠️ Do not store authoritative active plan execution state exclusively in browser-local storage or frontend-only caches.

> ⚠️ Do not treat markdown plans as the only operational state store for checkpoints, continuation, or review state.

> ⚠️ Do not keep completed plan execution structures indefinitely active once their verified outcomes have crystallized into durable project entities.

> ⚠️ Do not introduce a separate sidecar persistence model for core operational plan state unless a future ADR explicitly justifies it.
