# ADR-204: Rebrand v11 preference layer as Adaptive Future Engine

**Date:** 2026-05-23T03:13:35.099Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** plans/V11_ADAPTIVE_FUTURE_ENGINE_PLAN.md, plans/WHAT_NOW.md, feature_adaptive_future_engine, feature_cognitive_intervention, tool_get_remediation_plan, ADR-203  

## Context

The proposed v11 preference layer was previously called Taste Engine, but that name overemphasizes subjective taste and underemphasizes the system's actual role: ranking compliant candidate futures using graph evidence, governance constraints, and learned project preference.

**Constraints:**
- The rebrand must preserve the existing architectural scope: advisory preference ranking, not hard enforcement or a new cognitive lifecycle state.
- ADR-203 model-routing rules remain binding for LLM-enabled tools regardless of the product label.
- Existing planning artifacts and future implementation work need a stable name that describes candidate-future selection rather than subjective taste.
- Terminology should continue to distinguish hard ADR/API/workflow constraints from softer adaptive preference evidence.

## Decision

Use Adaptive Future Engine as the durable name for the proposed v11 preference layer. Use future-fit, future signals, future objections, adaptive future outcomes, and adaptive future context as the preferred vocabulary in plans and future implementation work. Treat Taste Engine as historical terminology only.

### Alternatives Considered

- **Keep Taste Engine as the durable name** — Rejected: It is concise but too easily read as subjective or aesthetic preference rather than evidence-backed future selection.
- **Use only generic preference engine terminology** — Rejected: That loses the central product idea: DreamGraph chooses among compliant candidate futures, not just preferences in isolation.

## Consequences

- V11 planning and implementation work will use Adaptive Future Engine terminology consistently.
- Future data model and API names should prefer FutureSignal, FutureOutcome, FutureObjection, future-fit scoring, and adaptive future context over TasteSignal/TasteOutcome/TasteObjection terminology.
- Historical ADRs or plan references that still mention Taste Engine should be interpreted as referring to Adaptive Future Engine unless explicitly discussing prior naming.

**Risks accepted:**
- Some existing historical ADR tags or planning text may still contain Taste Engine until migrated.
- Longer terminology may need careful UI copy to stay compact.

## Guard Rails

> ⚠️ Do not introduce new implementation artifacts named TasteEngine, TasteSignal, TasteOutcome, or TasteObjection for this v11 layer unless explicitly documenting historical compatibility.

> ⚠️ Do not reinterpret the rebrand as a scope expansion; Adaptive Future Engine remains advisory and subordinate to accepted ADRs, API surface, workflows, and graph evidence.

> ⚠️ Do not use Adaptive Future Engine as a hard enforcement mechanism without a separate reviewed ADR.
