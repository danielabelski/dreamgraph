# ADR-157: ToolOutcome is the single normalized event for every tool invocation regardless of provider, tier, or kind

**Date:** 2026-05-09T21:30:18.840Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/execution/outcome.ts, extensions/vscode/src/architect-v2/autonomy/task.ts  

## Context

v1 had several result shapes: `LocalToolResult`, `McpToolCallResult`, `StructuredPassEnvelope`, ad-hoc shell objects. Cards, autonomy, and verification each parsed each shape with provider-specific branches. The user directive at Slice 4 kickoff was explicit: 'all tool results are normalized regardless of the provider.'

**Constraints:**
- Provider-specific result shapes must be normalized AT the dispatcher boundary, never leak past it.
- `ArtifactRef` shape must match what Slice 3 `TaskState.artifacts` consumes (no-progress detection depends on artifact hash equality).
- Verification operations must be expressible without a separate event type — they're `success` outcomes carrying `evidence`.

## Decision

Every tool invocation \u2014 MCP, VS Code, shell, regardless of provider \u2014 produces exactly one `ToolOutcome` value: a discriminated union of `success`, `failure`, or `partial`. Every variant carries `tool`, `tier`, `intent`, `executedAtEpochMs`, `durationMs`. `success` and `partial` carry `artifacts: ArtifactRef[]`; `success` may carry `evidence: VerificationEvidence` when the operation IS a verification step. `failure` carries `failureReason`, `recoverable`, optional `suggestedFallbackTier`. Constructors validate base fields. Cards, the autonomy decision engine, and the verification harness all consume this exact shape.

### Alternatives Considered

- **Per-provider result types with a thin shared base** — Rejected: Forces every consumer (cards, autonomy, verification) to discriminate by provider before reading the result. Inverts the directive 'normalized regardless of the provider'.
- **Free-form result envelope (e.g. `{ raw: unknown }`)** — Rejected: Pushes parsing onto every consumer. v1's `StructuredPassEnvelope` parsing tangle was caused by exactly this pattern.
- **Add a fourth `kind: 'cancelled'`** — Rejected: Cancellation is a `failure` with a specific reason; modeling it as its own kind would force every consumer to handle four cases instead of three.

## Consequences

- Slice 5 cards render `ToolOutcome` directly without provider switches.
- Slice 7 verification harness reads `evidence` from any tool, not just from a dedicated verify path — 'every code change should attempt relevant verification' from foundation §Verification becomes a one-line lookup.
- Provider adapters become strictly boundary-layer concerns; no part of v2 outside the adapter knows what provider produced an outcome.
- The autonomy `no_progress` detector compares `artifacts` arrays directly; provider differences are invisible to it.

**Risks accepted:**
- Some MCP tool results carry rich nested data that doesn't fit cleanly into `ArtifactRef[]`. Mitigation: the dispatcher boundary is responsible for projection — it may need per-tool projection logic, but that complexity stays bounded to one place.
- `recoverable: boolean` is a coarse classification; some failures are conditionally recoverable. Mitigation: `failureReason` carries the detail; `recoverable` is the orchestrator's hint only.
- If a tool produces no artifacts and no evidence, it looks indistinguishable from a no-op. Intentional — the no-progress detector treats it as such.

## Guard Rails

> ⚠️ Do not extend `ToolOutcome` with provider-specific fields. Provider details belong in the dispatcher boundary.

> ⚠️ Do not add a fourth top-level `kind`; cancellation, timeout, etc. are `failure` reasons.

> ⚠️ Do not let consumers branch on `tool` strings to extract custom data — use `artifacts` and `evidence`.

> ⚠️ Do not bypass the constructors (`success()`, `failure()`, `partial()`); they enforce base-field invariants.
