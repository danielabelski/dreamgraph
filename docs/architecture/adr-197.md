# ADR-197: Provider-safe plugin tool names and native-source discovery

**Date:** 2026-05-17T03:15:34.813Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/plugins/manager.ts, packages/host/src/gates.ts, packages/sdk/src/manifest.ts, src/tools/scan-project.ts, src/tools/init-graph.ts  

## Context

Dotted plugin tool names such as examples.hello-events.greet can pass DreamGraph plugin gates but are rejected by LLM providers that require tool names to match ^[a-zA-Z0-9_-]+$. Separately, bootstrap/scan can no-op on C/C++ projects because native source extensions are absent from scanner extension allow-lists.

**Constraints:**
- Provider-facing tool names must match ^[a-zA-Z0-9_-]+$ and therefore cannot contain dots.
- Plugin contribution gates must reject invalid tool names before tools enter MCP/provider catalogs.
- The rule must be applied consistently in daemon manager, host gates, SDK manifest validation, and examples/tests.
- Scanner discovery must include common C/C++ source/header extensions without weakening existing language support.

## Decision

Use provider-safe plugin tool identifiers at the plugin boundary: derive plugin prefixes by replacing non [a-zA-Z0-9_-] characters with underscores and require every registered tool name to match the provider-safe pattern. Add C/C++ source and header extensions to scan/bootstrap allow-lists.

### Alternatives Considered

- **Sanitize tool names only immediately before provider calls** — Rejected: It creates mismatches between plugin manifests, host gates, MCP catalogs, and execution dispatch.
- **Continue accepting dotted plugin names internally** — Rejected: Invalid names can still leak into provider tool catalogs and break assistant requests before execution.
- **Rely on manual target overrides for C++ projects** — Rejected: Bootstrap/scan should work for common C++ repositories without requiring users to know internal extension filters.

## Consequences

- Invalid dotted plugin tool names are rejected early with actionable errors.
- Provider tool registration no longer fails due to plugin-contributed dotted names.
- Plugin authors use sanitized prefixes such as examples_hello-events_greet or examples_hello_events_greet instead of examples.hello-events.greet.
- OpenRCT2-style C/C++ projects are discoverable by default during scan/bootstrap.

**Risks accepted:**
- Existing plugins using old dotted tool names must update manifests.
- If execution dispatch assumes dotted names elsewhere, those call paths must be migrated to sanitized names.
- Naive extension expansion may increase scan volume on large native repositories.

## Guard Rails

> ⚠️ Add or keep tests asserting no registered/contributed tool name contains dots or violates ^[a-zA-Z0-9_-]+$.

> ⚠️ Keep plugin-id to tool-prefix derivation deterministic and shared between host/daemon validation paths.

> ⚠️ Run targeted plugin gate/manifest tests plus build after patching.

> ⚠️ If scan volume becomes excessive, add explicit caps or ignore rules rather than removing C++ extension support.
