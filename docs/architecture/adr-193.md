# ADR-193: Keep Architect core normalized while classifying MCP tools by authority

**Date:** 2026-05-14T09:04:52.206Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** ArchitectRunRequest, ArchitectRunResult, ArchitectPassEnvelope, CliAgentAdapter, DreamGraph MCP server, codex-cli, copilot-cli, claude-cli, OpenAI API adapter, Anthropic API adapter, ChatGPT manual bridge, Claude manual bridge  

## Context

CLI agents such as Codex CLI, Copilot CLI, and Claude CLI can be configured with MCP servers and generic/provider tools. Architect needs to use DreamGraph tools as authoritative system capabilities without letting provider-native inline tools or arbitrary MCP tools redefine Architect core contracts or become untrusted sources of truth.

**Constraints:**
- Architect core may speak only ArchitectRunRequest, ArchitectRunResult, and ArchitectPassEnvelope.
- Provider-specific requests, transcripts, process captures, MCP configs, and tool outputs must remain adapter-private until normalized.
- DreamGraph tools may be exposed to CLI agents via MCP, but their outputs must still be policy-checked and normalized before Architect core consumes them.
- Generic MCP tools and provider inline tools may be useful for context or local actions, but they must not be treated as authoritative DreamGraph facts unless revalidated by DreamGraph.
- CLI implementations differ: Copilot CLI uses ~/.copilot/mcp-config.json and per-server tools allowlists; Codex CLI uses ~/.codex/config.toml / project config with mcp_servers allowlists, required flags, timeouts, and sandbox/approval controls; Claude CLI/Claude Code MCP support must be handled through its own adapter policy.

## Decision

Classify MCP/tool access into authority tiers. DreamGraph-authoritative MCP tools are the only tool outputs that can become authoritative Architect evidence, and only after adapter readiness checks, allowlist verification, transcript capture, and normalization into ArchitectRunResult. Generic MCP tools and provider inline tools are treated as contextual or action-producing provider-local capabilities; their outputs can be quoted in adapter evidence but cannot mutate Architect state or satisfy authoritative graph/tool requirements unless revalidated through DreamGraph. Architect core remains provider-agnostic and receives only ArchitectRunRequest, ArchitectRunResult, and ArchitectPassEnvelope.

### Alternatives Considered

- **Let each CLI expose arbitrary MCP and inline tools directly to Architect core.** — Rejected: This would couple Architect to provider-specific tool semantics and allow untrusted/generic tools to become de facto authoritative.
- **Disable all MCP support for CLI agents.** — Rejected: This wastes the strongest integration path for giving subscription/CLI agents controlled DreamGraph context and tool access.
- **Treat all MCP servers equally if configured by the user.** — Rejected: User configuration alone does not establish authority, provenance, normalization, or compatibility with Architect contracts.

## Consequences

- Adapters must generate or validate CLI-specific MCP configuration before authoritative runs.
- Adapters must capture MCP/tool transcripts sufficient for audit and normalization.
- Routing can fail closed when an authoritative DreamGraph operation is requested but the CLI adapter cannot prove DreamGraph MCP tools are available under policy.
- Provider inline tools remain useful but are never considered a substitute for DreamGraph-authoritative MCP tools.
- The same ArchitectRunResult contract can represent manual bridge, CLI, and API outputs without changing Architect core.

**Risks accepted:**
- CLI MCP configuration formats and flags may change across versions.
- Some CLIs may not support run-scoped MCP config cleanly, requiring profile isolation or temporary config directories.
- Generic MCP/tool output can still influence model text unless prompts and adapters label authority boundaries clearly.
- Provider CLIs may auto-select tools, making strict transcript capture and tool allowlists important.

## Guard Rails

> ⚠️ Do not add provider-specific request/result types to Architect core.

> ⚠️ Do not treat generic MCP or provider inline tool output as authoritative DreamGraph facts without revalidation.

> ⚠️ Do not route authoritative Architect operations to a CLI adapter unless DreamGraph MCP readiness and allowlists pass.

> ⚠️ Keep CLI process captures, MCP configs, and provider-native transcripts adapter-private except as normalized evidence fields in ArchitectRunResult.

> ⚠️ Prefer fail-closed behavior for missing or ambiguous MCP authority configuration.
