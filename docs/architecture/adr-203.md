# ADR-203: LLM-enabled tools use connected model, daemon model, then deterministic fallback

**Date:** 2026-05-23T03:00:54.463Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/cognitive/intervention.ts, src/cognitive/llm.ts, feature_cognitive_intervention, feature_taste_engine, tool_get_remediation_plan, plans/V11_TASTE_ENGINE_PLAN.md  

## Context

LLM-enabled tools need a consistent model-selection order so remediation drafting and future Taste Engine features behave predictably across Architect-connected, external LLM, daemon-only, and no-LLM contexts.

**Constraints:**
- Connected Architect or external LLM contexts may already provide the best task-local model and should be used when present.
- Daemon-side operation must still work outside interactive Architect contexts when dreamer or normalizer LLM configuration exists.
- Tools must remain usable without any LLM provider by preserving deterministic behavior.
- LLM output must remain evidence-bounded, schema-validated, and compatible with existing governance.
- Daemon-side LLM temperature may vary by task because drafting, normalization, and repair planning have different creativity requirements.

## Decision

All LLM-enabled DreamGraph tools must select models in this order: first use the connected interactive model supplied by Architect, an external LLM, or caller context; second use the configured daemon-side LLM, choosing the appropriate dreamer or normalizer model and task-appropriate temperature; third fall back to the deterministic implementation when no LLM layer is available or validated LLM output fails.

### Alternatives Considered

- **Always use daemon-side LLM configuration for tool generation** — Rejected: This ignores richer connected Architect or external LLM contexts that may already carry the task model, user intent, and conversation-local constraints.
- **Always use the connected Architect or external model and fail without it** — Rejected: Daemon-side tools must remain useful in scheduled, headless, and non-interactive contexts.
- **Replace deterministic implementations entirely once LLM drafting exists** — Rejected: DreamGraph needs reliable no-provider operation and a validation fallback for malformed, unavailable, or low-confidence LLM output.

## Consequences

- Remediation LLM drafting will work in interactive Architect contexts, daemon-only contexts, and no-LLM contexts without changing the public get_remediation_plan contract.
- Future LLM-enabled tools will share one predictable provider precedence rule instead of inventing per-tool routing.
- Daemon-side tools can choose task-appropriate temperature while staying within strict schema validation and graph-governed evidence boundaries.
- Observability can report which model layer was selected and why fallback occurred.

**Risks accepted:**
- Connected model behavior may vary across adapters unless the schema and validation layer stay strict.
- Daemon-side temperature flexibility can make outputs less reproducible if task defaults are not documented.
- Maintaining deterministic fallbacks increases implementation surface area but preserves reliability.

## Guard Rails

> ⚠️ Do not make daemon-side LLM the first choice when a connected Architect, external LLM, or caller-supplied model context is available for the same LLM-enabled tool invocation.

> ⚠️ Do not fail an LLM-enabled tool solely because no LLM is configured when a deterministic fallback exists.

> ⚠️ Do not surface LLM-generated tool output until it passes the tool's schema, evidence, governance, and safety validation.

> ⚠️ Do not hard-code one daemon-side temperature for all LLM-enabled tools; choose temperature per task and document defaults where behavior matters.

> ⚠️ Do not remove existing deterministic behavior from an LLM-enabled tool without recording a replacement ADR.
