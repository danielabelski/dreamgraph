# ADR-153: Dual budget model: PassBudget (required) + TimeBudget (defaulted per mode); both visible, both bounded, no uncapped runs

**Date:** 2026-05-09T21:18:40.396Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/autonomy/budget.ts, extensions/vscode/src/architect-v2/autonomy/task.ts, extensions/vscode/src/architect-v2/autonomy/decision.ts, extensions/vscode/src/architect-v2/autonomy/modes.ts  

## Context

v1's pass budget was optional \u2014 `0` or `undefined` meant uncapped \u2014 and there was no wall-clock bound at all. A pass that called a slow LLM could hang indefinitely; a model that issued many small operations could blow through resources without ever tripping a counter. The Slice 3 directive was explicit: prevent both failure modes by construction.

**Constraints:**
- v1's optional `totalAuthorizedPasses` (where 0 / undefined meant 'uncapped') is rejected as unsafe — the user directive at Slice 3 kickoff explicitly required dual bounded budgets.
- Counters must remain visible during runs (Slice 3 carry-over: 'visible counters as a product requirement').
- The decision engine must be able to detect exhaustion without performing I/O — it is given `nowEpochMs` as an input.
- Both budgets must be constructible without I/O so they can be created in tests.

## Decision

Every Architect v2 autonomous run is bounded by BOTH a `PassBudget` AND a `TimeBudget`. `PassBudget.total` is REQUIRED on every run \u2014 there is no uncapped mode. `TimeBudget.totalMs` is defaulted per `ModeProfile.defaultTimeBudgetMs` and overrideable per run. The decision engine stops on whichever exhausts first, returning `{ kind: 'stop', condition: 'pass_budget_exhausted' }` or `{ kind: 'stop', condition: 'time_budget_exhausted' }` respectively. Both budgets expose `total` / `used` / `remaining` so the UI can display live counters at all times. `createPassBudget(0)` and `createPassBudget(NaN)` throw \u2014 there is no way to construct an unbounded run.

### Alternatives Considered

- **Pass budget only (v1 model)** — Rejected: Does not bound long-running stalls — a single pass that hangs on a slow provider call can run indefinitely while consuming zero budget. v1 had no defense against this.
- **Time budget only** — Rejected: Doesn't bound runaway tool-call loops within a single time window. Wall-clock alone allows pathological retry storms.
- **Optional budgets with sensible defaults** — Rejected: Optional means default-on which means users may not realize a long-running task is bounded; explicit-required matches the safety posture this rewrite is trying to establish.

## Consequences

- Infinite loops and long stalls are structurally precluded — the decision engine cannot return `{ kind: 'continue' }` past either budget.
- UI always has both counters available via `deriveBudgetView()`.
- Slow-provider degradation surfaces as `time_budget_exhausted` rather than as a hung session.
- Settings UI must prompt for or validate a pass-budget integer at run start — there is no 'just keep going' option.

**Risks accepted:**
- Forcing a pass budget on every run adds a UX step (or a settings default lookup) that didn't exist in v1. Mitigation: each `ModeProfile` carries a `defaultPassBudget` that the orchestrator can apply silently.
- Wall-clock budgets in untrusted/sandboxed clocks (clock skew, suspended laptops) may produce unexpected exhaustion. Mitigation: the engine takes `nowEpochMs` as a pure input; clock-source policy is a Slice 5+ concern.
- Tight default time budgets on slow providers (e.g. local Ollama on a laptop CPU) may exhaust before the pass budget. Mitigation: `cautious=2min` and `conscientious=5min` defaults can be widened per-run by the caller.

## Guard Rails

> ⚠️ Do not add a code path that bypasses `PassBudget.remaining <= 0` or `isTimeBudgetExhausted()` checks in `deriveNextAction`.

> ⚠️ Do not introduce an 'unbounded' `PassBudget` constructor or default.

> ⚠️ Do not let `PassBudget` mutate — use `consumePass()` to derive the next budget.

> ⚠️ Do not call `Date.now()` inside `architect-v2/autonomy/`; accept `nowEpochMs` as input for testability.
