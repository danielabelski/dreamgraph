# ADR-228: Standalone Architect Doom tab is a host-owned local-convenience emulator surface

**Date:** 2026-05-31T19:14:21.143Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** standalone-architect, src/architect/routes.ts, package.json, package-lock.json, plans/doom-tab.md, architectTabTypeRegistry, feature_plugin_sdk, src/plugins/architect-contributions.ts, /api/architect/v1/assets/js-dos/*  

## Context

Running Doom inside a standalone Architect tab requires executable browser emulator code and game content handling. The existing Architect plugin-tab contract intentionally permits only declarative host-rendered projections and forbids iframe, arbitrary-script, remote-script, inline-script, and browser-plugin-module escape hatches. The feature also must not turn gameplay state or proprietary Doom assets into DreamGraph authority or packaged project content.

**Constraints:**
- ADR-206 keeps standalone Architect daemon-authoritative and plan-centered; entertainment surfaces cannot gain filesystem, graph, mutation, or execution authority.
- ADR-208 and ADR-210 require daemon-served versioned Architect contracts and local daemon-served browser asset delivery.
- ADR-224 keeps Architect plugin tabs declarative and host-rendered and forbids executable browser escape hatches.
- ADR-222 and ADR-223 establish the relevant local-convenience precedent: bounded browser runtime behavior is allowed when it remains outside repository evidence and cleans up lifecycle resources.
- id Software's GPL Doom source release does not include or authorize casual redistribution of proprietary Doom game data.
- js-dos can run DOS bundles in-browser but its GPL-2.0 package and any demo content require redistribution review before packaging.

## Decision

Implement the standalone Architect Doom tab as an explicit host-owned built-in dynamic tab, parallel to terminal and code-editor tabs. Use locally served emulator assets under the versioned Architect daemon asset namespace, with js-dos v8 as the preferred spike dependency. Do not implement Doom through plugin-tab iframe, arbitrary HTML, remote scripts, inline scripts, or executable browser plugin modules. Keep gameplay and save state outside DreamGraph plan, graph, repository, runtime-identity, and MCP authority. Ship no proprietary Doom IWAD or executable data. Authentic Doom content is user-provided locally. A clearly labelled Freedoom demo bundle may ship only after compatibility, provenance, license-notice, and redistribution review.

### Alternatives Considered

- **Embed a DOS.Zone or other remote iframe** — Rejected: It conflicts with the reviewed local-first Architect browser boundary, depends on remote execution/content, and would create an iframe escape hatch.
- **Expose Doom as an executable Architect plugin tab** — Rejected: ADR-224 intentionally limits plugin tabs to declarative host-rendered projections and excludes executable browser plugin code.
- **Bundle proprietary Doom IWADs or DOS executables with DreamGraph** — Rejected: The open engine source does not authorize redistribution of proprietary game data.
- **Start with a custom Doom source port compiled to WebAssembly** — Rejected: It remains a valid fallback but adds source-port selection, build, audio, input, filesystem, packaging, and content-policy work before validating the simpler js-dos path.

## Consequences

- DreamGraph can add an explicit recreational Doom tab without weakening plugin-tab security or repository authority.
- The first implementation can validate browser gameplay quickly with js-dos while retaining an offline daemon-served asset model.
- Authentic Doom content remains a user-local responsibility and proprietary data does not enter packaged artifacts or the graph.
- A later daemon-owned game library or executable plugin UI model requires separate ADR review.

**Risks accepted:**
- js-dos and emulator assets increase packaged size and may impose GPL distribution obligations that must be satisfied before release.
- Browser keyboard capture, audio permission, worker lifecycle, hidden-tab CPU use, and multi-tab cleanup need explicit verification.
- Freedoom compatibility and notice handling must be verified before a demo bundle ships.
- Keeping the initial implementation in src/architect/routes.ts may increase route-file complexity and justify extraction.

## Guard Rails

> ⚠️ Do not implement the Doom runtime through Architect plugin-tab iframes, arbitrary HTML, remote scripts, inline scripts, executable browser modules, or direct plugin DOM callbacks.

> ⚠️ Do not fetch required emulator scripts, WASM, workers, or game bundles from a CDN or remote DOS portal in the shipped local-first path.

> ⚠️ Do not commit, package, or serve proprietary Doom IWADs or executables without explicit legal approval.

> ⚠️ Do not treat gameplay frames, emulator logs, save files, screenshots, or imported bundles as DreamGraph repository facts, MCP evidence, plan state, graph state, or runtime identity.

> ⚠️ Do not persist recreational save state through Architect plugin plan state or scan it into the graph.

> ⚠️ Do not ship a Freedoom demo until compatibility, provenance, redistribution terms, and required notices are verified.

> ⚠️ Do not leave emulator workers, audio, listeners, object URLs, or hidden-tab CPU activity alive after tab teardown.
