# ADR-206: Standalone Architect migration is plan-centered and daemon-authoritative

**Date:** 2026-05-27T18:56:26.775Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** plans/STANDALONE_ARCHITECT_MIGRATION_PLAN.md, standalone-architect, DreamGraph daemon web surface, DreamGraph Explorer, Architect ChatPanel, Adaptive Future Engine, scheduler tool group, ADR-142, ADR-144, ADR-171, ADR-173, ADR-087, ADR-192, ADR-203, ADR-204, ADR-205  

## Context

The standalone Architect migration needs a DreamGraph-specific implementation plan rather than a generic browser IDE plan. The plan must bind to accepted ADRs, preserve graph-first/daemon-authoritative practices, and clarify how plans, ADRs, AFE, scheduler operations, and governed mutations become standalone browser workflows.

**Constraints:**
- DreamGraph remains local-first and daemon-authoritative; browser clients do not gain direct filesystem or graph mutation authority.
- Accepted ADRs for tool priority, Explorer consistency/mutation safety, task/card persistence, context authority, AFE advisory semantics, product vocabulary, and VS Code canonicality remain binding.
- Current VS Code V1 hybrid ChatPanel remains the canonical extension surface until a superseding ADR changes that boundary.
- Implementation planning must follow ADR-142: Markdown plan for human narrative and ADR mirror for machine-readable graph reasoning.
- Standalone Architect should become a graph-grounded implementation orchestrator centered on explicit plans, not a generic AI IDE or editor-first chat surface.

## Decision

Adopt the revised plans/STANDALONE_ARCHITECT_MIGRATION_PLAN.md as the narrative implementation plan for migrating Architect into a standalone daemon-served browser control plane. The plan makes implementation plans first-class working objects, binds work to accepted ADR guard rails, routes execution and mutations through daemon/MCP governance, reuses Explorer-style snapshot/SSE/mutation safety semantics, surfaces AFE and scheduler operations as DreamGraph-native plan workflows, and keeps VS Code as a companion/escape-hatch surface until an explicit cutover ADR supersedes the current canonical VS Code decision.

### Alternatives Considered

- **Treat standalone Architect as a generic browser IDE with direct file/editor operations** — Rejected: This would violate DreamGraph's daemon-authoritative, graph-first, curated mutation, and audit/governance model.
- **Only move the existing VS Code chat UI into a browser shell** — Rejected: That would preserve chat as the primary abstraction and miss the core DreamGraph realization that plans are the primary operational object.
- **Implement browser mutation endpoints before locking ADR bindings and safety model** — Rejected: Mutation authority is the most sensitive boundary; Explorer and tool-priority ADRs require curated, audited, authenticated daemon-mediated flows.
- **Replace VS Code immediately during standalone work** — Rejected: ADR-192 keeps the V1 hybrid VS Code ChatPanel as the canonical extension surface until a superseding ADR/cutover is recorded.

## Consequences

- Future standalone Architect work has a DreamGraph-specific implementation roadmap with phases, API/data ownership assumptions, guard rails, and verification criteria.
- Plan work can be queried by the graph through this ADR while the Markdown file remains the human-readable narrative source.
- Implementation slices will start from daemon API skeleton, plan registry/graph binding, SPA shell, execution trace projection, mutation review, AFE/scheduler integration, VS Code compatibility, and release hardening.
- Reviewers can check proposed standalone changes against explicit ADR bindings before code is written.

**Risks accepted:**
- The plan is still pre-implementation and exact endpoint/type names may change during design.
- Some existing Explorer/Architect internals may not map cleanly to the proposed phased boundaries without adapter work.
- Additional ADRs are still required for concrete API contracts, persistence schema, mutation review semantics, and VS Code cutover behavior.

## Guard Rails

> ⚠️ Do not implement standalone browser filesystem writes or arbitrary graph mutations; route through daemon-governed intents and MCP tools.

> ⚠️ Do not bypass the established MCP-first tool priority or omit fallback justifications in standalone execution flows.

> ⚠️ Do not make AFE a hard enforcement mechanism without a new ADR; keep it advisory and subordinate to accepted ADR/API/workflow constraints.

> ⚠️ Do not activate or deprecate VS Code Architect paths without a superseding ADR that addresses ADR-192.

> ⚠️ Do not start implementation slices that change architecture boundaries without updating both the Markdown plan and ADR mirror per ADR-142.
