# ADR-225: Architect plugin plan state is daemon-owned, namespaced, and action-mediated

**Date:** 2026-05-31T15:28:29.380Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** feature_plugin_sdk, standalone-architect, architect-plan-registry-projection, src/plugins/architect-plan-state.ts, src/plugins/architect-contributions.ts  

## Context

Architect plugin tabs need durable plan-bound state such as checklist items without making browser storage, selected-plan inference, or plan markdown a second authority.

**Constraints:**
- Plan-bound reads and writes require explicit planId.
- Plan state is persisted under daemon-owned instance data.
- Writes must pass capability, effect, schema, plan existence, and revision checks.
- Unload must remove active behavior while preserving persisted user state.

## Decision

Persist Architect plugin state per instance, plugin id, plan id, tab type id, and key in a daemon-owned JSON store using atomic writes and locking. Reads return immutable snapshots with revision tokens. Writes occur only through registered host-side plugin action handlers after capability, effect, schema, explicit plan existence, and revision checks. Project-scope summaries are exposed only when explicitly declared and never silently bind to a selected plan.

### Alternatives Considered

- **Use browser localStorage as checklist authority** — Rejected: Browser-local state would diverge across reloads and clients and bypass daemon governance.
- **Write checklist toggles directly into plan markdown** — Rejected: The initial slice needs namespaced operational plugin state, not implicit mutation of governed plan documents.
- **Infer a target from the selected or first plan** — Rejected: No selected plan is a valid state and implicit plan targeting violates plan-scope separation.

## Consequences

- Checklist state survives browser reload and plugin unload/reload.
- State is isolated across plugins, plans, tabs, and keys.
- Stale concurrent writes fail explicitly.

**Risks accepted:**
- A persistent store adds locking and migration concerns.
- Plugins may need clear handling for missing plans and stale revisions.

## Guard Rails

> ⚠️ Do not make browser localStorage authoritative for Architect plugin state, badges, or sidebar summaries.

> ⚠️ Do not write checklist toggles directly into plan markdown in the initial implementation.

> ⚠️ Do not target an implicit first plan or stale selected plan.

> ⚠️ Do not delete persisted Architect plugin state during normal unload or reload.
