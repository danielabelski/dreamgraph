# ADR-208: Standalone Architect API uses a versioned daemon-governed /api/architect contract

**Date:** 2026-05-27T20:13:34.193Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** standalone-architect, DreamGraph daemon web surface, /architect, /api/architect/plans, /api/architect/runs, /api/architect/events, plan records, run records, review gates, ADR-087, ADR-206  

## Context

The standalone Architect migration needs a concrete API boundary before implementation begins. Without an explicit ADR, route naming, plan/run payloads, event streaming, and execution authority could drift between browser, daemon, and VS Code surfaces.

**Constraints:**
- Standalone Architect is daemon-authoritative per ADR-206; the browser issues governed intents and does not gain direct filesystem or graph mutation authority.
- Explorer consistency and mutation-safety semantics from ADR-087 remain binding: snapshot-first reads, live events, replay-gap recovery, curated mutation endpoints, audit context, and optimistic concurrency where applicable.
- The API must support plan listing, plan detail, run/task visibility, review-gate decisions, and live updates without making exact v0 field names prematurely rigid.
- Future endpoint names may evolve, but the versioned namespace and governed-intent boundary must stay stable.

## Decision

Lock the standalone Architect transport boundary to a daemon-served, versioned `/api/architect/*` contract plus the `/architect` app shell. The browser may list plans, inspect a plan with graph bindings, trigger governed slice/gate intents, inspect run/pass/task state, and subscribe to an Architect event stream, but it does so only through daemon-owned contracts that preserve Explorer-style snapshot/event consistency and governed mutation semantics.

### Alternatives Considered

- **Expose standalone Architect through ad hoc unversioned daemon routes and payloads** — Rejected: This weakens forward-compatibility and makes browser/daemon contracts drift-prone during phased implementation.
- **Let the browser call existing lower-level tools or filesystem-like routes directly** — Rejected: This violates the daemon-governed intent boundary and would bypass audit and mutation safety expectations.
- **Postpone the contract decision until after UI work begins** — Rejected: That would allow early implementation slices to hard-code unstable route and event assumptions.

## Consequences

- Phase 1 can implement an API skeleton without re-opening the authority boundary.
- Browser and VS Code companion surfaces can converge on one plan/run contract instead of inventing separate orchestration APIs.
- Replay-gap, stale-state, and audit behaviors inherit established Explorer-style expectations rather than becoming implicit UI behavior.

**Risks accepted:**
- Early field choices may still require additive evolution as implementation clarifies run and review payloads.
- Some Explorer semantics may need adapter shaping for plan/run concepts rather than graph-only concepts.

## Guard Rails

> ⚠️ Do not add standalone Architect endpoints outside a versioned `/api/architect` namespace unless they are static asset routes for `/architect` itself.

> ⚠️ Do not let browser clients bypass daemon-governed intents for plan execution, review gates, or mutations.

> ⚠️ Do not treat the live event stream as authoritative without snapshot/bootstrap and replay-gap recovery behavior.

> ⚠️ Do not make exact route names or payload fields a reason to violate the stable authority boundary established here.
