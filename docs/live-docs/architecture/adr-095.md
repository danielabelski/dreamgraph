# ADR-095: Lazy-Created JSON-Backed Resources Bootstrap Empty and Degrade Gracefully on ENOENT

**Date:** 2026-04-29T20:55:14.775Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** system://datastores, query_resource, datastore-bootstrap  

## Context

Some registered DreamGraph resources are backed by JSON files that may not exist yet during bootstrap or in intentionally inert configurations. Clients should see stable resource semantics instead of bootstrap-state failures such as ENOENT or INVALID_URI when the resource is known but its backing file has not been created yet.

**Constraints:**
- Registered resource URIs must remain stable regardless of whether their backing JSON file has been created yet.
- Instance data storage is authoritative for ADRs and resource backing state; workspace files are not the ADR source of truth.
- The datastore bootstrap path is intentionally inert when no DATABASE_URL is configured, but the resource surface should still be queryable.
- Client-facing query semantics should hide expected bootstrap absence while still preserving explicit invalid-resource errors for unknown URIs.
- The solution should align tool behavior and bootstrap behavior so file-on-disk truth converges with resource-registration truth.

## Decision

Adopt a two-part policy for lazy-created JSON-backed resources: (1) bootstrap creates known backing files in an empty canonical state where appropriate, such as datastores.json initialized to []; and (2) resource-query tooling treats ENOENT for known registered JSON-backed resources as an empty resource instead of surfacing an internal error. Unknown resource URIs must still return INVALID_URI.

### Alternatives Considered

- **Surface ENOENT to clients for missing backing files** — Rejected: This leaks expected bootstrap state into the client contract and makes a registered resource appear broken during inert or first-run states.
- **Bootstrap empty files only, with no tool-level ENOENT degradation** — Rejected: This leaves clients exposed to runtime failures when older instances or partial deployments lack the expected seed file.
- **Tool-level graceful degradation only, without creating empty files during bootstrap** — Rejected: This keeps behavior stable for clients but allows file-on-disk truth to diverge from resource-registration truth longer than necessary.

## Consequences

- Known JSON-backed resources can be queried safely before any substantive configuration exists.
- The no-database-configured case returns an empty datastore list instead of an internal error.
- Bootstrap semantics become more predictable because known empty resources have canonical on-disk representations.
- Operational debugging remains clear because unknown URIs still fail explicitly with INVALID_URI.

**Risks accepted:**
- Graceful ENOENT degradation may hide some genuine deployment mistakes for known resources if operators expect the file to exist already.
- Creating empty backing files during bootstrap introduces small amounts of inert instance data for users who never configure those resources.

## Guard Rails

> ⚠️ Do NOT return INTERNAL_ERROR for ENOENT when querying a known registered JSON-backed resource that is allowed to start empty; return the canonical empty shape instead.

> ⚠️ Do NOT treat unknown resource URIs as empty resources; they must continue to fail explicitly as INVALID_URI.

> ⚠️ Do NOT rely on workspace ADR files as the source of truth for this decision; the daemon instance ADR store is authoritative.

> ⚠️ Do NOT remove bootstrap creation of canonical empty backing files for lazy-created resources without revisiting this ADR.
