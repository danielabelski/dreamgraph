# ADR-135: SDK host loader discovers declared ESM plugins only from instance roots and keeps runtime loading out of M1

**Date:** 2026-05-08T17:42:31.154Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** packages/host, packages/sdk, plans/DREAMGRAPH_SDK_ROADMAP.md, docs/sdk/host-loading-model.md  

## Context

The SDK roadmap needs a stable host loading model before plugin APIs become public. Without an explicit discovery and module-loading rule, plugin authors and daemon code could depend on accidental paths, CJS/ESM behavior, or early runtime loading semantics that are hard to revoke.

**Constraints:**
- M1 must ship SDK and host package skeletons without runtime plugin loading.
- DreamGraph is a type=module Node project, so ESM should be the default module format.
- Plugin discovery must be instance-admin controlled, not implicit global scanning.
- Version skew must be handled through manifest engine.dreamgraph ranges before any plugin code executes.
- In-process execution is trusted-only until later worker isolation hardening.

## Decision

Use an explicit host loading model: discover plugins only from <instance>/plugins/*/plugin.json and packages listed in instance.json plugins; target ESM modules as the supported plugin format; validate plugin.json and engine.dreamgraph before importing plugin code; keep @dreamgraph/host in M1 as a schema/contract package with no runtime plugin execution; defer in-process loading to the trusted M3 model behind the host safety switch.

### Alternatives Considered

- **Scan all node_modules packages matching dreamgraph-plugin-* automatically** — Rejected: Implicit scanning expands trust and supply-chain risk and conflicts with instance-admin control.
- **Support CJS and ESM equally from day one** — Rejected: Dual loader semantics create packaging ambiguity before the SDK surface is stable.
- **Implement runtime plugin loading in M1** — Rejected: M1 is intentionally a skeleton/schema phase; loading before capability gates and audit artifacts are stable would freeze unsafe contracts.

## Consequences

- Plugin installation remains explicit and auditable.
- M1 can validate package shape and manifests without executing third-party code.
- Future M3 loader work has a clear discovery and validation sequence.
- ESM-first package design avoids dual-package hazards in the initial SDK.

**Risks accepted:**
- Some plugin authors may expect automatic npm package discovery.
- CJS-only plugin authors will need migration guidance or a later compatibility decision.
- Host package may appear underpowered until M3 because it intentionally does not load plugins.

## Guard Rails

> ⚠️ Do not add runtime plugin execution to M1.

> ⚠️ Do not discover plugins outside instance-admin declared roots.

> ⚠️ Validate manifest schema and engine.dreamgraph before importing plugin main modules.

> ⚠️ Keep ESM as the default supported plugin module target unless a later ADR supersedes it.

> ⚠️ Do not imply in-process plugin loading is sandboxed before worker isolation exists.
