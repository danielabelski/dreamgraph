# ADR-134: Provider adapters use a hybrid trust model with core presets and signed or allowlisted plugins

**Date:** 2026-05-08T11:23:46.455Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** plans/DREAMGRAPH_SDK_ROADMAP.md, architect-llm, sdk:provider_adapters, provider-adapters:gemini, provider-adapters:openrouter, plugin-sdk:capabilities  

## Context

The SDK roadmap needed to decide how to support provider-specific integrations such as Gemini, OAuth bridges, CLI bridges, and OpenRouter-like providers without contaminating architect-llm or granting unsafe authority to arbitrary plugins.

**Constraints:**
- architect-llm should remain lean and protocol-pure, consuming normalized LLM/MCP surfaces rather than provider-specific quirks.
- Provider adapters may require network access, process execution, OAuth/device-code flows, secrets, retries, and provider-specific error normalization.
- Safe/simple OpenAI-compatible providers can often be represented as core presets without a full plugin adapter.
- Risky adapters must not receive arbitrary network or process authority by default.

## Decision

Use a hybrid provider-adapter model: implement safe/simple providers as core presets; allow risky or complex adapters through signed or allowlisted plugins; never grant arbitrary network or process authority by default. Adapters normalize provider quirks behind a stable LLM/MCP-facing surface so architect-llm stays protocol-pure.

### Alternatives Considered

- **Put Gemini and other provider-specific behavior directly into architect-llm** — Rejected: Would contaminate the architectural reasoning layer with provider-specific request shaping, safety settings, streaming formats, tool-call conversion, auth, and error handling.
- **Allow any plugin to perform arbitrary network or process calls as a provider adapter** — Rejected: Would violate the SDK trust model and expose secrets, operator environment, and process/network authority too broadly.
- **Only support core provider presets and never plugin adapters** — Rejected: Would keep the core safer but limit integration with complex providers whose quirks are better isolated in optional adapters.

## Consequences

- architect-llm can remain focused on normalized protocol semantics.
- Gemini-style integrations can live in adapters that handle provider-specific content parts, tool calls, safety blocks, streaming chunks, model IDs, auth, and errors.
- OpenRouter and other OpenAI-compatible providers can start as core presets where possible.
- Security review can focus on signed or allowlisted adapters for providers requiring elevated authority.

**Risks accepted:**
- The normalized provider contract may be hard to design across Gemini, OpenAI-compatible providers, OAuth-backed services, and CLI bridges.
- Adapter signing and allowlisting infrastructure must be implemented before broad third-party provider adapters are safe.
- Core presets may accumulate too many special cases if not kept strict.

## Guard Rails

> ⚠️ Do not add provider-specific Gemini-style quirks directly to architect-llm without superseding this decision.

> ⚠️ Do not grant provider-adapter plugins arbitrary fetch, socket, shell, or child_process authority by default.

> ⚠️ Require signed or explicitly allowlisted status for risky provider adapters that need network, process, OAuth, or secret-bearing capabilities.

> ⚠️ Keep simple OpenAI-compatible providers as core presets when they do not require new trust boundaries.

> ⚠️ Provider adapters must present normalized LLM/MCP-facing requests, responses, tool-call events, stream events, errors, and capability metadata to core consumers.
