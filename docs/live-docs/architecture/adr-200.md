# ADR-200: Copilot CLI Context Inspector records adapter prompt composition

**Date:** 2026-05-19T20:54:18.790Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/chat-panel.ts, extensions/vscode/src/context-inspector.ts, extensions/vscode/src/architect-core/adapters/copilot-cli/provider-port.ts, extensions/vscode/src/architect-core/adapters/copilot-cli/orchestrator.ts, BudgetCoordinator, ContextBuilder, ContextInspector, copilot-cli, dreamgraph-mcp-bridge  

## Context

Operators need to understand what the Copilot CLI adapter actually sent to the provider and which DreamGraph MCP surface was advertised, especially because repository markdown ADR files were not accurate for the live DreamGraph ADR state. Without adapter-level Context Inspector output, prompt economy and MCP bridging failures are hard to diagnose.

**Constraints:**
- Context Inspector output must be compact enough for routine use but specific enough to diagnose prompt byte size, history volume, MCP advertisement, current-turn isolation, and selected model.
- Diagnostics must not expose secrets or raw full prompt content.
- The adapter must report facts from the actual prompt-composition path rather than stale documentation files.
- BudgetCoordinator structured accounting and Context Inspector plain-line diagnostics may coexist, but they should not contradict each other.
- Provider-specific diagnostic fields must remain behind the adapter/provider boundary unless normalized for shared UI display.

## Decision

Emit Copilot CLI prompt-composition diagnostics to the Context Inspector when the adapter composes a run: serialized prompt byte length, bounded history message count, advertised MCP server name and tool count, current-turn marker status, and model selection. Treat this as adapter provenance for live run diagnosis, while preserving the opportunity to add structured BudgetCoordinator prompt-component accounting separately.

### Alternatives Considered

- **Do not log Copilot CLI prompt composition** — Rejected: Users and maintainers would have no compact evidence of context-economy behavior or MCP bridge advertisement during a run.
- **Dump the full serialized prompt into Context Inspector** — Rejected: That would violate context economy, risk exposing sensitive conversation/source content, and make the inspector noisy.
- **Depend on markdown ADR/docs files for Copilot adapter truth** — Rejected: The user explicitly identified those files as inaccurate for DreamGraph ADR state; the live graph and runtime inspector must be treated as the authoritative surfaces.

## Consequences

- Copilot CLI runs expose compact diagnostics for prompt size, bounded history, MCP advertisement, current-turn isolation, and model selection.
- MCP bridge failures such as missing dreamgraph command/tool advertisement can be diagnosed from live run metadata.
- Context Inspector remains a low-noise operational surface rather than a raw prompt dump.
- Future work can align this plain diagnostic line with shared structured budget summaries without changing the adapter decision.

**Risks accepted:**
- Plain text inspector lines are less queryable than structured budget records.
- If prompt-composition metadata diverges from BudgetCoordinator component accounting, operators may see inconsistent budget narratives.
- Overly detailed diagnostics could accidentally expose provider or workspace internals if expanded without review.

## Guard Rails

> ⚠️ Do not remove Copilot CLI prompt-composition diagnostics from Context Inspector without replacing them with an equally visible structured diagnostic.

> ⚠️ Do not log full serialized prompts, secrets, MCP config contents, or raw tool payloads in this inspector line.

> ⚠️ Do not rely on repository markdown ADR exports as the source of truth for Copilot adapter decisions; use live DreamGraph ADR records.

> ⚠️ Keep provider-specific diagnostic collection adapter-local and expose only normalized/compact facts to shared UI surfaces.
