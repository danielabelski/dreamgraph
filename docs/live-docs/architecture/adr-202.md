# ADR-202: Do not position VS Code Marketplace as the primary DreamGraph distribution channel

**Date:** 2026-05-22T22:24:30.309Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** extensions/vscode, src/cli, src/server, src/cognitive, src/instance, dreamgraph-release-distribution  

## Context

DreamGraph's VS Code extension is only one user-facing surface of a larger installed system. The extension requires the DreamGraph daemon, engine, CLI, instance registry, and MCP-backed graph services to be installed and running. Publishing or promoting the VSIX as a normal standalone VS Code Marketplace extension creates a false installation expectation: users may install the extension without the required runtime and conclude DreamGraph is broken.

**Constraints:**
- The VS Code extension/backend contract is explicit and daemon-dependent per existing accepted ADR guidance.
- DreamGraph is a full local engine/daemon/CLI system, not a standalone editor extension.
- The extension must degrade when backend services are unavailable, but degraded mode is not the intended product experience.
- Distribution messaging must avoid implying that the Marketplace install alone is sufficient.
- The GitHub release artifact can remain useful for manual VSIX installation after the engine/CLI are installed.

## Decision

Treat the VS Code Marketplace as non-primary or inappropriate for DreamGraph's current distribution model unless the Marketplace listing is explicitly framed as a companion extension that requires a separately installed DreamGraph daemon/engine/CLI. Prefer GitHub releases and installer-led distribution where the engine, CLI, daemon, and VSIX are presented as one coherent product installation.

### Alternatives Considered

- **Publish and promote DreamGraph as a normal Marketplace extension** — Rejected: This misrepresents the product boundary. Users can install the extension without the daemon/engine/CLI and encounter a broken or degraded experience.
- **Do not distribute the VSIX at all** — Rejected: The VSIX remains useful as a companion artifact for users who have installed the DreamGraph engine/CLI or are following the full installer flow.
- **Marketplace listing as companion-only with hard prerequisite language** — Rejected: Acceptable only as a secondary channel; still weaker than installer-led distribution because VS Code Marketplace UX encourages extension-first installation.

## Consequences

- Release messaging will emphasize DreamGraph as an engine/daemon/CLI plus VS Code companion experience, not a standalone extension.
- Marketplace publishing work is deprioritized until prerequisite detection/onboarding can make the dependency boundary unmistakable.
- GitHub releases and installer scripts remain the correct primary distribution path for v10.6.x.
- Promotional copy should describe the Architect adapters as user-facing surfaces on top of the DreamGraph engine, not as the product itself.

**Risks accepted:**
- Skipping Marketplace may reduce casual discovery by VS Code users.
- Companion-only Marketplace positioning may still confuse users unless the listing and activation UX are very explicit.
- Installer-led distribution requires better documentation and onboarding polish.

## Guard Rails

> ⚠️ Do not describe the DreamGraph VS Code extension as standalone installable software unless the daemon/engine/CLI prerequisite is stated in the same context.

> ⚠️ Do not make VS Code Marketplace the primary release success criterion for DreamGraph while the extension requires a separate daemon/engine/CLI install.

> ⚠️ Do not publish Marketplace copy that implies the extension alone provides DreamGraph's graph, cognitive engine, CLI, or MCP services.

> ⚠️ If Marketplace publishing resumes, frame it as a companion extension and include hard prerequisite language plus links to the full installer.
