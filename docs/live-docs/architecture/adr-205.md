# ADR-205: Separate DreamGraph product semantics from repository-instance specifics

**Date:** 2026-05-27T16:44:16.633Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** extensions/vscode/src/tool-groups.ts, scheduler tool group, prompt-based tool selection, schedule_dream  

## Context

DreamGraph can be used to assist development of its own repository, but product behavior must remain suitable for arbitrary client projects. Prompt-routing and tool-selection decisions must not treat the DreamGraph repository instance as special evidence that generic DreamGraph product concepts, such as dreams or scheduling, should be avoided or narrowed.

**Constraints:**
- DreamGraph is a general product used across many client instances, not only the DreamGraph source repository.
- When DreamGraph operates on its own repository, that repository is just one client workspace and must not leak project-specific assumptions into product semantics.
- Tool selection should prioritize user intent and product vocabulary over defensive avoidance caused by the current workspace name.
- Changes should keep minimal blast radius by updating prompt/tool-selection policy without changing runtime tool implementations unless needed.

## Decision

Treat DreamGraph product vocabulary, including generic terms like dream, dreaming, schedule, and scheduling, as valid routing signals independent of whether the current workspace is the DreamGraph repository. Do not suppress product-level keywords merely because they may also appear in the product or repository name.

### Alternatives Considered

- **Avoid plain product terms such as dream because they may match DreamGraph in the current repository.** — Rejected: This lets one client workspace contaminate global product behavior and makes users discover exact tool names unnecessarily.
- **Special-case the DreamGraph repository to avoid self-reference.** — Rejected: Special-casing the product repository increases complexity and violates the principle that DreamGraph should behave consistently across client instances.

## Consequences

- Natural prompts using product vocabulary are more likely to attach the correct tools without requiring exact MCP tool names.
- The DreamGraph repository remains just another workspace from the product's perspective.
- Some broad terms may attach scheduler tools more often, but this is acceptable when they are core product vocabulary and only affect tool availability, not automatic execution.

**Risks accepted:**
- Broad keyword matching can increase the number of attached tools for prompts that mention DreamGraph without scheduling intent.
- Future contributors may reintroduce repository-specific assumptions when testing DreamGraph on itself.

## Guard Rails

> ⚠️ Do not use the current repository name or product self-hosting context as a reason to suppress generic product keywords.

> ⚠️ Keep prompt-routing changes advisory: attaching a tool group must not execute tools automatically.

> ⚠️ Prefer focused routing tests that include both generic client projects and the DreamGraph repository as equivalent workspaces.
