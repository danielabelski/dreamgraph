# ADR-233: Chat output follows execution timeline with final report after tool trace

**Date:** 2026-06-08T18:56:40.292Z  
**Status:** accepted  
**Decided by:** human  
**Affected entities:** chat_output_timeline, tool_trace_rendering, final_report_rendering  

## Context

The chat surface was not matching the intended execution chronology: the initial intent statement should appear before tool execution, while the final report must appear only after the tool trace. Additionally, the tool trace container should be visible/unfolded by default, but each individual tool call's detailed payload should remain collapsed by default.

**Constraints:**
- Initial intent/status text must render before any tool trace for the turn.
- The final report/answer must render after the tool trace, preserving the actual execution timeline.
- The tool trace group itself should be expanded/unfolded by default so the user can see that tools ran.
- Individual tool-call detail rows/payloads must remain collapsed by default to avoid noisy output.
- This is a UI/interaction ordering decision and should not be changed without revisiting the human clarification.

## Decision

Render assistant turns in chronological phases: pre-tool intent statement first, then expanded tool-trace summary with each tool line's details collapsed by default, then the post-tool final report.

### Alternatives Considered

- **Place the final report before or around the tool trace** — Rejected: It violates the intended execution timeline and makes the report appear before the evidence/tool execution it summarizes.
- **Collapse the entire tool trace by default** — Rejected: The user explicitly wants the tool trace itself unfolded/visible by default.
- **Expand every individual tool call detail by default** — Rejected: The user explicitly wants each tool line's details to remain collapsed to reduce noise.

## Consequences

- Chat turns communicate intent before work begins, then expose tool execution, then provide the final synthesized result.
- Users can immediately see that tools executed without being overwhelmed by raw per-tool arguments/results.
- Future UI changes have a clear guard rail for timeline ordering and default collapse state.

**Risks accepted:**
- If the renderer cannot distinguish trace container expansion from per-tool detail expansion, implementation may require a small state-model change.
- Streaming implementations must avoid emitting final-report blocks before all tool trace rows have been rendered.

## Guard Rails

> ⚠️ Do not render the final report before the tool trace for tool-using turns.

> ⚠️ Do not default-collapse the entire tool trace when tool calls occurred.

> ⚠️ Do not default-expand individual tool-call details unless the user explicitly requests verbose/debug trace output.

> ⚠️ Preserve chronological order: intent/status → tool trace → final report.
