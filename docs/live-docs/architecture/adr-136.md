# ADR-136: Schedule actions will migrate from a closed union to a guarded registry without changing existing schedule semantics

**Date:** 2026-05-08T17:42:31.180Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** packages/sdk, packages/host, src, plans/DREAMGRAPH_SDK_ROADMAP.md, docs/sdk/schedule-action-registry.md  

## Context

The SDK roadmap requires plugins to eventually register schedule action types, but current schedule behavior depends on known built-in actions, timeout handling, error streaks, and workflow visibility. Opening the action type space without a registry design could break existing schedule semantics or make custom actions unobservable.

**Constraints:**
- Existing built-in schedule semantics must not change during registry migration.
- Timeout and error-streak guards must apply uniformly to built-in and plugin actions.
- system://workflows must continue to expose a stable enumerable surface for operators and tools.
- Plugin actions must be capability-gated and schema-validated.
- M4 implements the seam; M1 should only document and type the eventual contract where needed.

## Decision

Adopt a schedule action registry design in which built-ins are first-class registry entries, plugin actions use open string IDs only through explicit registration, every action declares a zod-validated parameter schema, and the scheduler invokes all action types through the same timeout, error-streak, and observability wrapper. system://workflows lists both built-in and registered plugin action metadata while preserving stable built-in identifiers.

### Alternatives Considered

- **Keep ScheduleAction as a permanently closed union** — Rejected: Prevents the planned plugin schedule action seam.
- **Allow arbitrary string actions without a registry** — Rejected: Breaks validation, observability, and operator trust.
- **Give plugin actions a separate scheduler path** — Rejected: Would bypass or duplicate timeout/error-streak behavior and create inconsistent semantics.

## Consequences

- M4 can open the schedule action seam without bypassing existing protections.
- Built-in actions can migrate incrementally into the registry.
- Operators retain a discoverable action catalog.
- Plugin action failures produce the same telemetry and pause behavior as built-in failures.

**Risks accepted:**
- Registry migration may reveal assumptions in code that expects a closed union.
- Action ID collision rules must be precise to avoid shadowing built-ins.
- Schema validation errors need clear operator-facing rejection reasons.

## Guard Rails

> ⚠️ Do not invoke plugin schedule actions outside the shared scheduler guard wrapper.

> ⚠️ Do not allow plugin action IDs to collide with built-in action IDs.

> ⚠️ Require registered action parameter schemas before accepting a schedule using a plugin action.

> ⚠️ Keep built-in action IDs stable in system://workflows.

> ⚠️ Do not implement arbitrary string action execution without registry metadata.
