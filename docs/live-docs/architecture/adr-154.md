# ADR-154: Continuation prompts MUST embed the exact selected tool name; createContinuationNeed() enforces at construction

**Date:** 2026-05-09T21:18:40.427Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/autonomy/signals.ts, extensions/vscode/src/architect-v2/autonomy/decision.ts  

## Context

In v1, continuation prompts described the next step in natural language without reliably embedding the exact tool name. Models would then continue using a near-synonym tool from the available set (e.g. `read_file` instead of `read_source_code`) and silently fail or do the wrong thing. The user directive at Slice 3 kickoff specifically called this out: 'continuation prompt must include proper keywords or actual tool names to absolutely ensure correct tool selection.'

**Constraints:**
- The selected tool name must reach the model in unmistakable form, not as a label or paraphrase.
- Enforcement must be at construction time so violations cannot be silently introduced anywhere downstream.
- The prompt must also list considered alternatives so the model can recover gracefully if the top choice fails (without re-discovering the option set).

## Decision

Every `ContinuationNeed` produced by the autonomy decision engine MUST embed the exact MCP/local tool name of `selectedAction.tool` verbatim in `continuationPrompt`. This is enforced at construction: `createContinuationNeed()` throws if `continuationPrompt.includes(selectedAction.tool) === false`. `buildContinuationPrompt(top, alternatives)` produces a string that includes the tool name in backticks plus a brief mention of considered alternatives. Direct construction of `ContinuationNeed` literals that bypass `createContinuationNeed()` is forbidden by guard rail.

### Alternatives Considered

- **Free-form continuation prompts (v1 model)** — Rejected: v1's `buildContinuationPrompt` produced strings like 'Continue with the recommended next step: <label>' with the tool name only as an optional hint. Models routinely pick a near-synonym tool when the exact name is not embedded; this is the failure mode ADR-154 exists to remove.
- **Pass tools as a separate structured field instead of embedding in the prompt** — Rejected: The provider's tool-call dispatcher receives the `tools` array regardless, but the model's free-text reasoning is what selects WHICH tool to call. Embedding the name in the prompt anchors that selection. Both mechanisms together (tools array + prompt embed) is defense in depth.
- **Validate at the LLM-call boundary instead of at construction** — Rejected: Defers the failure to a place where it's harder to attribute and easier to silently work around. Construction-time enforcement makes the violation visible at the source.

## Consequences

- The class of failure where the model continues with `read_file` instead of `read_source_code` (or similar near-synonym substitution) is prevented at the prompt layer.
- Action producers must populate `ActionCandidate.tool` with the exact registered tool name, not a friendly label — this is now enforced.
- Continuation prompts have a recognizable shape that includes both the chosen tool and the reasoning, useful for telemetry and replay.
- Tests can assert prompt content includes specific tool names without brittle regex.

**Risks accepted:**
- Tool name strings change when MCP servers are reconfigured; if action producers populate `tool` from a stale source, the prompt will embed a tool the model can't actually call. Mitigation: action producers in Slice 4+ MUST source tool names from the live capability inventory.
- The construction-time throw is loud; a buggy producer will surface as a thrown error rather than a silent wrong-tool call. This is the intended behavior but requires defensive callers.
- Prompt grows by a few tokens per continuation; negligible against the token cost of the actual chat turn.

## Guard Rails

> ⚠️ Do not construct `ContinuationNeed` as an object literal; always use `createContinuationNeed()`.

> ⚠️ Do not strip backticks or rephrase the tool name when building the prompt; the literal string must appear.

> ⚠️ Do not let `ActionCandidate.tool` be a label, alias, or near-synonym of a tool name — it must match the registered tool exactly.

> ⚠️ Do not catch and ignore the `createContinuationNeed()` validation throw — a failed construction is a design bug, not a runtime concern to be swallowed.
