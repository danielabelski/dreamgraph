# ADR-217: Standalone Architect CLI adapters execute through a daemon MCP bridge

**Date:** 2026-05-28T19:20:47.503Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/architect/routes.ts, src/architect/cli-bridge.ts, src/architect/cli-mcp-bridge.ts, tests/standalone-architect-routes.test.ts, standalone-architect, codex-cli, copilot-cli  

## Context

Standalone Architect exposed Codex CLI and Copilot CLI selector options, but the chat route treated those selections as metadata-only fallback. That violated the adapter/runtime identity model and prevented selected CLI adapters from using DreamGraph MCP tools as the authoritative repository operation path.

**Constraints:**
- ADR-201 requires CLI adapters to be first-class DreamGraph Architect adapters rather than dumb metadata labels.
- ADR-216 requires adapter, provider, model, runtime, traces, and provenance to agree on one daemon-owned session runtime.
- CLI adapters must keep provider-native shell/read/write routes denied and route repository actions through DreamGraph MCP tools.
- The browser must not become the authority for adapter execution or filesystem access.
- Bridge startup must fail closed when the upstream daemon MCP endpoint cannot be reached or required tools are absent.

## Decision

Standalone Architect chat requests with adapter codex-cli or copilot-cli now invoke a daemon-owned CLI bridge. The bridge materializes per-run CLI home/config files, exposes the active daemon MCP endpoint to the selected CLI through a stdio MCP proxy, audits tool calls, and returns normalized content, route, provenance, and tool trace metadata. Metadata-only fallback is no longer used for selected CLI chat execution.

### Alternatives Considered

- **Keep codex-cli and copilot-cli selector values as metadata-only deterministic fallbacks.** — Rejected: That was the reported bug and made UI/runtime/provenance metadata claim an adapter path that was not actually used.
- **Spawn a fresh DreamGraph stdio server directly for each CLI run.** — Rejected: That can create a second graph/session boundary instead of using the active daemon session.
- **Let CLI adapters use provider-native filesystem and shell tools for repository operations.** — Rejected: That bypasses DreamGraph MCP authority and weakens auditability.

## Consequences

- Selecting Codex CLI or Copilot CLI in the standalone Architect launches the real CLI path for chat execution.
- Selected CLI adapters receive DreamGraph MCP tools including run_command through the bridge instead of provider-native shell/write/read routes.
- CLI runs emit route/provenance/tool trace metadata tied to the active Architect runtime.
- If the daemon MCP endpoint or required tools are unavailable, the selected CLI path fails explicitly rather than pretending to be metadata-only success.

**Risks accepted:**
- CLI versions may change their argument/config semantics and require bridge updates.
- The initial standalone bridge normalizes post-run tool audit records rather than fully streaming every CLI event into the browser.
- Development-mode tsx bridge spawning may depend on the host process exec arguments until the compiled bridge exists.

## Guard Rails

> ⚠️ Do not reintroduce metadata-only fallback for selected codex-cli or copilot-cli chat execution.

> ⚠️ Do not let standalone CLI adapters answer repository questions without a reachable DreamGraph MCP bridge or an explicit fail-closed error.

> ⚠️ Do not route CLI repository mutations through provider-native shell/write/read surfaces when DreamGraph MCP tools are available.

> ⚠️ Do not spawn a separate graph-authority session for CLI runs without a new ADR that addresses active daemon runtime identity.

> ⚠️ Keep CLI adapter route, runtime, provenance, and tool trace metadata synchronized with ADR-216.
