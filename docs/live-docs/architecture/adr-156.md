# ADR-156: selectExecutor walks T1\u2192T5 in strict order; fallbacks across tiers require an explicit FallbackJustification

**Date:** 2026-05-09T21:30:18.807Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/execution/policy.ts, extensions/vscode/src/architect-v2/execution/tiers.ts, ADR-144  

## Context

Foundation plan \u00a73 mandates a 5-tier execution priority (DreamGraph MCP knowledge \u2192 mutation \u2192 verification \u2192 VS Code editor \u2192 shell) and the user directive at Slice 4 kickoff reinforces it: 'It will naturally fall back to VS Code tools when it proves necessary and only then.' v1 had no enforcement \u2014 tool selection was ad-hoc per call site.

**Constraints:**
- DreamGraph tier (T1–T3) wins over fallback tier (T4–T5) by construction — not by score, not by config.
- Every fallback must carry a recordable, machine-readable reason.
- A missing capability must surface as a blocker, not as a substitute tool.
- Selection must be a pure function of intent + resolved catalog — same inputs, same plan, every time.

## Decision

`selectExecutor(intent, resolvedCatalog)` walks `TIER_ORDER` (T1 \u2192 T5) in strict ascending order. The first tier with at least one available descriptor matching the intent wins. Within a winning tier, the first descriptor in catalog declaration order wins. If the chosen tier is numerically higher than `preferredTierForIntent(intent)`, an explicit `FallbackJustification` is attached describing why (`mcp_tool_failed`, `mcp_tool_unavailable`, `intent_not_covered_by_dreamgraph`, or `editor_native_required`). If no tier covers the intent, returns `NoExecutorAvailable` which the orchestrator translates into a Slice 3 `Blocker` of kind `'capability_missing'`.

### Alternatives Considered

- **Score-based selection across all tiers** — Rejected: Scores hide the priority. A high-confidence VS Code tool could outscore a slightly-lower-confidence DreamGraph tool, which violates the 'DreamGraph first, naturally' directive. Strict ordering makes the invariant visible.
- **Per-mode tier overrides (e.g. autonomous mode allows shell more freely)** — Rejected: Modes are decision-layer concerns (Slice 3 / ADR-152). Bleeding them into execution would re-create the v1 entanglement that ADR-152 exists to remove.
- **Try the chosen tier; if it fails, silently fall back** — Rejected: Silent fallback was a v1 failure mode — the model would think a DreamGraph tool succeeded when actually a shell command had been substituted. Failures must be recorded as `FailureOutcome` and any subsequent tier change must be an explicit orchestrator decision.

## Consequences

- The 90–100% DreamGraph-tool coverage target from the user's directive is enforced by structure: any time a fallback occurs, the orchestrator gets a justification card, not a silent substitution.
- Cards can render a fallback pill with the exact reason (`'MCP unavailable'` vs `'editor-native by design'`).
- Slice 6 (Copilot-plus matrix) can compute parity by scanning catalog entries, no need to invoke selection.
- The `preferredTierForIntent` helper makes 'is this intent DreamGraph-native?' a one-line predicate for the rest of the system.

**Risks accepted:**
- Strict ordering may pick a slow Tier-1 tool when a faster Tier-4 tool exists. Mitigation: the action producer can declare a more specific intent that only the appropriate tier covers.
- If catalog ordering within a tier is wrong, the wrong tool wins ties. Mitigation: declaration order is part of the contract; reviewer attention required when adding entries.
- An unknown intent (typo) will return `NoExecutorAvailable` — loud rather than silent. Intentional, but requires the action producer to know the intent vocabulary.

## Guard Rails

> ⚠️ Do not allow score-based or preference-based selection to override tier order.

> ⚠️ Do not skip recording `FallbackJustification` when chosenTier > preferredTier.

> ⚠️ Do not let `selectExecutor` perform I/O. It is a pure function over `ResolvedCatalog`.

> ⚠️ Do not promote a `NoExecutorAvailable` to a different tool silently — the caller must raise a blocker.
