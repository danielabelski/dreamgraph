# ADR-137: M3 plugin host runtime is now active and graph should treat plugin loading as implemented, tested platform capability

**Date:** 2026-05-08T22:17:59.106Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** packages/host, packages/sdk, src/plugins/manager.ts, src/resources/register.ts, src/cli/commands/plugin.ts, examples/hello-events, plans/DREAMGRAPH_SDK_ROADMAP.md, docs/sdk/events-audit.md, README.md  

## Context

The project has moved beyond the M1/M2 planning state for plugins. M3 host runtime, stable plugin telemetry contracts, reject reasons, system://plugins inventory, dg plugin CLI, and reference plugin loading are now implemented and tested, but prior graph knowledge and ADR context still emphasize future-tense or host-stub assumptions. The graph must preserve the milestone transition so future reasoning does not continue treating plugin loading as unimplemented.

**Constraints:**
- Plugin loading in M3 is in-process and trust-gated; it is not a sandbox.
- The host runtime is opt-in via allowInProcessPlugins / DG_ALLOW_INPROCESS_PLUGINS and may also require per-plugin trust.
- Stable plugin telemetry kinds are host-owned contracts and must remain documented as such.
- system://plugins is the canonical operator-visible inventory for loaded/discovered plugins.
- Runtime evidence from server logs confirms at least one successful plugin load for examples.hello-events@0.1.0.

## Decision

Treat M3 as completed and update graph reasoning accordingly: @dreamgraph/host is an implemented daemon plugin runtime providing discovery, manifest validation, capability/effect gating, telemetry emission, trust banner behavior, watchdog support, system://plugins inventory, and dg plugin administration. Plugin telemetry event kinds and PluginRejectReason are stable SDK contracts. examples/hello-events is the reference plugin and runtime evidence of successful loading should be considered validation input for the feature state.

### Alternatives Considered

- **Keep graph state at pre-M3 planning/stub status until a later manual documentation sweep** — Rejected: This leaves the graph stale and causes future reasoning to misclassify implemented host-runtime behavior as planned-only.
- **Treat M3 plugin runtime as production-sandboxed capability** — Rejected: The current model is trust-gated in-process execution, not worker-isolated sandboxing; overstating security would be inaccurate.

## Consequences

- Future graph queries can rely on plugin host runtime as implemented rather than speculative.
- Operator/runtime reasoning can use system://plugins and dg plugin as active surfaces.
- Future planning can treat worker isolation and deeper sandboxing as later milestones rather than prerequisites for plugin loading existence.

**Risks accepted:**
- Some pre-existing graph entities and docs may still contain stale future-tense wording until separately refreshed.
- Recording milestone completion via ADR does not by itself rewrite every feature/workflow entity description.

## Guard Rails

> ⚠️ Do not describe M3 plugin execution as sandboxed; it is trust-gated in-process loading until later worker isolation lands.

> ⚠️ Do not regress plugin telemetry kinds from stable host-owned SDK contracts without a superseding ADR.

> ⚠️ Do not model webhook dead-letter as part of M3 plugin host completion; that remains outside this milestone.
