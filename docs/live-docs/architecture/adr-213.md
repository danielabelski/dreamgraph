# ADR-213: Standalone Architect browser access reuses DreamGraph instance auth and local-first remote-access semantics

**Date:** 2026-05-27T20:14:59.918Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** standalone-architect, DreamGraph daemon web surface, instance auth, mutation routes, secure tunnel / reverse proxy deployment, remote browser access, ADR-087, ADR-206  

## Context

The migration plan required an auth-boundary decision for browser mutation and review flows. Without a decision, standalone Architect could drift toward bespoke identity infrastructure, weak unaudited mutation access, or remote-access assumptions that conflict with DreamGraph's local-first model.

**Constraints:**
- DreamGraph remains local-first per the migration plan's Remote Access Philosophy.
- Remote access is expected through secure tunnel or reverse proxy patterns such as VS Code port forwarding, Cloudflare Tunnel, Tailscale, ngrok, or SSH reverse proxy, not through a new DreamGraph identity platform.
- Mutation review and execution flows must preserve instance isolation, audit semantics, and existing daemon authentication expectations.
- Standalone Architect must distinguish authenticated mutation capability from read-only or stale-state visibility.

## Decision

Lock standalone Architect access control to existing DreamGraph instance-authenticated daemon semantics, preserving the distinction between daemon-served browser access and governed mutation authority. Remote access remains local-first and operator-mediated through secure tunnel or reverse-proxy patterns rather than a new DreamGraph identity product. Mutation, review, and execution routes must require authenticated instance-scoped access and preserve audit/isolation semantics; browser convenience must not outrank these protections.

### Alternatives Considered

- **Build a new first-party DreamGraph identity and session product as part of standalone Architect** — Rejected: This expands scope away from graph cognition and orchestration and duplicates infrastructure better handled by operator-selected access layers.
- **Allow mutation flows over unauthenticated or read-equivalent browser access** — Rejected: This would violate instance isolation and mutation audit expectations.
- **Treat remote access as unsupported so the browser surface remains effectively localhost-only** — Rejected: The plan explicitly allows secure remote access through operator-controlled tunnels and proxies.

## Consequences

- Implementation can reuse existing auth/isolation semantics instead of inventing a separate identity stack.
- Remote browser access remains possible without redefining DreamGraph as a hosted auth platform.
- Mutation endpoints can inherit clear authentication expectations from existing daemon/Explorer patterns.

**Risks accepted:**
- Legacy or minimally configured deployments may still have weaker auth postures and need explicit operator guidance.
- Users may expect more polished remote-auth UX than the initial operator-mediated approach provides.

## Guard Rails

> ⚠️ Do not expand standalone Architect into a new DreamGraph identity-platform scope without a dedicated ADR.

> ⚠️ Do not allow governed mutation, review, or execution flows on unauthenticated or insufficiently scoped browser access.

> ⚠️ Do not weaken instance isolation or audit requirements for the sake of remote convenience.

> ⚠️ Do not describe standalone Architect as a hosted multi-tenant web product when the architecture remains local-first and daemon-served.
