# ADR-155: Native tool catalog is the source of truth; MCP roster is queried only for liveness, never for discovery

**Date:** 2026-05-09T21:30:18.775Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/execution/catalog.ts, extensions/vscode/src/architect-v2/execution/inventory.ts, plans/ARCHITECT_V2_SLICE4_EXECUTION.md  

## Context

v1 mixed three sources of tool truth: hard-coded `tool-groups.ts` allowlists, runtime MCP `listTools()` discovery, and ad-hoc `local-tools.ts` wrappers. The agent's actual capability set on any given session was the union of all three at that moment, with no audit trail when something changed. Slice 1 \u00a71.5 flagged this as the third-largest tangle in v1.

**Constraints:**
- DreamGraph tools must be treated as native, not as third-party negotiated capabilities.
- Tool-name drift must be impossible — the orchestrator knows tool names from the catalog, not from a probe.
- Roster outages must produce a recordable `mcp_tool_unavailable` signal, not a silent fallback.
- New MCP tools shipped by the daemon must not change agent behavior until intentionally adopted via catalog edit + ADR.

## Decision

`NATIVE_TOOL_CATALOG` in `architect-v2/execution/catalog.ts` is the single source of truth for which tools v2 can invoke. Each entry is a frozen `ToolDescriptor` with exact `tool` name, `tier`, `intent`, and `kind`. The live MCP roster (`McpRosterProbe`) is queried at session start and used solely to mark catalog entries as available or unavailable in `ResolvedCatalog`. MCP tools present on the roster but absent from the catalog are recorded in `ResolvedCatalog.unknownRosterTools` for telemetry but never auto-promoted. Adding/removing a catalog entry requires a code change AND a superseding ADR.

### Alternatives Considered

- **Discover the catalog at runtime from the live MCP roster** — Rejected: DreamGraph tools are first-class to the agent (user directive at Slice 4 kickoff: 'they are native to it'). Discovery treats them like third-party tools the agent must negotiate with. It also breaks repeatability — a roster blip during session start would silently shrink the agent's capability set.
- **Auto-promote unknown roster tools into the catalog** — Rejected: Auto-promotion means a new MCP server can change the agent's behavior without an ADR or code change. That's exactly the silent-capability-drift mode this rewrite is designed to remove.
- **Keep the catalog minimal and let the action producer name tools directly** — Rejected: Tool-name embedding (ADR-154) requires the orchestrator to know exact tool names. Centralizing them in the catalog is the only place to enforce that consistently across action producers.

## Consequences

- Adding a new MCP tool to the daemon does not change the agent's behavior until the catalog is edited and the change is ADR-recorded — capability drift is opt-in only.
- Cards and telemetry can render `unknownRosterTools` to surface 'the daemon now offers X, want to adopt it?' as an explicit prompt rather than as an invisible behavior change.
- Tests can stub `McpRosterProbe` with a deterministic set; no live MCP needed.
- The list of canonical tool names lives in one file, satisfying ADR-154's 'exact tool name' invariant by construction.

**Risks accepted:**
- Catalog can drift from the live MCP roster — if the daemon renames a tool, the catalog entry becomes a dead reference until updated. Mitigation: `ResolvedCatalog` flags it as `unavailable` and `selectExecutor` raises `NoExecutorAvailable` rather than silently misrouting.
- Catalog requires manual maintenance for every MCP daemon release. Mitigation: this is a feature, not a cost — the friction is the point.
- If the catalog is incomplete, the agent will under-use the MCP surface. Mitigation: `unknownRosterTools` telemetry surfaces gaps.

## Guard Rails

> ⚠️ Do not auto-promote `ResolvedCatalog.unknownRosterTools` into `NATIVE_TOOL_CATALOG`. Adoption is a code change.

> ⚠️ Do not add a catalog entry without an ADR mentioning the new tool.

> ⚠️ Do not remove a catalog entry without a deprecating ADR.

> ⚠️ Do not query the MCP roster outside `inventory.resolveCatalog()`. The roster is liveness data, not discovery data.

> ⚠️ Do not let `ToolDescriptor.tool` be a label or alias — it must be the exact dispatch name (cross-cuts ADR-154).
