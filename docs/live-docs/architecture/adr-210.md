# ADR-210: Standalone Architect frontend reuses the daemon-served Explorer/Vite delivery model

**Date:** 2026-05-27T20:14:15.299Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** standalone-architect, DreamGraph Explorer, Explorer Vite production pipeline, daemon web surface, /architect, /architect/assets/*, graph snapshot primitives, SSE client primitives  

## Context

The migration plan left frontend integration strategy open. Without a decision, implementation could split into a separate standalone app, a one-off browser bundle, or an integrated daemon-served surface with shared Explorer primitives.

**Constraints:**
- The daemon already serves browser surfaces and Explorer assets; reuse is preferred where practical.
- Standalone Architect must remain part of the DreamGraph local-first daemon product rather than becoming an independently deployed web product.
- ADR-087 consistency semantics and existing Explorer snapshot/event patterns are valuable reusable primitives.
- The frontend must support plan-first UX, ADR visibility, run feeds, and mutation review without duplicating infrastructure that Explorer already solved.

## Decision

Lock standalone Architect frontend delivery to a daemon-served app shell that reuses the existing Explorer/Vite production pipeline and shared browser primitives where practical. Architect may have its own route, app shell, and plan-centric UI, but it should be built and shipped as a sibling daemon-served surface, not as a separately deployed product or a special-case webview-only artifact.

### Alternatives Considered

- **Build standalone Architect as a completely separate deployable web app with its own runtime and delivery pipeline** — Rejected: This duplicates deployment/runtime concerns and weakens the daemon-served local-first product boundary.
- **Keep standalone Architect as only another VS Code webview surface** — Rejected: The migration goal is a true daemon-served standalone browser control plane, not a renamed extension webview.
- **Create a separate frontend stack unrelated to Explorer conventions** — Rejected: That would throw away existing snapshot/event/build primitives and increase maintenance cost without architectural benefit.

## Consequences

- Phase 3 can build an Architect SPA without inventing a second product deployment story.
- Shared build, asset, and consistency primitives reduce implementation duplication.
- Explorer and Architect can share visual/system concerns while remaining distinct user-facing surfaces.

**Risks accepted:**
- Tight reuse could accidentally leak Explorer-specific assumptions into plan-centric Architect UX if boundaries are not kept clear.
- Shared build changes may affect both surfaces and require stronger verification.

## Guard Rails

> ⚠️ Do not introduce a separate primary deployment/runtime for standalone Architect outside the daemon-served web surface without a superseding ADR.

> ⚠️ Do not fork Explorer consistency/build primitives unnecessarily when reuse satisfies the same need.

> ⚠️ Do not treat standalone Architect as just a VS Code webview wrapper; it must remain reachable as a daemon-served browser surface.
