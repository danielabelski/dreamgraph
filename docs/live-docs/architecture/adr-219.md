# ADR-219: Standalone Architect chat scope separates project prompts from plan execution

**Date:** 2026-05-28T23:21:56.877Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/architect/routes.ts, tests/standalone-architect-routes.test.ts, standalone_architect_chat_scope_pill, standalone-architect  

## Context

Standalone browser Architect chat previously treated a selected plan as implicit context for every prompt, causing global project/repo/graph questions to inherit selected-plan context and risk polluting selected-plan implementation logs or planning action records.

**Constraints:**
- Standalone Architect remains daemon-authoritative and browser clients only send governed intents through /api/architect/v1 per ADR-208.
- Plan operational state and implementation logs remain durable daemon-owned records per ADR-209 and ADR-218.
- Users need a valid no-plan-selected state, and that state must imply Project chat scope.
- Project-scope prompts can still use DreamGraph MCP tools and governed mutation authority, but project scope must not become an unsafe bypass mode.

## Decision

Add an explicit Architect chat scope contract with plan and project values. Plan scope binds prompts to the selected plan and may use selected-plan context/resume/log updates when the action is plan-related. Project scope treats prompts as global project/repo/graph requests, does not inject selected-plan context, and does not write selected-plan implementation-log or planning action records by default. The browser sends scope in /api/architect/v1/chat, supports /ask, /global, /repo, and /plan slash overrides, exposes a scope pill before send, and allows clearing the selected plan by clicking it again.

### Alternatives Considered

- **Keep selected plans as implicit chat context for every prompt.** — Rejected: This makes global graph/repo questions dirty plan execution context and implementation logs.
- **Use separate chat pages for plan and project questions.** — Rejected: That would fragment the standalone Architect workflow and duplicate route/UI behavior instead of making scope explicit in the existing governed contract.
- **Let the browser infer whether a prompt is plan-related from assistant text after the run.** — Rejected: The daemon/orchestrator must decide context injection and log-writing before execution; post-hoc inference cannot prevent pollution.

## Consequences

- Browser Architect can ask graph health or repo questions in Project scope without creating selected-plan implementation-log entries.
- Plan-scoped slice execution continues to include selected plan context and use durable implementation-log checkpoints.
- No plan selected remains a first-class UI state and defaults chat to Project scope.
- Slash commands provide fast per-message override while preserving daemon-governed mutation rules.

**Risks accepted:**
- Users may expect the selected plan to remain active while the chat pill is in Project scope, so the UI must keep the scope label visible before send.
- Some older clients that omit scope still rely on compatibility defaults based on whether a plan id is sent.
- Future tool mutations in Project scope still require careful governance messaging so project scope is not mistaken for unrestricted mode.

## Guard Rails

> ⚠️ Do not inject selected-plan context into Project-scope chat unless the user explicitly changes to Plan scope or a future ADR defines a narrower explicit-request contract.

> ⚠️ Do not write selected-plan implementation-log entries or planning action records for Project-scope chat by default.

> ⚠️ Do not force-select the first plan when no selected plan is configured or requested.

> ⚠️ Do not make browser-local state the authority for plan execution; persist selected-plan changes through daemon-owned engine.env/Architect selection routes.
