# ADR-142: Every Architect v2 slice produces both a Markdown plan and ADR mirror(s); the two formats must agree

**Date:** 2026-05-09T19:55:43.812Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** plans/ARCHITECT_V2_SLICE1_INVENTORY.md, ADR-140, ADR-141  

## Context

DreamGraph treats ADRs (queryable via mcp_dreamgraph_query_architecture_decisions) as the canonical decision store, but a multi-slice rewrite also needs human-readable narrative documents for review, onboarding, and diff archaeology. The team needs an explicit rule about which format owns what so neither is an afterthought.

**Constraints:**
- DreamGraph cognitive cycles must be able to reason over rewrite decisions — they live in the graph or they don't exist for the dream engine.
- Human reviewers (and the user) read Markdown in the repo; an ADR-only baseline is invisible during code review.
- A single source of truth would be ideal but ADR JSON is poor for narrative prose and Markdown is poor for structured graph queries.

## Decision

Every Architect v2 slice produces both: (a) a plain Markdown plan/inventory/spec document under plans/ for human review and diffing, AND (b) one or more ADRs recorded via mcp_dreamgraph_record_architecture_decision for graph reasoning. The two formats must agree. The Markdown document is the canonical narrative; the ADRs are the canonical machine-readable decision records. Slice 1 establishes the pattern: plans/ARCHITECT_V2_SLICE1_INVENTORY.md + ADR-140 through ADR-145.

### Alternatives Considered

- **Markdown file only** — Rejected: The graph cannot reason over an external Markdown file; future cognitive cycles, dream insights, and graph_rag_retrieve queries would miss the entire baseline.
- **ADR(s) only** — Rejected: Humans review plans by reading files in the repo; an ADR-only baseline is invisible during code review and onboarding, and Markdown remains the diff-friendly source for human discussion.
- **Auto-generate the Markdown from the ADRs at build time** — Rejected: Adds tooling complexity now to solve a problem we don't yet have; the dual-write cost for a single inventory document is trivial, and divergence detection can be added later if needed.

## Consequences

- Future dream cycles, tension detection, and graph_rag_retrieve calls can reason over the rewrite using ADR-140… series.
- Human PR review and onboarding stays grounded in repo files (plans/ARCHITECT_V2_*.md).
- Slice handoffs always cite both the Markdown section and the ADR id, making cross-references unambiguous.
- Drift between the two surfaces is detectable by inspection — if a future ADR contradicts plans/ Markdown or vice versa, an explicit reconciliation ADR is required.

**Risks accepted:**
- Dual-write cost: every locked decision must be expressed twice.
- Drift risk: Markdown and ADR can diverge if updated separately; mitigated by guard rails but not eliminated.
- Slight ambiguity about which format wins in a contradiction — explicit rule: ADRs win for machine reasoning; Markdown wins for narrative; conflicts trigger a reconciliation ADR.

## Guard Rails

> ⚠️ Do not begin a slice without producing both a Markdown plan/inventory document AND its ADR mirror(s).

> ⚠️ Do not silently update one format without updating the other in the same commit.

> ⚠️ Do not delete the Markdown plans/ document after recording the ADR — both must persist.

> ⚠️ Do not record an ADR whose chosen direction contradicts an existing Markdown plan without first deprecating the Markdown section in the same commit.
