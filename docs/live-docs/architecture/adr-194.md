# ADR-194: Architect agentic loop: write-pressure reservation is anchor-gated and auto-lifts on any write

**Date:** 2026-05-15T23:01:59.001Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/chat-panel.ts, extensions/vscode/src/autonomy.ts, extensions/vscode/src/autonomy-loop.ts, extensions/vscode/src/tool-classification.ts  

## Context

The Architect's task-level write-pressure mechanism in `runAgenticLoop` (`extensions/vscode/src/chat-panel.ts`) had two failure modes observable at runtime: (1) once tripped, the reservation never lifted within the loop even after the model successfully wrote, causing the model to paraphrase the constraint as a permanent "no more reads" persona that bled into subsequent turns; (2) the reservation armed on lifetime read count regardless of task type, so read-only or assess-only user prompts (which inherently must read) were getting blocked from reading. A user-reported case showed the Architect refusing to read the body of a Copilot CLI provider file it had been asked to investigate, citing a "no more reads" constraint that did not match the user's intent.

**Constraints:**
- Never-fail invariant: the loop must keep serving the Architect; constraints are gravity hints, not hard router gates.
- Provider-agnostic: the rule must work for any architect provider/model — no provider-specific branching.
- Token economy: must still apply real pressure when the prior pass established a sticky patch anchor and the model is wasting tokens re-locating the same anchor.
- Common-sense reset: any write of any kind (host-local writes, MCP writes, markdown chapter patches, entity edits, run_command, etc.) must reset the constraint — not just a hard-coded subset.
- Read/assess tasks and fresh user prompts must not be subject to write-pressure at all.

## Decision

In `runAgenticLoop`, gate the write-reservation on `AutonomyState.lastAnchorPaths` being non-empty (a sticky patch anchor established by a prior autonomy pass), track `readsSinceLastWrite` instead of lifetime reads, and lift the reservation automatically the first time any non-read-prefixed tool runs in the loop — emitting a synthetic user message that announces the lift. The reservation may re-arm later in the same loop if the model returns to consecutive reads without writing. The reservation text now explicitly enumerates allowed reads under pressure (exact body for safe patch, post-write verification, stale-anchor recovery, reading a newly identified concrete blocker target) versus discouraged reads (broad search, re-reading already-inspected files, relocating the same anchor, "just to be sure" discovery). The wrap-up "you spent the budget on reads" framing is gated by the same anchor signal so read-only turns get the generic wrap-up regardless of read volume.

### Alternatives Considered

- **Keep the original one-shot lifetime-read reservation** — Rejected: Caused the runtime regression where the Architect refused to read on inherently read-only tasks and held the constraint across turns.
- **Hard-strip read tools from the catalog after threshold** — Rejected: Violates the never-fail / no-firewall invariant; the router must never reject reads mid-turn — pressure is gravity-driven, not gate-driven.
- **Lift the reservation only on a hard-coded subset of write tools (e.g. replace_string_in_file, multi_replace_string_in_file)** — Rejected: Provider-agnostic and surface-agnostic resets are required: patch_markdown_chapter, edit_markdown_section, edit_entity, create_file, run_command, MCP-prefixed write tools, etc. all represent legitimate progress and must reset the counter. The existing `isReadOnlyTool` prefix classifier in `autonomy-loop.ts` already provides the canonical read/non-read split.

## Consequences

- Read-only/assess user prompts read freely; the reservation never arms when no prior-pass anchor exists.
- When the prior pass established an anchor, write-pressure still applies — but lifts the moment the model writes anything (including markdown chapter patches), and may re-arm if the model goes back to consecutive reads.
- The Architect no longer paraphrases the reservation as a persistent 'no more reads' persona, because the synthetic user message explicitly states it is not a permanent ban and is automatically lifted on the next write.
- Wrap-up messaging matches the task type: read-only turns get the generic summary, anchor-bound write-stalled turns get the strict 'name the patch or the prerequisite' framing.

**Risks accepted:**
- The reservation depends on `AutonomyState.lastAnchorPaths` being populated by the prior pass via `extractProseAnchorPaths` and the autonomy state advance — if that signal regresses (false negatives), write-pressure will under-fire on legitimate stalls.
- The `isReadOnlyTool` prefix list in `autonomy-loop.ts` is the classification source of truth; new read-only tools added without that prefix would be miscounted as writes and would prematurely lift the reservation. Mitigation: keep the prefix list as the canonical taxonomy and extend it when new read-only tools are introduced.

## Guard Rails

> ⚠️ Do not re-introduce a hard-strip / firewall that removes read tools from the catalog after threshold — pressure is gravity only.

> ⚠️ Do not gate the reservation on lifetime read count or on a per-turn one-shot flag — `readsSinceLastWrite` plus auto-lift on any write is the contract.

> ⚠️ Do not arm the reservation in the absence of `AutonomyState.lastAnchorPaths` — read-only and assess tasks must read freely.

> ⚠️ Do not narrow the auto-lift to a hard-coded subset of write tools — any non-read-prefixed tool counts as a write for reset purposes.
