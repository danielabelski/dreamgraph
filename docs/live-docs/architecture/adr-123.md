# ADR-123: Discipline manifest must mirror the live MCP tool registry 1:1

**Date:** 2026-05-05T12:04:18.630Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/discipline/manifest.ts, src/discipline/tool-proxy.ts, TOOL_CLASSIFICATIONS, MCP tool registry  

## Context

src/discipline/manifest.ts had a 56-tool TOOL_CLASSIFICATIONS map but the server registered 72 tools. 17 live MCP tools (including init_graph, scan_project, edit_file, lucid_dream, graph_rag_retrieve, get_cognitive_preamble, and discipline_record_tool_call) had no classification. tool-proxy.checkToolPermission and the discipline manifest exposed to clients were silently incomplete. The header doc-comment claimed '53 MCP tools', further understating coverage.

**Constraints:**
- Phase permissions for new tools must be chosen by analogy with the closest existing peer (e.g. all *_file tools mirror create_file's posture; lucid_* mirror dream_cycle's internal-only posture)
- Cognitive tools that run only inside the engine lifecycle must have allowed_phases=[]
- Tools that mutate persistent target files must carry target-write semantics + ['execute'] phase + plan_entry=true
- The doc-comment count and the actual TOOL_CLASSIFICATIONS map size must agree

## Decision

Treat src/discipline/manifest.ts as a strict mirror of the live MCP tool registry. Every server.tool('name', ...) registration must have a matching TOOL_CLASSIFICATIONS entry, and the doc-comment header must report the same count. Reconciled this pass by adding 17 missing classifications (truth/analysis/write/file_operation/cognitive/verification categories) and updating '53 MCP tools' to '73 MCP tools (72 server + 1 local extension equivalent)'. The single non-server entry (read_local_file) is the VS Code extension's filesystem peer of read_source_code and is referenced by MANDATORY_TOOL_RULES. A diff check (Select-String 'server\\.tool\\(' vs Select-String 'tool_name:') must report 0 missing and 0 extras.

## Consequences

- tool-proxy.checkToolPermission() now sees ground truth for every registered tool; phase gating is no longer silently bypassed for unclassified tools
- buildManifest() exported to clients reflects every real capability
- Discipline session enforcement covers the full surface area, not just the legacy 56 tools
- Future contributors get a CI-style diff signal when they add a tool without classifying it

**Risks accepted:**
- Future tool additions can re-introduce drift if contributors do not also update manifest.ts
- Phase permissions chosen by analogy may be wrong for a genuinely novel tool category
- The extension's read_local_file entry creates a single 'classified but not server-registered' exception that future maintainers must understand

## Guard Rails

> ⚠️ Do NOT add a new server.tool registration without simultaneously adding a TOOL_CLASSIFICATIONS entry and updating the header count

> ⚠️ Do NOT classify a tool by guessing posture — mirror the nearest existing peer's category, target, allowed_phases, audit_trail, and plan_entry

> ⚠️ Do NOT remove the 'read_local_file' entry without first removing the corresponding extension capability from extensions/vscode/src/local-tools.ts

> ⚠️ Always run the registered-vs-classified diff (Select-String) before merging discipline changes
