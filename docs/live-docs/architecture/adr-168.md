# ADR-168: Slice 7 — CompletionStatus is a closed 6-kind discriminated union with assertNeverStatus exhaustiveness

**Date:** 2026-05-09T22:30:46.958Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/verification/types.ts, extensions/vscode/src/architect-v2/verification/classifier.ts  

## Context

Verification logic must enforce ADR-163's never-fall guarantee at runtime: a missing toolchain or a verification failure must produce a typed status, not an exception. Without a closed discriminated union, dispatch sites diverge and 'partial completion' creeps back as a silent half-state.

**Constraints:**
- Status set is closed; new kinds require ADR + update of every dispatch site
- verification_unavailable is a status, not an exception
- classifyCompletion is pure (no I/O, no Date.now)
- Exhaustiveness enforced by assertNeverStatus(s: never): never at every dispatch

## Decision

CompletionStatus is a closed 6-kind discriminated union: completed, completed_no_verification_needed, repair_recommended, blocked, failed_verification (reason: verification_unavailable), mutation_failed. assertNeverStatus(s: never): never is exported and used at every dispatch site so adding a kind without updating consumers is a compile error. classifyCompletion never throws on missing toolchain; it returns failed_verification with the missing kinds enumerated.

### Alternatives Considered

- **Throw on missing toolchain instead of returning a status** — Rejected: violates ADR-163 never-fall: a single missing toolchain would crash the whole pass and lose unrelated work
- **Open status set with arbitrary string kinds** — Rejected: loses exhaustiveness, makes card rendering and metrics aggregation a guessing game
- **Boolean 'completed' flag plus optional reason** — Rejected: loses the structured discriminator cards and metrics need; ambiguous about repair vs blocker vs unavailable

## Consequences

- Cards (Slice 5) can switch on .kind with TS exhaustiveness enforcement
- Missing toolchain surfaces as a typed blocker the user can act on
- Mutation failures are clearly distinguished from verification failures in metrics
- Adding a 7th status requires touching every consumer (intentional friction)

**Risks accepted:**
- Adding new status kinds is high-friction (intentional); requires ADR amendment
- assertNeverStatus only catches drift at compile time; tests need to exercise each kind to confirm runtime dispatch

## Guard Rails

> ⚠️ Every switch on CompletionStatus.kind MUST end with assertNeverStatus(s)

> ⚠️ classifyCompletion MUST NOT throw for missing toolchain (return failed_verification instead)

> ⚠️ New CompletionStatus kinds MUST be added in the same commit as their ADR and all consumers

> ⚠️ verification_unavailable's missingKinds array MUST be non-empty when this status is returned
