# ADR-211: VS Code remains the companion Architect surface until a deliberate standalone cutover ADR

**Date:** 2026-05-27T20:14:27.997Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** Architect ChatPanel, standalone-architect, VS Code command surface, deep links between standalone and VS Code, daemon orchestration contracts, ADR-192, ADR-206  

## Context

The migration plan required a concrete coexistence and cutover decision for VS Code. Without it, implementation could drift into duplicated orchestration logic or accidentally deprecate the canonical VS Code path before standalone Architect is ready.

**Constraints:**
- ADR-206 already states that VS Code remains a companion/escape-hatch surface until an explicit cutover ADR supersedes the current canonical boundary.
- Phase 7 requires no duplicated orchestration logic between VS Code and standalone.
- Standalone Architect must become a daemon-served browser control plane, but existing VS Code flows still need editing escape hatches and continuity during migration.
- Any activation, deprecation, or thin-client transition must be deliberate and reviewable.

## Decision

Lock the coexistence model so VS Code remains the companion Architect surface during migration, with standalone Architect becoming the daemon-served plan-first control plane and VS Code providing editing escape hatches, deep links, and eventual thin-client integration opportunities. No activation, deprecation, or cutover of the canonical VS Code path occurs until a dedicated superseding ADR explicitly defines the transition.

### Alternatives Considered

- **Replace or deprecate VS Code Architect immediately as standalone work begins** — Rejected: This would violate the accepted migration boundary and remove a working companion surface before the browser control plane is proven.
- **Keep standalone and VS Code as permanently separate orchestration stacks** — Rejected: This would duplicate logic, increase drift risk, and undermine the daemon-authoritative design.
- **Decide cutover ad hoc in implementation PRs without a dedicated ADR** — Rejected: That would make activation and deprecation behavior hard to audit and easy to change accidentally.

## Consequences

- Implementation can share daemon orchestration contracts across browser and VS Code without duplicating control logic.
- Users retain a stable editing/escape-hatch surface while the standalone control plane matures.
- Future cutover work has a clear review trigger instead of happening by drift.

**Risks accepted:**
- Maintaining two user-facing surfaces during migration adds integration overhead.
- Delay in recording a future cutover ADR could prolong dual-surface complexity.

## Guard Rails

> ⚠️ Do not duplicate core orchestration logic between VS Code and standalone Architect.

> ⚠️ Do not deactivate, deprecate, or silently thin-client the VS Code Architect surface without a dedicated superseding ADR.

> ⚠️ Do not make standalone-only assumptions that remove VS Code deep-link and escape-hatch interoperability during migration.
