# ADR-174: PromptComposer declares context requirements; ContextAssembler fulfills

**Date:** 2026-05-09T23:09:48.150Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/prompts/composer.ts, extensions/vscode/src/architect-v2/prompts/requirements.ts, extensions/vscode/src/architect-v2/orchestrator/ports.ts, extensions/vscode/src/architect-v2/orchestrator/loop.ts  

## Context

ADR-171 + Slice 8A.2 invariant force the composer to be passive (no graph reads, no MCP). But a passive composer that only renders whatever the assembler chose creates a knowledge-gap: only the prompt template knows what *kinds* of context this particular pass actually needs (architectural decisions? unresolved blockers? prior failed attempts? ADR lineage?). If the assembler has to guess, it either over-fetches (wastes the window) or under-fetches (silently degrades the prompt). We need a way for the composer to *declare* its needs without *performing* retrieval.

**Constraints:**
- composer.ts and requirements.ts MUST NOT import from execution/, MCP, vscode, fs, http, or ProjectGraphReader.
- ContextRequirementManifest is a plain data structure (frozen). No callbacks, no thunks, no promises inside it.
- ContextBuilderPort.buildContext receives the manifest as advisory input; the assembler MAY satisfy fewer than requested but MUST NOT fetch beyond declared kinds without an ADR amendment.
- The composer MUST tolerate any envelope shape the assembler returns — missing requested kinds is not an error.
- declareContextRequirements is pure: same inputs → same output, no clock, no randomness, no I/O.

## Decision

Two-step composer/assembler contract. The PromptComposer exposes a pure function declareContextRequirements(input) -> ContextRequirementManifest *in addition to* composePrompt. The orchestrator calls declareContextRequirements first, passes the manifest to ContextBuilderPort.buildContext, then calls composePrompt with the resulting ContextEnvelope. The composer stays passive about retrieval (no graph reads, no MCP calls, no I/O); it only declares what it would *like* to see. The assembler/RelevanceEngine remains the only cognition site: it interprets the manifest, ranks, fetches, trims, and emits the envelope. If a requirement cannot be satisfied (sparse mode, no graph), the assembler still emits an envelope and notes the unmet requirements via section provenance; the composer renders what it gets without retrying.

### Alternatives Considered

- **Composer also retrieves graph data when it spots a gap.** — Rejected: Smears cognition across two layers; tests need a graph to render a prompt; sparse-mode behavior depends on which layer ran first.
- **Assembler guesses what each capability needs.** — Rejected: Couples the assembler to every prompt template; adding a new capability touches both layers; the knowledge of 'what this prompt needs' belongs with the prompt.
- **Static per-capability requirement tables owned by Slice 6.** — Rejected: Requirements depend on the *user intent* and *continuation state*, not just the capability id. A pure table can't see those.
- **Skip the manifest; let composer accept a richer envelope shape that already includes everything possibly needed.** — Rejected: Forces the assembler to over-fetch on every pass; defeats budget discipline; loses the very signal the assembler needs to rank.

## Consequences

- Adding a new prompt template means editing the composer only — it declares its needs and the assembler already knows how to fulfill the supported kinds.
- Adding a new retrieval source (e.g. test-history backend) means editing the assembler only — it learns to satisfy more requirement kinds, no composer change.
- Tests can golden-file both layers independently: declareContextRequirements is pure; the assembler is tested with a fake reader; the composer is tested with a hand-built envelope.
- Token budgets become declarative: composer says 'medium' for ADR lineage, assembler decides what 'medium' means against the active provider window.

**Risks accepted:**
- Manifest taxonomy bloats. Mitigation: requirement kinds are an enum union; adding a kind requires ADR.
- Composer 'declares everything' to be safe, defeating budget discipline. Mitigation: golden-file tests assert minimal requirement sets per template; reviewer flag.
- Assembler silently ignores half the manifest. Mitigation: assembler must mark unmet requirements in envelope section provenance (added in 8A.3); a metrics check could surface chronic mismatches.

## Guard Rails

> ⚠️ Build-time check (Slice 8B): grep that fails if prompts/*.ts imports anything matching /^(vscode|fs|node:|http|mcp_)/ OR imports from ../execution/ or ../orchestrator/project-graph (composer must not see ProjectGraphReader at all).

> ⚠️ Test (8A.3): assembler ignoring the manifest entirely (returns NULL_PROJECT_SUBGRAPH-derived envelope) must still produce a renderable prompt.

> ⚠️ Test (8A.2): declareContextRequirements called twice with identical input must return deeply-equal manifests.
