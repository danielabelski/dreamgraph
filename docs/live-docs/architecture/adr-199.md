# ADR-199: Copilot CLI live output is sourced from NDJSON event stream

**Date:** 2026-05-19T20:54:05.003Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-core/adapters/copilot-cli/event-stream.ts, extensions/vscode/src/architect-core/adapters/copilot-cli/argv.ts, extensions/vscode/src/architect-core/adapters/copilot-cli/orchestrator.ts, extensions/vscode/src/architect-core/adapters/copilot-cli/provider-port.ts, extensions/vscode/src/chat-panel.ts, ToolTraceEntry, RecordedMcpToolCall, copilot-cli  

## Context

The Copilot CLI adapter needs reliable live assistant text, reasoning, and tool-call telemetry in the VS Code chat UI. File-based or audit-tail derived observations are insufficient as the primary runtime source because they can lag, miss provider events, or duplicate transcript content.

**Constraints:**
- Copilot CLI exposes typed stdout events when invoked with --output-format json.
- The adapter must preserve provider-neutral chat/tool trace contracts while keeping Copilot-specific event shapes adapter-local.
- Assistant text must not be duplicated by combining streamed deltas with a later full transcript chunk.
- Tool start/complete events must map into ToolTraceEntry rows with stable provenance such as dreamgraph:<tool> or cli:<tool>.
- Audit-live tailing may remain as secondary MCP provenance but must not compete with the CLI stdout event stream as the authoritative live UX source.

## Decision

Invoke Copilot CLI with --output-format json and treat its stdout NDJSON event stream as the authoritative live runtime feed for assistant message deltas, reasoning deltas, tool execution start/complete events, and final result metadata. Parse events in the Copilot adapter, translate them through provider-port into provider-neutral chat events and ToolTraceEntry updates, and suppress duplicate full-transcript emission when per-token assistant deltas were already streamed.

### Alternatives Considered

- **Use only the final CLI transcript after process exit** — Rejected: The UI would lose live tool-call and token streaming behavior and would provide poorer progress visibility.
- **Use bridge audit-live tailing as the primary source** — Rejected: Audit tailing is MCP-specific secondary provenance and can lag or diverge from the provider CLI's own typed runtime events.
- **Expose Copilot CLI raw event types directly to Architect core and chat UI** — Rejected: That would couple provider-neutral components to Copilot-specific event schemas instead of normalizing at the adapter boundary.

## Consequences

- Users see live assistant text/reasoning and tool progress during Copilot CLI runs.
- Tool trace rows are populated from the CLI's own typed runtime events rather than inferred after the fact.
- Provider-specific NDJSON parsing remains isolated in the Copilot CLI adapter and provider port.
- Duplicate assistant messages are avoided when streamed deltas already cover the final response.

**Risks accepted:**
- Copilot CLI may change its output-format json event schema or event names.
- Malformed or partial NDJSON lines can reduce live trace fidelity even if the final CLI result succeeds.
- Provider event timing might still differ from MCP audit persistence timing, requiring clear provenance labeling.

## Guard Rails

> ⚠️ Do not replace the Copilot CLI NDJSON stdout stream with bridge audit-live tailing as the primary live UX source without a new ADR.

> ⚠️ Do not pass raw Copilot CLI event objects into Architect core; normalize them at the adapter/provider-port boundary.

> ⚠️ Do not emit a full transcript chunk when assistant.message_delta events already streamed the same content.

> ⚠️ Keep tool start/complete translation explicit so Context Inspector/chat traces retain tool provenance.
