# ADR-122: Anchor cognitive timeline analysis on real ISO timestamps via cycleFromIso

**Date:** 2026-05-05T12:04:18.323Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/cognitive/causal.ts, src/cognitive/temporal.ts, DreamHistoryEntry, TensionTrajectory, CausalLink  

## Context

Cognitive timeline analytics in causal.ts and temporal.ts (causal lag, urgency-over-time trajectories, first/last-observed timestamps) were derived from synthetic counters (currentCycle - ttl, original.occurrences) instead of the real ISO timestamps already carried by dream-history entries and tension events. Active tensions all collapsed onto currentCycle and resolved tensions onto original.occurrences, so trajectory pattern=spike was unreachable, CausalLink.first_observed/last_observed were synthetic, and lag arithmetic was meaningless.

**Constraints:**
- No schema change to existing data files (dream_history.json, tension_log.json must remain readable)
- No new runtime dependency
- Lookup must be O(log n) on long histories
- engine.loadDreamHistory()/loadTensions() must remain the data source

## Decision

Add a buildHistoryIndex() + cycleFromIso() helper pair in both cognitive/causal.ts and cognitive/temporal.ts. Both consume engine.loadDreamHistory(), build a sorted {ts, cycle}[] index from per-cycle generated_at, and binary-search for the largest ts <= target ISO. All trajectory anchors and CausalLink.first_observed/last_observed derive from real ISO via this pair. The currentCycle - ttl and original.occurrences heuristics are removed. Rejected alternatives: extracting a shared helper now (broadens scope), persisting resolution_cycle on ResolvedTension at write time (schema migration), recomputing cycle from a synthetic monotonic counter (the bug being removed).

## Consequences

- Trajectory pattern=spike becomes structurally reachable for tensions whose urgency actually spiked between cycles
- CausalLink.first_observed/last_observed carry meaningful ISO strings derived from real cause/effect events
- Lag values in propagation_hotspots reflect real cycle deltas and become safe to act on
- Resolved-tension resolution_cycle reflects the actual resolution moment instead of original.occurrences

**Risks accepted:**
- Two ~30 LOC helpers (one per module) drift out of sync until extraction
- Building the index per call has measurable cost on very large histories (mitigated by the 5s mtime cache on loadJsonData)
- Non-UTC ISO offsets could sort incorrectly (mitigated: all writers use new Date().toISOString() which is always UTC Z)
- detectSeasonalPatterns() had to be stubbed pending a DreamHistoryEntry schema change to record per-cycle per-domain tension counts

## Guard Rails

> ⚠️ If a third consumer of cycleFromIso appears, hoist buildHistoryIndex/cycleFromIso to a shared module before adding a third copy

> ⚠️ Keep the fallback to `now` when first_seen/resolved_at is missing or unparseable — older logs may lack the field

> ⚠️ Do NOT replace cycleFromIso with currentCycle-based heuristics; that regressed the analytics once already

> ⚠️ Do NOT remove the NOTE block on detectSeasonalPatterns without first extending DreamHistoryEntry to carry per-cycle per-domain tension counts
