# ADR-124: All persistent JSON writes use atomicWriteFile (temp + fdatasync + rename)

**Date:** 2026-05-05T12:04:18.874Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/utils/atomic-write.ts, src/utils/engine-env.ts, src/cli/commands/attach.ts, src/cli/commands/export.ts, src/cli/commands/fork.ts  

## Context

Several CLI commands (attach, export, fork) and the engine-env initializer wrote persistent JSON state with raw writeFile/writeFileSync. A crash or power loss mid-write would leave a truncated or zero-byte file in place of the previous valid state, with no recovery path.

**Constraints:**
- No introduction of native fs-extra or graceful-fs deps — use built-in fs/promises and fs only
- Sync writes (engine-env init) must also be atomic — mid-init crash must not leave a corrupt instance.json
- atomicWriteFile must default to UTF-8 so callers do not have to repeat the encoding flag
- Failure path must clean up the orphan .tmp where possible without masking the original error

## Decision

All persistent JSON state writes go through src/utils/atomic-write.ts (open \u2192 writeFile \u2192 fdatasync \u2192 close \u2192 rename) for the async path. The synchronous engine-env initializer in src/utils/engine-env.ts mirrors the same pattern with openSync \u2192 writeFileSync \u2192 fdatasyncSync \u2192 closeSync \u2192 renameSync, and unlinks the orphan .tmp on failure. Audit pass converted 8 sites: attach.ts (3), export.ts (3), fork.ts (1), engine-env.ts (1).

## Consequences

- Crash or power loss during a write leaves the original file intact and at most a harmless orphan .tmp
- Operators can trust that data/*.json files are either the prior valid version or the new valid version, never a partial truncation
- New code adding a writeFile against persistent state is an obvious code-smell visible in review

**Risks accepted:**
- Inline sync atomic pattern in engine-env.ts duplicates the helper's logic and can drift
- The orphan .tmp cleanup is best-effort; if both rename and unlink fail, the .tmp lingers (harmless but noisy)
- Atomic rename is per-filesystem; cross-device renames will fail (mitigated: temp file is in same directory as target)

## Guard Rails

> ⚠️ Do NOT add a raw writeFile() / writeFileSync() against any data/*.json or instance.json path — always go through atomicWriteFile or its sync mirror

> ⚠️ Do NOT skip fdatasync; rename without fdatasync can still expose torn writes on some filesystems

> ⚠️ Do NOT swallow rename errors silently — propagate so the caller knows the write was not durable

> ⚠️ When adding new sync write sites, replicate the engine-env.ts inline pattern rather than blocking on the async helper
