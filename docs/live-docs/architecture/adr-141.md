# ADR-141: v10.0.0 is the cutover release; intermediate Architect v2 slices ship as v9.x behind a feature flag

**Date:** 2026-05-09T19:55:19.119Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** package.json, extensions/vscode/package.json, plans/ARCHITECT_V2_SLICE1_INVENTORY.md, ADR-140  

## Context

During the multi-slice Architect rewrite, the project still needs a coherent versioning story: when does the version bump, what does v10.0.0 mean, and how are intermediate slices released without confusing users about which Architect they are running?

**Constraints:**
- Existing v9.0.0 users must keep getting bug fixes and minor improvements during the rewrite.
- v10.0.0 must be a clean break, not a 'mostly v2 with some v1 still around' release.
- Intermediate releases must not require users to opt into a half-built v2.
- Release version semantics must stay predictable — v9.x = v1 Architect, v10.x = v2 Architect, no exceptions.

## Decision

v10.0.0 is reserved for the cutover commit. All intermediate Architect v2 progress ships as v9.1.0, v9.2.0, … on main. Each minor v9.x release may include v2 internals behind an off-by-default feature flag (or stay unreleased to npm/marketplace if no user-facing change is ready). v1 remains the default Architect for every v9.x release. The first commit on main that flips the default to v2 and deletes v1 is the v10.0.0 release commit.

### Alternatives Considered

- **Bump major to v10.0.0 at the start of the rewrite and ship intermediate v10.0.0-rc.N pre-releases** — Rejected: Pre-release tags fragment user installs and break the 'main is shippable' invariant for stable release channels; users expect v10.x to be the new Architect, not a half-built one.
- **Stay on v9.0.0 for the entire rewrite and bump only at cutover** — Rejected: Loses the ability to ship intermediate value (instrumented v2 internals behind a flag, bug fixes to v1, opt-in v2 previews) and concentrates all release risk into one giant version bump.
- **Branch v9 maintenance from main and develop v10 on main** — Rejected: Contradicts ADR-140's parallel-folder choice and creates the long-lived branch problem we explicitly rejected.

## Consequences

- Users on v9.x get a stable Architect throughout the rewrite period.
- Each completed Slice can ship as a v9.minor release with v2 internals dark-launched behind a flag, providing real telemetry without changing default behavior.
- v10.0.0 marks a single clear product transition — marketing, docs, release notes, migration guide all align to one version.
- Internal teams can opt into v2 previews via the feature flag and report regressions early without affecting general users.

**Risks accepted:**
- A long rewrite period could accumulate many v9.minor releases with growing dark-launched code that never gets exercised by real users until cutover.
- The feature flag must be reliable; if it leaks, users on v9.x could accidentally land on v2 internals and report bugs against the wrong codepath.

## Guard Rails

> ⚠️ Do not bump to v10.x.x for any commit before the cutover.

> ⚠️ Do not enable the v2 feature flag by default in any v9.x release.

> ⚠️ Do not ship a v9.x release that breaks v1 default behavior — v1 is the contract for v9.x.

> ⚠️ Do not skip from v9.x straight to v11.x; v10.0.0 must be the cutover release.
