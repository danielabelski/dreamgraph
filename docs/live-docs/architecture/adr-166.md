# ADR-166: Slice 6 — DensityProbe + measureDensity: pure per-capability graph readiness signal that drives mode selection

**Date:** 2026-05-09T22:15:18.654Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/capabilities/density.ts, extensions/vscode/src/architect-v2/capabilities/selection.ts, plans/ARCHITECT_V2_SLICE6_CAPABILITY_MATRIX.md  

## Context

The two-mode contract (ADR-163) needs an input signal to decide which mode to use per capability. Without per-capability density, the architect either treats all capabilities uniformly (wrong) or invents heuristics ad-hoc (unauditable).

**Constraints:**
- measureDensity is pure: same (probe, capabilityId) -> same density forever
- Probe collection is the orchestrator's responsibility; Slice 6 takes the probe as input
- Bucket thresholds are intentionally low: a project with 50 entities of a kind is rich for that kind
- EMPTY_DENSITY_PROBE drives 'absent' for every capability (day-zero install state)

## Decision

DensityProbe is a small read-only snapshot of graph state (hasIndex, sourceEntityCount, apiEntityCount, adrCount, validatedEdgeCount, uiElementCount, dataModelEntityCount, recentDreamInsightCount, resolvedTensionCount). measureDensity(probe, capabilityId) is a pure function returning 'rich' | 'partial' | 'sparse' | 'absent', selecting the most-relevant count per capability and bucketing by thresholds (absent=0, sparse=1..9, partial=10..49, rich=50+). The orchestrator collects the probe once per pass via system://overview + system://capabilities; Slice 6 never does I/O.

### Alternatives Considered

- **Single global density signal (one bucket for the whole graph)** — Rejected: navigate.symbol may be rich while search.ui is absent; a global signal forces wrong mode for half the capabilities
- **Continuous numeric density score** — Rejected: Selection logic becomes harder to reason about and harder to render on cards; 4 buckets are sufficient
- **Density as side-effect of failed graph queries** — Rejected: Discovers density only after wasted T1 attempts; defeats the purpose of selection

## Consequences

- Different capabilities can be in different modes in the same pass (navigate.symbol = graph-amplified, search.ui = sparse-mode)
- Density bucket renders on every card as a pill
- Tuning thresholds is a single change to bucketByCount
- Day-zero install behavior is deterministic: every capability returns 'absent' from EMPTY_DENSITY_PROBE

**Risks accepted:**
- Probe fields go stale during a long pass — acceptable; mode is decided once per pass per ADR-163
- Thresholds mis-tuned for a small project that never crosses 50 entities — mitigated by 'partial' bucket which still uses graph-first first

## Guard Rails

> ⚠️ measureDensity MUST stay pure (no I/O, no Date.now, no random)

> ⚠️ DensityProbe MUST stay readonly; never mutated after construction

> ⚠️ Adding a CapabilityId requires adding a case to measureDensity (TypeScript exhaustive switch)

> ⚠️ Bucket thresholds (10, 50) MUST live in one helper (bucketByCount) for tunability
