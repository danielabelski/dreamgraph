# ADR-218: Standalone Architect plan status separates lifecycle from execution state

**Date:** 2026-05-28T21:35:17.018Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** src/architect/plan-registry.ts, src/architect/routes.ts, tests/standalone-architect-routes.test.ts, standalone_architect_plan_lifecycle_projection, browser-architect-ui-level-2  

## Context

Standalone Architect plan status projection used a vague single status field and could let generic action_recorded checkpoints override durable implementation checkpoints, causing Browser Architect UI Level 2 to show unknown or stale current slice after completed work.

**Constraints:**
- ADR-209 requires active plan operational state to be daemon-owned and reconstructable from operational records plus append-only implementation logs.
- Planning and implementation are separate lifecycle concerns; UI must not collapse them into a vague in_progress or unknown status.
- Generic chat/action audit entries are useful history but must not outrank concrete implementation slice checkpoints for current resume status.
- Browser UI remains a projection surface and must refresh from daemon APIs after governed chat runs instead of owning authoritative status locally.

## Decision

Project standalone Architect plan state as distinct plan_lifecycle and execution_state fields, with last_completed_slice, next_slice, active_slice, and active_phase derived from daemon-owned implementation-log checkpoints. Concrete implementation checkpoints are preferred over generic action_recorded entries, and the browser refreshes the daemon plan projection after chat runs so status changes are visible without manual page reload.

### Alternatives Considered

- **Continue displaying only plan.status/current_slice from the latest log heading.** — Rejected: This kept Status unknown/in_progress and allowed generic action_recorded checkpoints to hide completed implementation slice progress.
- **Let the browser infer current slice from visible plan text after a run.** — Rejected: That would make the browser an authority for operational plan state, conflicting with ADR-209.

## Consequences

- Browser Architect can show Lifecycle implementing, Execution idle, Last completed Slice 1, and Next slice Slice 2 for Browser Architect UI Level 2 after Slice 1 completion.
- Timeout or partial execution can be represented as execution_state timed_out or partial without corrupting plan_lifecycle.
- Plan rail and detail chips refresh from daemon projections after chat runs.

**Risks accepted:**
- Implementation-log parsing still depends on checkpoint heading conventions; malformed logs may project less detail until parser support expands.
- Existing consumers of plan.status may need migration to the richer operational_state fields.

## Guard Rails

> ⚠️ Do not use a vague single in_progress status as the only plan state display.

> ⚠️ Do not let generic action_recorded or chat-plan-update checkpoints override later concrete implementation checkpoints as current slice.

> ⚠️ Do not make browser-local storage the source of truth for lifecycle, execution state, completed slice, or next slice.

> ⚠️ Keep plan_lifecycle and execution_state distinct in daemon payloads and UI labels.
