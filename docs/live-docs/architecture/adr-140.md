# ADR-140: Architect v2 lives in a parallel folder; main stays shippable until the v10.0.0 cutover commit

**Date:** 2026-05-09T19:54:53.958Z  
**Status:** accepted  
**Decided by:** collaborative  
**Affected entities:** extensions/vscode/src/architect-v2/, extensions/vscode/src/chat-panel.ts, extensions/vscode/src/architect-llm.ts, extensions/vscode/src/extension.ts, plans/ARCHITECT_V2_SLICE1_INVENTORY.md  

## Context

DreamGraph v9.0.0 "Lattice" just shipped with a working but heavily patched Architect surface (~17000 LOC across ~60 files in extensions/vscode/src/, including a chat-panel.ts.good rollback artifact next to a 3600-LOC chat-panel.ts). A clean rewrite toward v10.0.0 must happen without breaking the released extension on main, without a long-lived feature branch that rots, and without a half-migrated state where v1 and v2 fight over the same files.

**Constraints:**
- Main must remain shippable at every commit during the rewrite.
- No long-lived feature branch is allowed; integration friction would compound over a multi-slice rewrite.
- Existing v1 Architect must keep working for users on v9.x throughout the rewrite.
- v2 must be free to evolve its internal shape without touching v1 source files.
- The cutover from v1 to v2 must be a single auditable event, not a gradual blend.

## Decision

Build Architect v2 in a parallel folder at extensions/vscode/src/architect-v2/. The existing v1 Architect surface stays untouched on main and continues shipping in v9.x releases. The v10.0.0 release is defined as the cutover commit that (a) deletes the v1 Architect files enumerated in plans/ARCHITECT_V2_SLICE1_INVENTORY.md §6 and (b) renames extensions/vscode/src/architect-v2/ contents into the canonical positions extension.ts expects. No mixed-mode period; cutover is atomic.

### Alternatives Considered

- **In-place rewrite of the existing files** — Rejected: Would either break main mid-rewrite or require a long-lived feature branch that diverges from main and accumulates merge debt across multiple slices.
- **Long-lived feature branch (architect-v2 branch)** — Rejected: Multi-slice rewrites on a side branch always rot; merge cost grows nonlinearly and the team loses incremental release leverage.
- **Gradual file-by-file replacement on main** — Rejected: Creates a half-migrated state where v1 and v2 share file paths, causing tool collisions, prompt collisions, and unclear ownership during the transition.

## Consequences

- Main is releasable at every commit during the rewrite — v9.1, v9.2, … can ship intermediate slices behind a feature flag (or stay unreleased) without disturbing v1 users.
- The v10.0.0 cutover is a single auditable commit with a precise deletion manifest (plans/ARCHITECT_V2_SLICE1_INVENTORY.md §6).
- v2 surfaces evolve freely under architect-v2/ without ever touching v1 source files, eliminating accidental cross-contamination.
- Rollback at any point before cutover is trivial — delete architect-v2/ and ship.

**Risks accepted:**
- Some shared infrastructure (extension.ts, commands.ts, daemon-client.ts, types.ts) must be refactored carefully so that v1 keeps working while v2 grows next to it.
- Two near-parallel implementations briefly increase repository size during the rewrite period.
- Cutover commit will be large by line count (mass deletes + renames), requiring careful review.

## Guard Rails

> ⚠️ Do not modify v1 Architect source files (the deletion list in plans/ARCHITECT_V2_SLICE1_INVENTORY.md §6) for new feature work during the rewrite — only critical bugfixes.

> ⚠️ Do not begin in-place renaming of architect-v2/ contents into the v1 file paths before the formal v10.0.0 cutover commit.

> ⚠️ Do not allow v2 code to import from v1 files or vice versa; the two surfaces are isolated until cutover.

> ⚠️ Do not introduce a long-lived 'architect-v2' branch; all v2 work lands on main inside extensions/vscode/src/architect-v2/.
